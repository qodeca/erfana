### 4.1 #324 (asar integrity)

The macOS session asked for a crash dump, an A/B with the two asar fuses off, and a RunAsNode test build.

- **Crash dump**: no `0xC0000409` crash in 45 runs under `cdb` (15 each of the PR build, the PR build with the asar fuses off, and the `develop` base `fb17d71b`). The x64 `cdb` from WindowsApps is the same ARM64EC engine as the ARM64 one and froze the debuggee in some runs ("GetContextState failed, 0x8007001F") in **all three** builds, so a 180 s watchdog took a hang dump and ended the run.
- **Asar-fuse A/B without a debugger** (15 runs each, PR / fuses off / base): crashes 0 / 0 / 0; a graceful quit slower than 30 s 0 / 1 / 2; driver timeouts at 240 s 1 / 1 / 1. In total the PR build had 2 slow or stuck runs out of 29 and `develop` 0 out of 25 in the debugger-free rounds, which is within the noise of this host; nothing points at the fuses.
- **Check 5 (winpty)**: OK.
- **Check 6 (RunAsNode copy)**: 6a every loaded app path is inside `app.asar`; 6b a path outside it gives `MODULE_NOT_FOUND`; 6c a resolve outside `app.asar` is refused; 6d a real `.docx` import succeeds in 511 ms with LiteParse loaded from `app.asar.unpacked`.
- **Side finding**: each start of these pre-`ea0c2ae8` builds left one `soffice.bin --version` process behind (68 after the A/B rounds; all stopped). `develop` no longer runs `soffice` on Windows (`ea0c2ae8`), so this does not affect v0.22.0.
