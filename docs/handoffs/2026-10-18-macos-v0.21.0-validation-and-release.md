## 0. Blocker first – Apple notarization (owner action)

The 2026-10-18 dry-run (run 39144882739) built and signed the macOS app, then notarization failed:

```
⨯ Failed to notarize via notarytool.  Failed with unexpected result:
Error: HTTP status code: 403. A required agreement is missing or has expired.
```

Not a code or secrets problem: Apple has a new or lapsed developer agreement that the team's **Account Holder** has not accepted. Until it is accepted, **every** macOS release build fails here. Cookbook: `.claude/skills/releasing-erfana/guides/troubleshooting.md` → Row 13.

1. Ask the owner whether the agreement is accepted (developer.apple.com/account, and App Store Connect → Business if it lists one). Only the Account Holder can do it; you cannot.
2. Then re-run the dry-run and wait for it – it needs the owner's approval of the `production-signing` gate (on 2026-10-18 `gh api -X POST …/pending_deployments -F "environment_ids[]=$ENV_ID" -f state=approved -f comment=…` worked; if it returns 422, see the troubleshooting "HTTP 422 not an integer" entry):
   ```
   gh workflow run release.yml --ref main -f dry-run=true
   ```
3. **Do not tag v0.21.0 until that dry-run is fully green** (Prepare, Build macOS including notarization, Build Windows). A tag spent on a failing notarization cannot be reused – the ruleset forbids deleting `v*.*.*` tags, so it would burn the version.

§ 4 and § 5 do not depend on this; run them while waiting.

## 5. Manual checks on macOS (the gate does not cover these)

Run the app with `npm run dev` (or the `build:mac:test` app). Logs: `~/.erfana/logs/main.log`.

**A. The new project watcher (#241) – the reason this handoff exists**

1. Open a project. `main.log` must show `Directory watcher backend selected` with `backend: "native-recursive"`, then `Native directory watcher ready` (counts only).
2. From the terminal (inside Erfana or outside), in the project: create a file, create a folder, rename a file, move a file into a subfolder, delete a file, delete a folder. The tree must follow each change on its own within ~2 s, with no manual refresh.
3. Rename **the folder that contains an open file**, and delete a folder while one of its files is open. The tree must update; the open tab must behave as before (no crash, no silent data loss).
4. A file named with glob characters, e.g. `[draft] {v2}.md`: it shows in the tree, opens, and an external edit to it reloads in the editor.
5. **Large project / file handles** – the bug the old chokidar 3 pin existed for: open a project with 20,000+ files (e.g. a repo with `node_modules`, or `mkdir -p big && for i in $(seq 1 25000); do touch big/f$i.md; done` inside a scratch project). Then:
   - `lsof -p <main Electron pid> | wc -l` – expect hundreds, **not** tens of thousands. Get the pid with `pgrep -f "Electron.*erfana" | head -1` (or Activity Monitor; check it is the main process, not a helper).
   - Export a Markdown file to **PDF**. It must succeed (the old failure was "Failed to initialize sandbox").
6. `files.exclude` in `.erfana/settings.json` (e.g. `["big"]`, reopen the project) hides that folder and changes inside it no longer refresh the tree.
7. Git status: commit / checkout in the terminal – the tree's git badges update.
8. Case: rename `notes.md` → `Notes.md` (APFS is case-insensitive). Tree shows the new name once, no duplicate, no ghost.
9. Escape hatch: start with `ERFANA_DIRECTORY_WATCHER=chokidar npm run dev` on a **small** project – it must still work (log says `backend: "chokidar"`). Do not test it on the large project; it is expected to run out of file handles there.

**B. Electron 44 (#240)**

10. Image viewer → **Copy as image**, paste into Preview / Notes: the image appears. Export image to PNG and PDF.
11. Export a Markdown file to PDF and to DOCX. The save dialog opens in the **last folder you used** (not Downloads); cancel works.
12. Clipboard text: copy from the editor and from the terminal, paste both ways.
13. HTML preview: open one, switch tabs until it sleeps, come back – the still picture shows, then the live page.
14. Screenshot / Screen Recording permission flow still works (macOS-only grant + relaunch).
15. Terminal: `claude` (or any shell) runs; the Claude Code context bar updates.

**C. LiteParse 2 (#167)**

16. Import a PDF, a `.docx` and an image (PNG/JPG) – each converts to Markdown. A file over the size cap is refused with a message.

## 6. Release (only if § 0's dry-run, § 4 and § 5 are all green)

Use the **`releasing-erfana`** skill. It owns the whole procedure: Phase 0 pre-flight (via `release-quality-runner`), two-tier release notes, signed tag, `release.yml`, minisign + sha256 verification, and the operator publish gate. Things that are easy to miss:

- **Run it from `main`.** The skill refuses any other branch.
- **Release date.** `docs/CHANGELOG.md` says `*Released 2026-10-18. Tag v0.21.0.*`. If you release on a later day, fix the date in the §1.5 commit.
- **`main` rejects an unchecked SHA (`GH006`).** The release-notes commit must land on `develop` first, earn its green checks, then fast-forward `main` – the skill's §1.5 does this; do not push it straight to `main`.
- **Signing.** The tag must be signed (`guides/git-signing.md`). The `production-signing` environment gate in `release.yml` needs the owner's approval in GitHub.
- **Audit.** Policy is zero high/critical production advisories. `docs/security.md` still has the dated "Accepted exceptions for v0.20.1" table as history; v0.21.0 needs none. Any new production advisory blocks the release – report it.
- **Windows status snapshot** is already re-anchored on v0.21.0 (`docs/windows/implementation-plan.md`). If you fix anything Windows-relevant before tagging, extend that note.

## 7. If something is red

- **Do not release.** Write down the failing check, the exact output, and whether it reproduces focused.
- Product bug: branch off **`develop`** (`fix/<name>`), fix with a test, PR to `develop`, merge through the **merge queue** (below), wait for `develop`'s checks on the merge SHA, fast-forward `main` to it, then restart § 4 on the new `main`. Add a CHANGELOG line under `## 0.21.0` if users would notice.
- The macOS watcher misbehaves and the fix is not quick: the low-risk fallback is to make `selectDirectoryWatchBackend` return `chokidar` on `darwin` again – **but chokidar 5 on macOS costs one file handle per file**, so a large project would hit the old FD-exhaustion crash. That trade-off is the owner's call; ask, do not decide.
- Anything that needs a decision (skip a check, ship with a known issue, change the version): ask the owner.

## 8. Repo facts for this session

- `develop` has a **merge queue**; `gh pr merge` fails. Enqueue with:
  `gh api graphql -f query='mutation($id:ID!){enqueuePullRequest(input:{pullRequestId:$id}){mergeQueueEntry{state}}}' -f id="$(gh pr view N --json id -q .id)"`, poll until `MERGED`, then delete the branch by hand.
- `main` is direct-push but enforces the 7 required checks on push: push the SHA to `develop` first, wait for green, then `git push origin <sha>:refs/heads/main`.
- Lockfile: after any `npm install --package-lock-only`, re-check `node_modules/encoding` is still in `package-lock.json` (npm 11 drops it; `npm ci` then fails in CI).
- `THIRD-PARTY-LICENSES.md` is generated on a darwin-arm64 tree (`npm ci --ignore-scripts --os=darwin --cpu=arm64` in a temp dir, `npx generate-license-file`, keep the first 34 header lines). Regenerate only if dependencies change.
- Open follow-up, not a release blocker: `src/main/index.ts:256` calls `shell.openExternal(details.url)` without a scheme check.
