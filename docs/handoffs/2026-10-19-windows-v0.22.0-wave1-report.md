## 4. #214 – fatal error while quitting

**Outcome: reproduced, cause found, fixed in [#261](https://github.com/qodeca/erfana/pull/261).** The PR says "Refs #214"; the issue is left open for the owner (see § 6).

- **Cause.** On quit, `TerminalService.dispose()` killed the shell and returned at once, and `app.exit(0)` followed within about 80 ms. node-pty reports a ConPTY shell's exit from a native thread that calls back into JavaScript (`node::MakeCallback` → `v8::Function::Call`, as in the issue). The shell ends 115–400 ms after the kill (median 147 ms). When that report arrived during Node teardown, V8 aborted the process – exit code `0xC0000409`; the crash site is the C runtime `abort()` path.
- **Not the cause.** A synchronous quit trace showed every disposer, including the directory watcher close, settled before `app.exit(0)` in every crashed run. File churn is not needed to reproduce it.
- **Fix.** `dispose()` waits until each killed shell has reported its exit – also shells killed earlier by a window close – bounded by 1.5 s.

Hit rates (dev build, quit after 15 s, 40 quits per row unless noted):

| Build | Setup | Crashes |
|---|---|---|
| `develop` | 190,400-entry project, churn | 1 / 20 |
| `develop` + trace | 19,040-entry project, churn | 8 / 40 |
| `develop` + trace | no churn | 6 / 40 |
| `develop` + trace | no churn, terminal off | 0 / 40 |
| `develop` + trace | no churn, 4 s wait before exit | 0 / 40 |
| #261 | no churn | **0 / 40** |
| #261 | churn | **0 / 40** |

The Windows event log on this host shows the same crash offset about 50 times since 2026-10-18, many during e2e runs.

Regression test: `TerminalService.test.ts` › "Issue #214 - dispose waits for shell exit" – 3 of 4 tests fail without the fix.

## 5. #208 – large, changing project

**Outcome: no crash, no overlapping tree reads, 0 failed reads and a normal quit in two soaks of about 4 hours.** Main-process memory is flat between tree reloads. Two limits:

- Run 1 lost about 33 minutes to host pauses of the VM.
- Run 2 had no pause, but the app window was not painted for most of the run, so the tree was reloaded only in two bursts. A burst fell in the last hour, so the "last-hour peak within 25 % of the first-hour peak" rule fails as written (115 → 266 MB heap). The heap was back at 34 MB six minutes later.

## 6. Open questions

1. **Close #214?** Acceptance criterion 4 asks the log to show "watchers disposed". `DirectoryWatcherService.safeLog` suppresses its lines while disposing, so the log cannot show it; the quit trace did. Either accept the trace as evidence or add one quit-time log line.
2. **A failed save logs the full file path.** `renderer.log` has `[RENDERER] Error saving file … open '<full path>'` (seen in S1/S3). The main-process rule is `redactUserInput`; the renderer path is not covered. The main-process `FileService: readDirectory error recovered` warning also logs the full folder path (seen in the #208 soak).
3. **E2E `KeyboardHelper.save()` presses `Control+S`.** The app's handler matches lowercase `s`, so in a hand-written harness the save did not fire; `Control+s` worked. I found no `*.e2e.ts` that calls it today, so it is a trap for the next test, not a hidden failure. Fix the helper?
4. **Terminal e2e need a POSIX `touch`.** `directory-watcher` and `preview-refresh-terminal` fail when the suite starts from PowerShell (no `touch`); they pass from Git Bash.
5. **Visual baselines depend on the host window size.** Five visual tests failed on the first run and passed on the last, with no code change in between.
6. **Unit-test timeouts under load.** `excludeMatcher` and the eslint POSIX-path guard also timed out once (besides `previewSchemeScope`). Add them to `docs/windows/known-flakes.md`?
7. **`.e2e-temp\` holds 852 old entries.** Delete them by hand?
8. **node-pty prints `AttachConsole failed` on every quit** (its `conpty_console_list_agent` helper, after the console is gone). Harmless here; not changed.
9. **S1 wording in the brief.** The command opens the file with `FileShare.Read`, which tests "no writer allowed", not "no delete sharing". Both behave correctly (§ 3).
10. **#208 memory rule.** Run 2 fails "last-hour peak within 25 % of the first-hour peak" only because a tree-reload burst fell in the last hour; between reloads the heap stayed at 20–44 MB for 4 hours. Accept that as a pass, or rerun with the window kept painted (host display awake) so reloads run all the time?
