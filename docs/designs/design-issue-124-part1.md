## 1.4 Fixes – confirmed causes only (WI-9)

- **C1 – per-frame measure-and-compare.** While `enabled && isVisible && isLive`, one rAF loop measures the placeholder and sends only when x, y, width, height or the find inset changed. That is at most one message per frame while moving and none while still (#120 smoothness unchanged). It replaces the first-rect pump; the observer and the window `resize` listener call the same compare-and-send, so a background tab still has the right size when activated. `pushBounds()` keeps its boolean return. The same measure computes the visible area (C2, below) and has a forced-push option – a push sent even when the rect is unchanged – for C2's return; WI-11 reuses it for `settled`. **As built (WI-9a):** the first measurement of every run is forced (main may have a brand-new view, or the tab was just activated); `pushBounds()` is the forced push; the find bar re-pushes only on a real toggle; a visible measurement while the `collapsed` flag is set is acted on even when unchanged, so the way back is never missed.
- **C2 – a clipped placeholder hides the view** (re-diagnosed by WI-8, §1.8). The collapsed centre's placeholder is not 0×0: it keeps a valid 100 px rect that paints nowhere, because an ancestor with non-visible overflow and width 0 clips it – so it is sent, and nothing hides the view.
  1. **One predicate in the loop's measure.** Visible area = the placeholder's bounds (after the find inset, so the find-bar strip never counts as page) intersected with the rect of every ancestor up to `<html>` that clips: its computed `overflow-x` or `overflow-y` is `hidden`, `clip`, `scroll`, `auto` or `overlay`, or its `contain` includes paint (`paint`, `strict`, `content`; `.dv-render-overlay` has `contain: layout paint`, `dockview.css:827`). As built (WI-9a), the predicate, the pure intersection and the ancestor walk are in a new `previewClip.ts` (`clipsDescendants`, `intersectRects`, `visibleArea`) – the plan had put the intersection in `htmlPreview.logic.ts` and the walk in the hook. A 0×0 rect never reaches it: it is degenerate (R3).
  2. **An empty area is never sent.** No `setBounds`: one R7 info line (`clipped-away`, with the measured rect) through the hook's reporter, once per change of that rect, and `clearRect(panelId)` in `usePreviewViewportStore`, so toasts stop avoiding a rect nothing occupies. The clear is keyed on geometry, not on the guard's output, so it cannot loop with the toast occluder.
  3. **The hide goes through the guard.** Once a rect has gone out since the view became live, an empty area sets the per-panel `collapsed` flag in a new `usePreviewCollapsedStore`; before the first send it is simply not sent, so an opening preview never flaps between hide and show. `OverlayGuardService` stays the only `setVisibility` caller: `getPanelGate` returns the chrome gate, else `'collapsed'`; `subscribeGate` subscribes to both stores; a new `collapsed` visibility reason (`VISIBILITY_REASON`, local to the guard – the IPC reason is a free string) names it in main's log. A separate store, not the chrome-gate store: that one has a single reason slot owned by `usePreviewChromeGate`, and two writers would overwrite each other.
  4. **Return, in this order:** one forced push (sent even if the rect is unchanged), then the flag is cleared, then the guard shows – so the view is shown at its new rect. The order holds because both are plain `ipcRenderer.send` calls (`previewBridge.ts:75`, `:84`) and main applies `setBounds` synchronously (`lifecycle-handlers.ts:228`); no coalescing was found in the files examined.
  5. **The loop keeps running while collapsed** – the hook's `isVisible` stays true – so it sees the return within a frame. This also covers the 1.75 s delay the e2e saw once: the check hides the view whatever the placeholder's own rect does.
  - **As built (WI-9a).** A 0×0 placeholder after a send collapses too, and logs R3, not R7. Every empty result – degenerate or clipped – clears the viewport rect. A background tab never collapses: only the visible, live tab that has sent a rect sets the flag. The flag survives a tab switch, so a panel re-activated while still collapsed never flashes a stale strip, and it is cleared when the view stops being live and on unmount. R3 and R7 are logged once per change of the measured rect, never per frame. A partly clipped placeholder is sent whole.
  - Rejected: an `IntersectionObserver` (it reports after the frame's layout, so the strip is drawn for at least a frame; jsdom has none, so a unit test could not recreate the clip) and a gate on `terminalExpanded` (couples the guard to one layout feature, flips before `setVisible` so the guard shows before a fresh rect on restore, misses any other clipping container). Not covered on purpose: a partly clipped placeholder – never reproduced, and the centre's 400 px minimum keeps the 100 px group inside it (answer 1).
  - Unchanged by C2: the drag freeze, except that a `collapsed` panel counts as no visible preview (§1.5); the stale picture (a collapsed hide is "any other hide"; the latch still starts only on the drag occluder or `resizeHold {held: true}`); the window-edge hold (a collapse during a hold is a recorded `setVisibility(false)`, so `release()` stays hidden).
- **C3 – zoom from the host window.** `PreviewWindowLike.webContents.getZoomFactor` (declared in `previewLiveTypes.ts`, added as optional in WI-5 for M10) becomes required, per the existing `isDestroyed` rationale (a `BrowserWindow` satisfies it structurally); the dep becomes `getZoomFactor(window)`, defaulting to the host's. The dep type and its hand-offs live in six places, and C3 edits all of them (RA2-3): `previewLiveTypes.ts` (the live-view dep, `:85`), `previewLiveBounds.ts` (the call in `computeBounds`, `:103`; its deps already carry the window), `previewViewTypes.ts` (the service dep, `:141`) and `PreviewViewService.ts` (its hand-off, `:88`), `preview-handlers.ts` (`:64`, `:99`) and `buildPreviewGraph.ts` (`:68` and the default at `:133-136`, used at `:144`) – never `PreviewLiveView.ts`, and never `previewLiveWiring.ts`, which passes the dep through unchanged (`:99`) (RA3, RA2-3). Line numbers as of G4, after WI-10. Confirmed (§1.8), so it ships. **M10 stays as a tripwire:** after the fix it fires only if something feeds a non-host zoom – such as a `getZoomFactor` dep passed to `buildPreviewGraph` in production, exactly the regression to catch. Keeping it costs no lines (deleting it would also edit `previewBoundsDropLog.ts` and five tests), and its runtime cost is one `getZoomFactor()` per applied push, main-side. The comment at `previewLiveBounds.ts:120` changes from "C3's fix (WI-9)" to "a tripwire after C3". **As built (WI-9b):** the dep takes `Pick<PreviewWindowLike, 'webContents'>` – the host window – (`previewLiveTypes.ts:90`), `webContents` is required (`:60`), `buildPreviewGraph`'s default reads the host's zoom (`:142`, used at `:151`), and `PreviewViewService.ts` stayed at 485 lines; of the M10 tests one went (no host page – impossible now) and three came (the host window is passed; silent with the default; a control fires when a host-ignoring dep is injected).
- **No main-process fallback on window resize for position.** With C1 fixed the renderer re-measures every frame; main reacts to window resizes only for the drag freeze (§1.5).

## 1.5 Drag freeze (answers 4 and 6, UX §4) – WI-10 and WI-11

### Splitter drag (renderer)

| Moment | What happens |
|---|---|
| `pointerdown` on `.dv-sash` (document, capture phase) | arm; nothing visible |
| first `pointermove` beyond `PREVIEW_LIMITS.DRAG_FREEZE_MOVE_THRESHOLD_PX` (3) | if a live preview is visible: register the `drag` occluder synchronously, and hold further moves (a capture-phase `pointermove` listener on `window` calls `stopImmediatePropagation`) until main's `visibilityApplied(false)` arrives for that panel; then stop holding |
| during the drag | dockview lays out as usual; bounds pushes are applied to the hidden view |
| the drag ends – the first of `pointerup`, `pointercancel`, `lostpointercapture`, a window `blur`, or a `pointermove` with `buttons === 0` | wait two animation frames, push fresh bounds, then release the occluder; the guard shows the page, main re-adds it topmost at the settled rect |
| after the show | what the hide showed – the picture, or the backdrop for a stale picture (latched, below) – stays until `visibilityApplied(true)` for that panel, so there is no empty frame and no flash |

- A click without movement registers nothing. No visible preview (inactive tab, open host list, dialog) → nothing. A panel hidden by the `collapsed` gate (§1.4, C2) counts as no visible preview too – otherwise a sash drag with the terminal expanded would hold moves waiting for a `visibilityApplied(false)` that never comes (the view is already hidden), the sash would not move, and the drag would end in `drag-hide-unconfirmed`.
- **Hide not confirmed when the drag ends:** the layout never moved (moves were held), so just release and log `drag-hide-unconfirmed`. The strict rule wins over responsiveness.
- **The panel loses its live visible view while moves are held** (renderer crash, suspend, eviction): stop holding at once and log `drag-hold-abandoned` – there is nothing left to cover (RU12).
- **A slow hide:** when the confirmation arrives more than `PREVIEW_LIMITS.DRAG_HOLD_SLOW_LOG_MS` (150) after the hold began, log `drag-hide-slow` with the elapsed time. No timer: the time is measured when the confirmation arrives.
- **The pointer over the live view (S14, inconclusive).** In a fast drag toward the preview the pointer may cross the native view before the hide lands; if the view takes the events, Erfana gets no more moves and no `pointerup`. The end signals above cover that case: the host loses pointer capture or focus, or its next move arrives with no button pressed. S14 could not prove it with synthetic input (which skips hit-testing), so its manual variant, the spike script `s14m.cjs` (a run note, not kept in the repo), joins the manual QA list, and WI-27 drags fast into the preview area on macOS, asserting only the end state.
- Dockview's sash handler reads the absolute pointer position (`splitview.js:412-420`), so held moves lose no distance. WI-27 pins it: after release the sash sits where the pointer is.
- Code: a pure controller `src/renderer/src/services/preview/previewDragFreeze.ts` (injected document, window, clock, rAF, "is a live preview visible in this panel", visibility-applied subscription, logger), mounted once by `useSplitterDragFreeze` (`src/renderer/src/hooks/`) in `AppDockLayout.tsx`.
- **No guard trap.** The renderer drives the hide through the occluder, so main's report agrees with the guard's cache and `OverlayGuardService`'s re-sync never fires.
- **As built (WI-11).** More end signals: a `contextmenu`, or any press during a drag, ends it; a second touch or pen is ignored. The threshold is more than 3 px. An unconfirmed hide releases at once; when the view is lost during a hold the holding stops, and the hide stays until the drag ends. The guard gained `visiblePanelId()`. Log message `Preview drag freeze`: `drag-hide-unconfirmed` at warn, `drag-hide-slow` and `drag-hold-abandoned` at info. The controller releases with `afterTwoFrames`, and `usePreviewDragFreezeTarget(panelId, pushBounds)` connects each panel's forced push. WI-27's spec, `e2e/html-preview-drag-freeze.e2e.ts`, never saw a drag-freeze log line fire.

### Window-edge drag (main)

- **Listeners in the app entry (RA5).** `src/main/index.ts` listens to the main window's `will-resize` and `resized`, next to the existing `closed` → `previewHandlers.closeWindow(windowId)` wiring (`:282`), and calls a new bundle method `previewHandlers.setResizeHold(windowId, held)`. The service keeps a per-window hold map and uses the pure state machine in `previewResizeHold.ts`. No Electron window event enters the service and `PreviewWindowLike` is unchanged, so WI-10 leaves the 2 194-line service suite and its cast fakes untouched. `closeWindow(windowId)` also drops that window's hold-map entry and its timers (RX2-4).
- **`held: true`** (the first `will-resize`; manual resizes only, macOS and Windows): for every shown view of that window, `visibility.hold()` – `setVisible(false)` **without** emitting `visibilityApplied`, and the cached still is published with its `stale` flag – and `preview:resizeHold {panelId, held: true}` is emitted. A `setVisibility(true)` or `(false)` during the hold is recorded, not applied; bounds are applied while hidden, as today. Every later `will-resize` restarts `PREVIEW_LIMITS.RESIZE_HOLD_MAX_IDLE_MS` (2 000); when it runs out with no `resized` (a lost or missing event), the hold ends as if `resized` had arrived, so a hold can never last forever (RX2-4). A user who pauses mid-drag for longer sees the page return at the paused size, and hide again on the next move.
- **`held: false`** (`resized`, or the idle maximum): emit `preview:resizeHold {panelId, held: false}`. The bounds hook answers two frames later with a forced push (sent even when the rect is unchanged) carrying `settled: true`. Main applies it and calls `release()`.
- **No settled push within `RESIZE_HOLD_SETTLE_TIMEOUT_MS` (500) (RS8, RX2-4):** the view stays hidden; main logs M9 and emits `held: false` once more. At the second timeout, if any bounds were applied after `resized`, main calls `release()` at those bounds – a settled layout that sends nothing is still shown. If none were, it logs M9 again (through the reporter, so repeats are capped) and asks again at every further timeout until a push arrives or the view closes. The view is never shown at bounds that predate `resized`. WI-11 (G6) answers `held: false` with the forced push two frames later (`pushSettledBounds` in `usePreviewEvents`); no e2e fires `will-resize`, so a person's window-edge drag stays a manual check (§1.8, parent §5.5).
- **One release function (RX2-4, RA3-2).** The settled push, the second timeout and the idle maximum all end the hold through the same `release()`, which reads the **latest** wanted state. If an occluder was raised during the hold – the external-link consent dialog, a menu – the view stays hidden and `release()` emits `visibilityApplied(false)`; otherwise it shows the view and emits `visibilityApplied(true)`. Either way the renderer clears `resizeHeld` only on that event, never on `held: false` (RU2-4). `previewResizeHold.ts` is the only caller of `visibility.release()`. The settled push reaches it as `settled(panelId)`, which clears that view's settle timer before releasing.
- **A stated exception to the single-hider rule.** The hold hides views without the overlay guard knowing; the guard's cache keeps "visible", so it never re-syncs against the hold. The guard's header comment (WI-11) and the panel's `CLAUDE.md` (Phase 10) name it as the one sanctioned bypass.
- The store's `resizeHeld` flag is set on `held: true` and cleared on the `visibilityApplied` that `release()` emits.
- Maximize, full screen, snapping, display moves and e2e `setSize` fire no `will-resize`; they are covered by the C1 fix, not frozen (UX §4) – and §1.3 says what happens when C1 is unconfirmed.
- Unverified: whether the first `will-resize` lands before the first resized frame paints on macOS. Manual QA item; unit tests pin the wiring.
- Tests (WI-10): an occluder raised mid-hold stays covered after the release; a settled layout that sends nothing is shown after two timeouts; a hold with no `resized` ends at the idle maximum; `release()` emits `visibilityApplied` either way; a settled push clears the settle timer – no M9 and no second `held: false`; the hold-map entry goes with `closeWindow`.

### The still picture

- **Fixed size, top-left.** The still carries `cssWidth` and `cssHeight`: the CSS rect of the view when the frame was taken, recorded by `PreviewStillFrameCache` at capture. `PreviewFallback` renders the `<img>` at that size (top-left, no scaling), inside a placeholder with `overflow: hidden`: a narrower panel crops, a wider one shows the backdrop.
- **Freshness – real input only (RU3).** Main listens to the preview's `input-event` (the type list is in `electron.d.ts:8734`). These types mark the cached frame stale and restart the idle timer (`STILL_FRAME_IDLE_REFRESH_MS`, 500 ms): `mouseWheel`, `gestureScrollBegin`, `gestureScrollUpdate`, `gestureScrollEnd`, `gestureFlingStart`, `gestureFlingCancel`, `gesturePinchBegin`, `gesturePinchUpdate`, `gesturePinchEnd`, `rawKeyDown`, `keyDown`, `char`, `mouseDown`, `mouseUp`, `touchStart`, `touchMove`, `touchEnd`, `touchCancel`. Every other type – `mouseMove`, `mouseEnter`, `mouseLeave`, `pointerMove`, `pointerRawUpdate`, `contextMenu` and the tap gestures – leaves the frame fresh, so a pointer crossing the page on its way to a splitter does not blank the drag. When the timer fires and the view is drawn, `captureWhileVisible()` refreshes the frame, keeping the chained settle barrier and the in-flight skip.
- **Stale picture → plain background, during drags only (answer 6, RU4, RU2-4, RU3-2).** Every hide publishes the cached still as today, now with `stale: true` when real input happened after the capture (`stale` is omitted when false). The renderer **latches** its choice when a drag or hold hide begins – the moment the splitter `drag` occluder registers or `resizeHold {held: true}` arrives: a stale picture gives way to the placeholder backdrop (the page's paper colour), a fresh one stays. The latched choice lasts until main confirms the show with `visibilityApplied(true)` for that panel; a `visibilityApplied(false)` never ends it – the drag's own hide confirmation is one, and a release that stays hidden because an occluder was raised meanwhile keeps the latched choice until the show. It is not keyed on the occluder or on `resizeHeld`, which clear before the page is back, so neither release sequence flashes the old picture or blinks the backdrop. Every other hide that begins while the page is shown – dialogs, menus, the band's host list, tab switches, the unsaved-changes prompt – shows the picture as today. There is no `preview:stillFrameCleared` event.
- Tests (WI-11), in `PreviewFallback.test` and `usePreviewStore.test`: the splitter sequence (occluder released → the latched picture or backdrop kept → `visibilityApplied(true)` → cleared), the window-edge sequence (`held: false` → settled push → `visibilityApplied(true)` → `resizeHeld` and the latch cleared), and a stale picture under a drag occluder followed by `visibilityApplied(false)` – the backdrop stays until `visibilityApplied(true)` (RU3-2).
- As built (WI-11): the latch is a mode that follows the current still's `stale` flag. A `suspended` does not clear it – a view suspended mid-drag shows the plain background until it resumes – while `resizeHeld` clears on `suspended`, unmount and either `visibilityApplied`. `PreviewFallback` draws a frame with `cssWidth` / `cssHeight` at that size (`html-preview-still-frame--sized`) and one cached before WI-10, which lacks the size, filling the area (`--fill`).
- Because `stale` is omitted when false and the CSS size rides inside the cached frame, `PreviewViewService.test.ts:1420-1432` ("publishes the cached frame on hide") stays unchanged.
