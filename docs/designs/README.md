# Designs

Every design lives in a folder named after the functionality it changes, never loose in this
folder and never named after an issue number: `docs/designs/<functionality>/`. A new feature
starts a new folder with a `README.md` that uses the headings below; work on an existing
functionality goes into that functionality's folder. The design system itself is in
`docs/design-system/` (open `docs/design-system/index.html`) – reusable rules for the whole app,
not per-feature design work.

**Open [`index.html`](index.html)** for every screen and design note, grouped by functionality folder. It is
generated by `npm run design` from the folders and the screens' `@card` markers – do not edit it.

## Screens and the design system

A screen is an HTML page here that shows one feature's UI. It reuses the design system's CSS
(`../../design-system/tokens.css`, `ds.css`, and component CSS) and **cites the card** for every system rule
it applies – a colour pairing, a focus ring, a menu's keyboard contract. A screen **never decides a system
rule**. If a screen needs a rule the system does not have, the rule is proposed on a design-system card (or
a new card) and the screen links to it; a screen that quietly invents one is how two documents start
describing one app.

### Screen status

Line 1 of every screen is the same marker the cards use:

```html
<!-- @card group="Comments" name="Comment window" subtitle="…" status="proposed" reviewed="2026-10-28" -->
```

| Status | On a screen it means |
| --- | --- |
| `decided` | Approved for build. The implementation must match it, or say why at the site. |
| `proposed` | A design under discussion. Build nothing from it yet. |
| `superseded` | Kept for history; the folder README names what replaced it. |

### Static by rule

Screens follow the design system's rule: **HTML, CSS and images only – no JavaScript.** No `<script>`, no
`on*` attribute, no `javascript:` URL and no `.js` file; every page starts its `<head>` with the
`Content-Security-Policy` meta, and `npm run design -- --check` fails otherwise. Interaction is CSS (`:hover`,
`:focus-visible`, `:checked` with a label, `<details>`, `popover`) or a gallery of static frames, one per
state. Numbers a screen quotes from the code are bake targets (`data-claim`, `data-contrast`), filled by
`npm run design` – see `docs/design-system/README.md`. A drawing coordinate in a mock-up (where a pin sits on
a fake page) is written as a custom property, `style="--ds-left: 82px; left: var(--ds-left)"`, so the
lint rule against literal spacing still holds everywhere else. Only positions go that way (`--ds-left`,
`--ds-top`, `--ds-right`, `--ds-bottom`, `--ds-inset-*`): a margin, padding or gap is spacing and uses a
`--space-*` token, or – inside a fake third-party page – a named class in the page's exempt stylesheet block.
`npm run design -- --check` refuses a `--ds-margin*`, `--ds-padding*` or `--ds-gap*` declaration.

A screen is a set of pictures, so its fake controls are not tab stops (`tabindex="-1"`) and its fake live
regions carry no `aria-live`; the guard refuses a focusable element inside `aria-hidden="true"` that is not
also `inert`.
