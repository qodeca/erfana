Comments v2 – marks, icons and the chip

What a comment looks like on the content, in the HTML Preview and the Markdown Preview: the comment mark under commented words, the icon at a commented part's top-right corner, the dashed ghost where a comment lost its target, the Comment chip after a selection, and the HTML label. One look in both previews.

Static, proposed. No script: every state is drawn on its own. Plan: docs/designs/comments/comments-v2.md §3 – C-05, C-06, C-11, C-12, C-16, C-17, C-21. Hover, focus and forced colours cannot be triggered on a static card, so each is drawn with its state class and named in the caption. In this card, white, grey and dark scenes are a third-party HTML page; the near-black panel is the Markdown preview.

The comment mark on every ground

One mark in both previews (C-12): a 35% accent fill plus a continuous 2px accent bar along the bottom of the text box – no break at descenders. The active thread (its window open, its drawer row active, or hovered) keeps the 35% fill and gets a bar twice as thick; in Markdown its words also turn to the emphasis colour. A 55% fill was tried and rejected: drawn over the text it drops contrast to about 3:1 (design doc R-01). On light page grounds only, the HTML overlay reads the container's luminance and adds a 1px ink hairline on top of the bar, between the text and the bar: the accent bar alone is too faint on white and grey, and the ink line is what carries the edge there. The mark never uses --color-bg-selected, so commented never looks selected; and it fills rather than colouring the words, so it never reads as a link.

Changed since the comment

Derived, never written to the file (C-06). When the commented words changed after the comment – usually because the agent did what was asked – the "now" words get a dashed accent underline and no fill (::highlight(erf-comment-changed) in Markdown, dashed boxes in the HTML overlay). The icon gets a filled 4px notch at its top-left: a shape, not a colour, so it survives greyscale and forced colours. The window then shows Was / Now (window card).

Mark and icon act as one

Linked hover (C-17). Hovering or focusing a mark puts its icon in the hover look; hovering an icon raises all its marks to the active fill. In Markdown a plain click inside a mark (no drag, not on a link) opens the window with only that thread expanded; the pointer is a hand and the title reads "Comment by {name} – click to open". In HTML, marks take clicks only in comment mode; outside it the page keeps its clicks. Icon step: 24px hit box plus a 2px gap, so neighbouring hit areas never overlap (v0.23.1 stepped 22px, overlapping by 2px). Beyond the cap, the rest of the row merges into a stack icon.

Not found: the ghost in Markdown

Possible success, not a warning (C-05). When a Markdown comment's target is gone – often because the agent removed or rewrote it as asked – a dashed ghost (1px dashed --color-text-tertiary, no fill) sits in the right margin at the comment's own slot, between the blocks around it. The drawer tags the thread "Not found", and it stays Open with Reply and Resolve. The HTML Preview draws no icon for a not-found comment; the drawer is its route.

The Comment chip

A visible next step after a drag (C-16). About 150ms after a pointer-up that leaves text selected inside a commentable part, a 28px chip appears 8px above the end of the selection's last line (below it near the top edge): the message-square-plus icon plus "Comment", on --color-bg-elevated with a 1px --color-border-subtle edge. It takes no focus, does not change the selection, and hides on Esc, scroll or collapse. Markdown: inside and outside comment mode. HTML: only in comment mode – outside it the page owns its mouse, and the right-click menu offers "Comment on selection" instead (OD-01). In HTML the label is generated content in the overlay's shadow root, so Find never counts it.

HTML label: inside the outline when it would cover text

Labels stop covering text (C-21). The HTML label drops the pixel size unless Alt is held. When the outline's top touches content, the label moves inside the outline's top-left corner, on its solid --color-brand-black ground. The Markdown Preview has no floating label at all: its comment-mode tab names the target instead ("Comment mode · List item, line 14 · Esc to leave", in the chip frames above).

Accessibility of icons

HTML (C-11): a visual cue only. The icon layer in the page's shadow root carries aria-hidden="true"; icons lose role, tabindex and aria-label. Assistive tech gets the same facts from the picker's spoken count (C-10), the drawer – the guaranteed route to every comment – and the stepper (C-13). Marks in the overlay are hidden the same way.

Markdown (C-11): real buttons. Erfana owns this DOM, so each icon is a <button type="button">, outside the Tab order (tabindex="-1") but pressable with Enter and Space, named like "2 comments on list item, line 18. Open." Each commented block carries aria-details pointing at its icon, so NVDA and JAWS say "has details" while reading. Export strips both attributes (E-M10). The marks themselves are CSS highlights and add nothing to the accessibility tree.

Forced colours

Mark, never Highlight (C-12). In forced colours (Windows High Contrast and similar) the mark takes the system Mark fill with MarkText words, plus a 2px CanvasText edge along the bottom; the active mark gets a 4px edge. Highlight / HighlightText stay reserved for the live selection, so commented and selected still differ. Changed words keep their dashed underline, which forced colours draw in CanvasText. Icons follow the overlay card's forced-colours rules unchanged; the changed notch is a shape, so it survives.

A static card cannot switch forced colours on. The strip below is only a simulation: the same system colour keywords as this browser resolves them outside forced colours. The user's theme sets the real values.

Every mark Markdown: CSS highlights (::highlight(erf-comment), erf-comment-active, erf-comment-changed) – no DOM node. HTML mark fill over the text The overlay box lies above the page's words, so its fill tints them. A span paints under the words, so on page scenes the card tints the words by the same 35% with color-mix(). Without it the card would show better contrast than the app.
HTML icons, chip, outline and label In the overlay root, position: fixed, the icon layer aria-hidden. Children of the page element they belong to (the Markdown placement rule from markdown-comments.css), each aria-hidden, so each scene needs no measuring.
HTML live selection The page's own ::selection, or Chromium's default. Erfana does not style it. Drawn with the Highlight / HighlightText system colours. .erf-comment-selection is Erfana's Markdown ::selection and is used only there.
Grey page ground, page link colours No hex colours. Literals for the third-party page, wrapped in the same color-no-hex exemption as demo.css: the page is not Erfana, and tokens there would hide where Erfana stops.
Hover and focus states Live :hover; the native title tooltip. Drawn with .erf-comment-mark--active, .erf-hpc-pin--hover, .mk-chip--hover and a tooltip box, because a static card cannot hover.
