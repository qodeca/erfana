# Design – issue #124, part 3: links can open in the same tab

Parent: [design-issue-124.md](design-issue-124.md). Covers P3-AC1 to P3-AC5, user answer 2 and UX spec §1–§3, §5–§7. Work items WI-7, WI-17a, WI-17b, WI-18 to WI-20 and WI-25. Supersedes sd-074b decision D4 ("every link opens a new tab").

## 3.1 Who decides what

| Layer | Owns |
|---|---|
| main | the link table, the click proof (gesture only), whether the target may run as a preview, every navigation check, the in-place load, each tab's history and page (authoritative) |
| renderer | the tab: its stable id, `params.filePath` (the page it shows), its mode, one file one tab (closing and asking), titles, toolbar, keys while focus is in Erfana's chrome |

A link click inside the page:

1. The preload reports `click` / `auxclick` on `preview-page:linkActivated`, now with `button`. `previewLinkBridge` validates, rate-limits and de-duplicates as today, then `routeLinkActivation` runs `decideLinkIntent` and, for an in-project target, `confinePath` (both unchanged).
2. The new pure `decideLinkDisposition` (§3.2) returns `same-tab`, `new-tab` or `by-mode`. `same-tab` and `by-mode` need a gesture, an `.html`/`.htm` target and a main-side `PreviewEligibilityService.check` saying it runs as a preview. Routing asks `requestedLinkDisposition` (rows 1–5) first, so the check – which may run `git` – is skipped when the answer is already `new-tab` or the target is not `.html`/`.htm`; a check that fails gives `new-tab` and a warning naming the error only (WI-17a). The check reads the target in project space: WI-17b converts the confined real path with `join(projectPath, relative(realRoot, realTarget))` first, or a project reached through a symlink would count every page as outside.
3. Main emits `preview:openFileRequested { sourcePanelId, filePath, anchor, disposition }`, with `filePath` in project space (§3.4). `disposition` is optional in the contract; absent means `new-tab`. The routing hands it to `requestOpenFile` as a fifth argument (WI-17a); `PreviewEmitters.openFileRequested` and `emit.ts` carry it from WI-17b.
4. The renderer router (`PreviewLinkRouter.ts`) turns `by-mode` into the source tab's mode. `new-tab` → today's `resolvePanelKind` + `openFileInPanel`; `same-tab` → the move coordinator (§3.6).
5. The coordinator calls `preview:navigate` twice – `phase: 'check'` before anything happens, `phase: 'commit'` once the other tabs are resolved. The handler (`src/main/ipc/preview/navigation-handlers.ts`, registered in `src/main/ipc/preview-handlers.ts` beside the lifecycle handlers, taking a `Pick<>` slice of the service like `lifecycle-handlers.ts:41-44`): sender gate → strict zod → the panel's view exists in the sender's window → the target (`open`: the given path; `back` / `forward`: main's own history target, only if the request's `generation` matches) → re-confine against the view's real root (no build-folder exception, dot rule kept) → `.html`/`.htm` → eligible → on `commit` only: no navigation pending for the panel (an `open`, `back` or `forward` main started; a watcher or approval reload is not one – the commit supersedes it, RS2-5), then the load.
6. The load goes through `startPageLoad(target, kind, load)` (part 2 §2.3): a pending page scope, then `wc.loadURL(url#anchor)` or a native history step. No new cancel is needed: `will-navigate` is already always cancelled, and S6 showed cancel-then-`loadURL` is clean. The main-frame `did-navigate` for the target's document commits the pending scope (part 2 §2.3), runs the per-page reset (§3.4), updates the history and emits `preview:pageChanged`.

**The contract** (`src/shared/ipc/preview-navigation-schema.ts`, WI-7):

| Part | Shape |
|---|---|
| request | `{ panelId, phase: 'check' \| 'commit', action: 'open', filePath, anchor }` or `{ panelId, phase, action: 'back' \| 'forward', generation }`; strict, bounded (path 1–4096, anchor ≤ 1024) |
| answer | `{ ok: true, target: { filePath, anchor }, generation }` or `{ ok: false, errorCode, history? }` – `history`, optional, is the tab's new `{ canGoBack, canGoForward, backTarget, forwardTarget, generation }` after main dropped a missing entry (§3.5); no raw error crosses IPC |
| codes (`errors.ts`) | `PREVIEW_NAV_TARGET_MISSING`; `PREVIEW_NAV_TARGET_REFUSED` (outside, not HTML, opens as source); `PREVIEW_NAV_UNAVAILABLE` (no view in this window, or suspended); `PREVIEW_NAV_SKIPPED` (stale generation, a navigation already pending, no step in that direction) |
| `preview:pageChanged` | `{ panelId, filePath, anchor, sameDocument, generation, canGoBack, canGoForward, backTarget, forwardTarget, failed }` – `filePath` and `anchor` come from the gated history entry, never from the committed URL, in the project-space spelling the tree uses (the renderer compares it to `params.filePath` by exact string); `failed` = `httpResponseCode >= 400` on the committing `did-navigate` (S15: a refused page commits with its 404) |

Why the round trip through the renderer: an unsaved editor tab for the target must be resolved first (Cancel aborts the move), and a three-way answer needs `useDialog()` (`DialogContext.tsx:27`). The imperative `showGlobalDialog` (`dialogService.ts:33`) is fire-and-forget and knows four dialog types only. The renderer is a trusted sender; main re-validates every path it receives.

## 3.2 The link table – `previewLinkDisposition.ts` (pure)

Evaluated in order, after `decideLinkIntent` has handled external links, refusals and same-page `#section` (all unchanged):

| # | Condition | Disposition |
|---|---|---|
| 1 | provenance other than `gesture` – in practice `navigation`, the `will-navigate` fallback: no preload, no click proof, no target | `new-tab` in both modes, never in place – a security invariant, labelled as such in its test (RX11); written as "not a gesture", so any other provenance fails closed |
| 2 | any button but the primary (`button !== 0`: the preload reports 0 and 1 only, so anything else is suspect), or the platform accelerator (Cmd on macOS, Ctrl elsewhere, from `deps.platform`) | `new-tab` |
| 3 | `target` is `_blank` or a named target | `new-tab`; a new tab inherits the source tab's mode |
| 4 | `target` is `_self`, `_top` or `_parent` (the preload already folds in `<base target>`; it runs in the top frame only, so these are top-level) | `same-tab` |
| 5 | no `target` | `by-mode` – the renderer applies the tab's mode |
| 6 | `same-tab` or `by-mode`, but the target does not run as a preview (non-HTML, or HTML that opens as source: gitignored, excluded folder, HTML execution off) | `new-tab` – its usual panel, unchanged |

Shift and Alt have no meaning of their own. `new-tab` means "the tab that already shows that page, or a new tab" (§3.4). External routing stays gated on provenance `gesture` (RX11, pinned in `previewLinkNavigation.test`). The table test covers every row on each platform; `PreviewNavigationPolicy.test.ts:175-184` (new tab for `_self`/`_top`/`_parent`) changes on purpose.

**Two entry points (WI-17a).** `requestedLinkDisposition(link, deps)` answers rows 1–5 from the link alone; `decideLinkDisposition(link, target, deps)` adds row 6 from the confined target's extension and eligibility. A caller that gets `new-tab` from the first stops there.

**Payload.** `LinkActivationPayloadSchema` (`previewLinkBridge.ts`) gained `button: z.number().int().min(0).max(4).default(0)`; the preload sends `event.button` (still inlined, still no `contextBridge`). `previewPage.contract.test.ts` and `previewLinkBridge.test.ts:67` changed with it.

**Staging.** WI-17a landed the table with its eligibility input injected and defaulting to `new-tab`, so nothing changes until WI-17b wires `runsAsPreview(realTarget)` and the platform into the link bridge.

## 3.3 The mode (RA7)

- Only the renderer knows it: `linkMode: 'new-tab' | 'same-tab'` in the tab store, default `new-tab`, memory only. The toggle writes the store; nothing is sent to main. Main never needs the mode: row 5 returns `by-mode`, and `commit` re-checks eligibility whatever the mode. There is no `preview:setLinkMode` channel and no `linkMode` on `preview:open`.
- A tab opened by a link: the router passes `params.linkMode` to `openFileInPanel` for a **new** panel only, and the panel seeds its tab-store entry from it; a reused tab keeps its own. WI-18 wired it; `PreviewLinkRouter.test`'s first test changed on purpose for it.
- Nothing persists: after a restart every tab is in new-tab mode.

## 3.4 The tab and its page

**Stable identity.** A panel's id never changes. The page inside the same `WebContentsView` changes, so there is no remount: no view teardown, no lost history, zoom kept.

**`params.filePath` is the page (RS3, RA6).** On every `pageChanged` the panel calls `props.api.updateParameters({ filePath })` (dockview, `panelApi.d.ts:25`). Title, tooltip, close label, the "(deleted)" marker, the lookup and crash recovery all read that one value: `HtmlPreviewTab` already reads `params.filePath` (`HtmlPreviewTab.tsx:65`) and `getFilenameFromPanelId` reads params first (`tabOperations.ts:79-90`). WI-18 pinned that the tab re-renders after `updateParameters`: dockview re-renders tab components, so `HtmlPreviewTab.tsx` is unchanged and its conditional subscription to `api.onDidParametersChange` was not needed.

**`usePreviewTabStore`** (new) holds UI state only, per panel: `{ linkMode, canGoBack, canGoForward, backTarget, forwardTarget, generation }` from WI-18, plus `announcement` (`{ origin, closedCount, target, focusMoved }`) and `lastMove` (`{ action, from, to }`) from WI-19. Seeded on mount from `params.linkMode`, updated by `pageChanged` and by a refusal's `history` field (`setHistory`), and removed on dockview `onDidRemovePanel` (wired in `EditorAreaSplitPanel`) – never on unmount, so an error-boundary remount keeps the mode. `generation` is 0 until main's first report, and `setHistory` accepts a lower one on purpose: a view reopened after a crash or a close starts a fresh history in main. Selectors return stored references, with `NO_*` constants outside the selector (`NO_PREVIEW_TAB`).

**Paths in one space.** Main reports every page as `join(projectPath, relative(realRoot, realTarget))`, so a tree path and a reported page compare equal even when the project folder is reached through a symlink (`/tmp` → `/private/tmp`). This also fixes a latent mismatch: link opens used to send the real path, the tree the project path, which minted two ids for one file. Comparison uses a new `pathsEqual(a, b)` in `fileUtils.ts`: separators normalised, case-folded when `isWindows()`, case-sensitive everywhere else, macOS included.

**The first load too (fixed after G7).** The first open and a failed resume's fallback used to load the renderer's path unchecked and build its URL against the real root, so a project opened through a symlinked folder got `erfana-preview://<t>/../../../tmp/proj/a.html` – a 404 – and a first page that no later comparison matched. They now run the move check's first step (`locate`, through `locateRendererPage` in `previewViewNavigation.ts`): the page is re-confined on the real root, loaded at its real path and named in project space, so "paths in one space" holds from the first load. The first open adds no page-type or eligibility check (still technical debt: the renderer checked eligibility before it made the tab); a page that step refuses, or a lookup that throws (a warning naming the digested panel id and the error name only), loads as sent, as before. The failed resume's fallback is stricter since QG-7 item 11 (below). If the renderer ever sends a real-folder path, the tab takes the tree's project-space name, as a move does. Pinned by `previewViewNavigation.test` and `previewNavigation.integration.test` (the user chose to fix this pre-existing bug in #124).

**The lookup** (`findPreviewTabShowing(path)`) scans this window's dockview panels whose component is the preview and whose `params.filePath` equals the path (`pathsEqual`). It returns the first match and takes no exclude; the move coordinator filters T out itself (§3.6).

- `openFileInPanel` with `kind: 'preview'`: a tab showing the file → focus it. Otherwise mint the id through `buildPanelId('preview', path, variant)` with the smallest variant not taken locally – variant 0 is today's id; `n > 0` appends `-v<n>` inside the length budget. No path is ever read out of an id.
- The project-tree click and the "already open" check go through that same call. `DocumentImportDialog` and `TranscriptionDialog` also call `getFilePanelId`; they open Markdown output (`.md`), so they stay unchanged – WI-18 confirmed.
- **Other windows (RA11).** Today's cross-window refusal (`PREVIEW_VIEW_LIMIT_REACHED`, `PreviewViewService.ts:132`) and its banner stay as they are, with the sender-window check; no variant retry and no `holderShowsFile`. The app ships one window (`src/main/index.ts:172`); keys that span windows (`windowId`, `panelId`) are recorded as technical debt.

**Error containment.** `EditorAreaSplitPanel` keys `HtmlPreviewPanelWithBoundary` by `panelId`, not `filePath`, and passes `resetKey={params.filePath}`. `PanelErrorBoundary` gains an optional `resetKey`: when it changes while the fallback shows, the error clears with no focus move and no retry counted. A Reload moves focus only when it raised the attempt count, so a `resetKey` clear, which raises none, moves no focus (WI-18). **After a crash**, the boundary's unmount closes the view (`usePreviewLifecycle.ts:212-220`) and main drops its history; Retry (counted once) reopens `params.filePath` – page B after a move – with a one-entry history. `EditorAreaSplitPanel.previewBoundary.test` pins key, `resetKey`, "a crash after a move keeps B and counts exactly one retry", that the store entry survives the remount, and the `pageChanged` wiring. The image-viewer wrapper is unchanged.

**Lifecycle.** `usePreviewLifecycle`'s open/close effect keys on `panelId` only (today it also keys on the file, which would remove the panel on every move).

**Main is authoritative on resume (RS6, RX2-6, RX3-1).** `preview:open` for a panel whose state survived a suspend runs the navigate gate on `history[index]` – re-confined on the real root, `.html`/`.htm`, eligible – then loads it and emits `pageChanged`; the renderer's `filePath` is only compared, and a mismatch is logged. When the gate refuses (the page was gitignored, or HTML execution turned off, while the view slept), main logs it and falls back to the tab's own page – the renderer's `filePath`, with a one-entry history one generation on (the previous + 1). **The fallback is gated and fails closed (QG-7 item 11, as built):** the page is located as above; a page that is `.html`/`.htm` and eligible opens; one that is not, or one whose lookup throws, opens nothing – `startingPage` answers a `PreviewStartingPageResult` with `PREVIEW_NAV_TARGET_REFUSED` or `PREVIEW_NAV_UNAVAILABLE`, and the tab shows its failed state (`previewViewNavigation.ts:376-404`). Only a page the lookup cannot locate (gone, or outside the root) loads at the path the renderer sent, and fails at the protocol handler, which re-confines every request. The gate checks `.html` and eligibility, not a second full confinement, because the handler already confines (decision). So RX2-6's resume half is closed; the first open (`preview:open`, `lifecycle-handlers.ts:129-158`) still checks no eligibility – the remaining technical debt. A first open, or an open after close, starts a one-entry history from the renderer's `filePath`, at generation 0 when main keeps no history for the panel; its `pageChanged` resets the tab's Back (WI-17b). `PreviewViewService.navigation.test` covers "suspend during a move" and "resume onto a page that is no longer eligible".

**Per-page reset**, when a load main started commits (part 2 §2.3):

- main: the pending scope becomes the committed one (failure log, CSP bridge, blocked hosts, frame refusals, frame counters and timers) and its snapshot is emitted; `stillFrameCache.invalidate`, so the next hide publishes B's picture, never A's (RS2-8) – it also cancels a capture of A still in flight, whose late picture is dropped, and B's first post-load step runs at once instead of waiting out A's 750 ms reload throttle (later reloads stay throttled), so a tab hidden right after the move still gets B's picture (both fixed after G7); the watch set recomputed for the new page (its links and frames); the entry watcher moved to the new file (extracted from `wirePreviewLifecycle` into `previewEntryWatch.ts` with `retarget(path)`); the link context's `currentUrl` a getter over `currentPage()`, which is always the committed page. While a navigation is pending the pipeline is paused and starts no reload; at the commit the paused work, which was about A, is dropped; when the pending load is dropped instead, the pipeline resumes on A. A same-file anchor step changes none of this.
- renderer, on a `pageChanged` with `sameDocument: false` (the branch lives in `usePreviewEvents`): `usePreviewStore.resetPage(panelId)` (blocked hosts, still frame, dropped; keeps load state, backdrop and allowed hosts). Failures and truncation are **not** reset there: the badge mirrors main's snapshot, which main sends for the new scope at the commit, so a snapshot that arrives before `pageChanged` survives (RS2-3). The find bar closes (focus to Back if it held focus, §3.6), the host list collapses (focus to the chip if it was in the list) – WI-20 added both, through `onLeavePage`, which `usePreviewEvents` calls only when `sameDocument` is false, so a `#section` step keeps both.

**Zoom** is re-applied from `previewPanelState` after each main-frame `did-navigate`; the e2e pins the level. **A new page opens at the top**; `page.html#section` is loaded with its fragment and Chromium scrolls to it.

## 3.5 History – Back and Forward

Chromium's joint session history records frame navigations too (a link inside a frame would enable Back) and is lost when a view sleeps (S6: restored entries point at a dead token). So Erfana keeps its own list per panel, main-side, in `previewPanelState`, which survives suspend.

- `previewTabHistory.ts` (pure, immutable): entries `{ filePath, anchor | null }`, an index, at most `MAX_HISTORY_ENTRIES` (50, oldest dropped), and a `generation` that increases on every change. Functions (WI-17a): `createTabHistory(first, generation = 0)` – a rebuild for the same panel passes the old generation + 1 –, `currentEntry`, `canStep`, `neighbourEntry`, `pushEntry`, `replaceCurrent`, `stepHistory`, `dropNeighbour` and `historyState` (Back and Forward state with their targets). The entry on screen is never pushed twice in a row, and a call that changes nothing returns its input, so `next === previous` means nothing happened.
- `previewPageNavigator.ts` (per panel): fed by main-frame `did-navigate` and `did-navigate-in-page` (`isMainFrame` only – S4: the in-page event also fires for frames). With a pending intent (initial, open, back, forward) whose target is the same document as the URL (`samePreviewDocument`, part 2 §2.3), set the index. With none: a fragment change records `{ same file, anchor }` – **pushed only after a real gesture, else it replaces the current entry** (QG-7 S1, QG-8 T1, as built): `previewStillFrameFreshness.ts` notes the time of the last `mouseDown`, `rawKeyDown`, `keyDown` or `touchEnd`, and its `takeRecentGesture()` is true when that came within `PREVIEW_LIMITS.HISTORY_GESTURE_WINDOW_MS` (1 s) and the clock did not run backwards; every read spends the gesture. The navigator reads it once per recorded in-page step (`previewPageNavigator.ts:357-359`), and a landed same-tab move or Back/Forward step spends it too (`:324-329`) – a refused or superseded move spends nothing – so one input buys at most one entry, and a page that loops `location.hash` after one click replaces the entry it is on instead of evicting the pages before it. An in-page step to another document is not recorded (logged with the digested panel id only). A cross-document commit of the committed document is a reload and changes nothing; any other cross-document commit is logged and pushes nothing, because `pageChanged` only ever names a gated history entry (top navigations are cancelled, so it should not happen). **A pending intent ends with its pending load** (part 2 §2.3: a commit, a replacement by another `startPageLoad`, or a `did-stop-loading` with no commit) – never on a fail event or on `did-start-navigation` (S15) – so a later commit is not refused as pending forever. `previewPageNavigator.test` pins it, with S15's re-encoded fragments. WI-17b starts moves with `startPageLoad(filePath, 'open' | 'back' | 'forward', load)`, the anchor inside `load`; an outcome callback it adds to `previewLivePage` ends the intent with the pending load, and `pendingLoad()` is the "navigation pending" check.
- **Executing a step.** If the live view's neighbouring Chromium entry (`getActiveIndex() ± 1`) has exactly the target's URL, step onto it with `navigationHistory.goToIndex(neighbour)` – native scroll restore, including after a `#section` jump; S6: no `will-navigate` fires. Never `goBack()` / `goForward()`: Chromium marks an entry a page pushed without a user gesture as skippable and they skip it, so Back after a `pushState` did nothing (fixed after G7). Otherwise `loadURL(target)`: after a sleep, or when frame entries sit in between; the page then starts at the top or at its anchor.
- **History targets pass the same gate as a link (RX8).** A `back` / `forward` target is re-confined on the real root and re-checked for `.html`/`.htm` and eligibility before either path runs – the native fast path only runs when the neighbour URL is exactly the checked target. A `pushState` entry is therefore confined like any link (test in `navigation-handlers.test`).
- **A history step onto a missing page drops that entry (RU2-3).** At `check` main refuses with `PREVIEW_NAV_TARGET_MISSING`, removes the entry (`dropNeighbour`; the generation increases) and returns the tab's new Back and Forward state in the answer's `history` field, which the renderer writes to the tab store; the toast says the entry was removed (§3.6). The next Back therefore goes one entry further: in `[X, B-missing, A]`, Back from A gives the toast and the next Back reaches X (`navigation-handlers.test`). Only a page that disappears between `commit` and the load ends in the main-frame 404, the "Missing local file" badge (fixed in part 2) and the failed banner with its return button (§3.8). S15: that page commits, with 404, and no fail event fires. So a navigation commit (open, back, forward) with `failed` set also sets the load state to `failed`: it reuses the load-state step of the entry-unlink path (`recordFailureAndFail`, which `onEntryDeleted` uses in `PreviewLiveView.ts`) without writing a second record, and the pipeline emits no `ready` for that load. `previewLivePage` already computes `failed` and only logs it (WI-29). A view's first load keeps today's screen, plus the badge.
- Script `history.back()` stays cancelled by `will-navigate` (out of scope). A script `pushState` or hash change within the document follows the gesture rule above: an entry after a real input, otherwise it replaces the current one. A fragment over `PREVIEW_LIMITS.NAV_MAX_ANCHOR_CHARS` (1024, read by the schema and the navigator alike) is cut before it is recorded, or `pageChanged` would fail its schema. A `pushState` to another path is refused by Chromium itself (`SecurityError`, pinned by an e2e tripwire), so the old `pushedFile` branch and its 4096-character cut were deleted (QG-7 S2).
- Back or Forward to a page open in another tab follows the link rule: the coordinator resolves the other tabs first (§3.6). `pageChanged` carries `backTarget` / `forwardTarget`, which the Back tooltip names.

## 3.6 One file, one tab (answer 2, UX §5)

**The coordinator** – `createPreviewTabMove(deps)` in `src/renderer/src/services/preview/previewTabMove.ts` (RA14). Deps: `closePanel`, `isDirty` (`useProjectStore.dirtyPanelIds`), `hasConflict` and `save` (the save registry), `prompt` (the dialog), `navigate` (the bridge), `focusBack(panelId)`, `showToast`, `logger`. A coordinator built without a prompt refuses any move that needs one (RX11). `setPreviewMovePrompt` is dropped. As built (WI-19): the deps also take `getDockviewApi` and an optional tab-store slice; `move(request)` never rejects and resolves with how the move ended (`moved`, `refused`, `cancelled`, `save-failed`, `ignored`, `failed`), and `isMoving(panelId)` reads the lock. `createPreviewBackFocuser(getDockviewApi)` builds `focusBack`: one frame later it focuses `PREVIEW_BACK_BUTTON_SELECTOR` (`[data-preview-nav="back"]`) inside T's panel element – the attribute WI-20's Back button carries. After QG-6 A7 the editor lookup is `findEditorTabsShowing` in `openFileInPanel.ts` beside `findPreviewTabShowing` (the coordinator's `EDITOR_COMPONENT` is gone), and its log lines carry `stablePathDigest(panelId)`, pinned in a split `previewTabMove.logging.test.ts`; the file is 491 lines and its test 499 – near the cap, so a later edit splits first.

**One creator (RA2-5).** `EditorAreaSplitPanel` is the only place that creates the link router and its coordinator. On mount it calls `useOptionalDialog()` – outside a `DialogProvider` it gets no prompt, so the router still routes and refuses any move that needs one (WI-19) – and passes `prompt` (the memoised `showUnsavedChanges`) and `closePanel` (from `tabOperations.ts:49`, so no service module imports a component module) to `mountPreviewLinkRouter(deps)`; on unmount it disposes both, so a remounted `DialogProvider` binds its own prompt on the next mount. `getPreviewLinkRouter()` (`PreviewLinkRouter.ts:99`, today a first-call-wins singleton called at `EditorAreaSplitPanel.tsx:85`) becomes a reader that returns `null` until then, so no early caller can create a router without a prompt. The panel's Back and Forward use the same instance, and Back stays `aria-disabled` while there is none. `PreviewLinkRouter.test` pins: the reader returns `null` before mount and creates nothing; a remount re-binds the prompt; unmount disposes. WI-19 built `same-tab`, `by-mode` and `mountPreviewLinkRouter`; with no preview bridge the router logs a warning and routes nothing.

**One move at a time per panel (RS5).** While a move runs – from the check to the commit's answer, prompt included – further Back, Forward and same-tab clicks for that panel are ignored and logged; so are the repeats of a held Back key. Main also answers `SKIPPED` to a commit while a navigation it started is pending – a watcher or approval reload is not one: the commit supersedes it (RS2-5) – and to a `back` / `forward` whose `generation` no longer matches.

**A prompt that fails is a Cancel (RX2-5).** A prompt that rejects, is dismissed without an answer, or whose provider unmounts while it is open counts as Cancel: `showUnsavedChanges` resolves `cancel` when the provider unmounts. The per-panel move lock is released in a `finally`, whatever happens. Tests: `previewTabMove.test` (unmount mid-prompt → Cancel, lock released), `DialogContext.unsavedChanges.test` (unmount resolves as cancel – split off so `DialogContext.test`, 594 lines before this change, is not grown).

**Steps** (RS4 – nothing irreversible happens until main accepts the move):

1. **Check.** `navigate({ phase: 'check', … })`. A refusal ends the move (refusal UX below).
2. **Find the other tabs** in this window showing the target: previews through the lookup (excluding T – the lookup takes no exclude, so the coordinator filters it out), editors through `findEditorTabsShowing` – panels whose component is `editor` and whose `params.filePath` equals the target (`pathsEqual`, project space). There is one dockview api per window, so other windows are left alone.
3. **Ask** if one of those editors is dirty (`UnsavedChangesDialog`, below). Cancel or Escape → the move ends, history position unchanged. Save → `editorSaveRegistry.save(panelId)`; `false` → the UX §7 toast, the move ends, T stays on A. Don't save → remembered; nothing is discarded yet.
4. **Commit.** `navigate({ phase: 'commit', … })` with the checked target, or the history `generation`. A refusal ends the move: nothing closed, nothing discarded, T stays on A, and the announcement is cleared. A refusal's `history` goes to the tab store through `usePreviewTabStore.getState().setHistory(panelId, history)`.
5. **Close** the other tabs (`closePanel` clears the dirty flag, so a "Don't save" editor's edits are dropped here – after main accepted the move).
6. **Announce** on the `pageChanged` for T that names the checked target (§3.8).

Rare edges: a suspend between the commit and `did-navigate` leaves T on A after resume (main is authoritative), and so does an approval reload, from any tab of the project, landing in that window – it replaces the pending load (part 2 §2.3; technical debt) – each while the other tabs are already closed. No edit is lost that the user did not agree to drop.

**Refusal UX.** T stays on its page in every case. Toasts carry the file name; logs are redacted.

**The prompt (RU1, RU9)** – `UnsavedChangesDialog`, on `BaseDialog`:

- `BaseDialog` focuses `initialFocusRef` about 10 ms after it opens (`FOCUS_DELAY_MS`), otherwise the first focusable control in DOM order (`BaseDialog.tsx:337-384`); `ConfirmDialog` and `ConflictDialog` pass no ref. With the UX order (Don't save, Cancel, Save) the default would land on Don't save and Enter would discard. So: `initialFocusRef` on **Save** (on **Cancel** in the conflict variant), `trapFocus`, `closeOnBackdrop={false}`, and no custom Enter handler – Enter activates the focused button natively; `ConfirmDialog`'s confirm-on-Enter is not copied. Don't save sits in the existing `.dialog-actions-left` group (`Dialog.css`), in danger style.
- Titles: "Save changes to pricing.html?"; the conflict variant has its own, "Discard your changes to pricing.html?", with "Discard my changes" (danger) and "Cancel" (focused). Other copy as UX §5.
- Tests: after `FOCUS_DELAY_MS` focus is on Save (Cancel in the conflict variant); Enter on the focused control runs that control; both titles.
- `showUnsavedChanges` on the dialog context, following `showConflict`. The existing dialog occluder hides T's page meanwhile.
- As built (WI-19): the icon is `alert-triangle` from the icon registry (`iconRegistry.tsx` gained it), so no direct `lucide-react` import raises the icon-registry-bypass claim; the dialog has no test ids – e2e finds it by role and name.

**Focus afterwards (RU6).** When the prompt closes – whatever the answer – and when a move closes a find bar that held focus, focus goes to T's Back button, which stays focusable when `aria-disabled`. `focusBack` looks the button up inside T's own panel element and runs one animation frame after `BaseDialog` restores focus on close (`BaseDialog.tsx:580-585`), so it wins. A link click in the page with no prompt leaves focus in the page. A move adds no IPC and never moves focus into the page; the only route in is the keyboard entry added after approval (§3.7). `HtmlPreviewPanel.test` (WI-20) pins the find-bar case.

**Saving an editor tab by its id.** No such path exists: save lives in `MarkdownEditorPanel.handleSave` (`:213`). New `editorSaveRegistry.ts` – panel id → `{ save(): Promise<boolean>, hasConflict(): boolean }` – filled by a `useEditorSaveRegistration` hook that `MarkdownEditorPanel` calls once. `handleSave` returns `true` / `false` instead of swallowing the outcome. The panel was 615 lines, over the cap before this change, and is 620 after WI-19 (+5, recorded). As built: `register(panelId, entry)` returns its unregister; the autosave callback wraps `handleSave(true)`; `MarkdownEditorPanel.integration.test` pins the registration by reading the panel's source, because Monaco does not load under the test runner.

## 3.7 Keys (UX §3, RA12)

- **One table, two users.** `src/shared/previewNavKeys.ts`: rows per platform (macOS Cmd + `BracketLeft` / `BracketRight`; Windows and Linux Alt + `ArrowLeft` / `ArrowRight`; no other modifier; key down only), a matcher over a normalised key (`code`, modifiers, type), and the tooltip and `aria-keyshortcuts` strings. `previewInputForward` (focus in the page) and the panel root's `onKeyDown` (focus in the toolbar, find bar or banner) both call it; one table test.
- **Physical key only (RU8, decision).** Matching is on `code` (S8): the key to the right of P, whatever it types. A layout where `[` sits on another key gets no second match on the typed character – one rule, and no extra key is taken from the page's text fields. `docs/keyboard-shortcuts.md` explains it; one non-US layout joins the manual list.
- **Focus in the page.** Forwarded as `back` / `forward`, with `preventDefault` (S8: that hides both keydown and keyup from the page). `PREVIEW_FORWARDED_SHORTCUTS` and `PreviewForwardedShortcutSchema` changed together in WI-17a (moved from WI-7), with the equality test. Their Back and Forward rows are `accel: false, nav: true`: they match through the shared table, whose modifier is Alt on Windows and Linux, so `emit.ts`'s Cmd/Ctrl key table is unchanged. WI-20 routes them (G4).
- **Focus in Erfana's chrome.** A React `onKeyDown` on the panel root only fires for focus inside that panel – no `window` listener, so the active-panel gate is met by construction, and neither Monaco's Cmd+[ nor the terminal's Alt+arrows can reach it. `HtmlPreviewPanel.test` pins that a key from outside the panel does nothing; an e2e pins that, with two previews open and focus in Monaco, Cmd+[ outdents and neither history moves (RS11).
- `usePreviewFindShortcuts` routes `back` / `forward` to the panel's actions, which go through the coordinator – on `payload.key` alone, since `accel` is false on every platform. Panel-root keys go through `navKeyFromDomEvent` and `matchPreviewNavKey`.
- **Keyboard entry into the page – a deviation added after design approval (QG-8 U1, WCAG 2.1.1).** The approved design gave a keyboard no way into the native page, so its links and every forwarded key above were pointer-only. As built: the placeholder is the target, with no new visible control. `usePreviewPageEntry` makes it focusable (`tabIndex` 0, role `button`) only while the tab is active (`api.isActive` through `onDidActiveChange`) and a page is live and drawn; Enter or Space calls the new sender-gated `preview:focusPage` (`focus-handlers.ts`: gate before the parse, `PreviewPanelRequestSchema`, the view in the sender's window; `{ ok }`, never a throw), which `previewViewFocus.ts` and `PreviewLiveView.focusPage()` turn into `webContents.focus()` for a live, drawn view only. Escape comes back to the permission chip, as it already did. Nothing else moves focus. Name: "HTML preview of page.html – press Enter to enter the page, Escape to come back" (`previewPlaceholderLabel`). Its focus ring shows on the top edge only – the panel clips the other three (accepted, WCAG 2.4.7). Detail in the [impl doc](design-issue-124-impl.md), QG-8 – U1; UAT P3-10 accepts or rejects it.
- Windows: `preventDefault` on the keydown should keep Alt+arrow from showing the auto-hidden menu bar – manual QA (P3-AC4). No application menu accelerator uses these keys (none found under `src/main`).

## 3.8 Toolbar, banners and announcements

- `PreviewNavControls.tsx` (new) renders Back (`aria-disabled`, two-line tooltip, `aria-keyshortcuts`) and the link-mode toggle (`aria-pressed`, fixed name) into the band's leading slot, before Find. Styles in `PreviewNavControls.css`: `erf-band__` classes, tokens only, `border-radius: 0`, a `forced-colors` rule, and the UX §1.5 container-query widths. **Pressed state (RU10):** both states carry a 2px bottom border – transparent when off, `--color-brand-lime` when on – so the icon never shifts; pressed+hover keeps `--color-bg-selected`; pressed+focus draws the band's focus ring over the fill.
- **The card ships with the code (RU2, WI-20).** `scripts/design-sync.mjs` gains a `COMPONENT_CSS` entry that copies `PreviewNavControls.css` to `design/system/components/permission-band/nav.css` (the pattern already used for `band.css`, `:45-54`), and the card links it. The card renders Back enabled and disabled, the toggle off, on, pressed+hover and pressed+focus, Open in browser busy, and the band at 640, 400 and 300 px with a measured readout. The container-query thresholds are measured there first (with a two-digit chip) and only then written into the CSS. `design/claims.json` gains the contrast pairs (icon on `--color-bg-primary` and on `--color-bg-selected`, the lime edge on the band, the focus ring on the pressed fill). The Exceptions section gains "`aria-disabled` on Back and Open in browser, `disabled` on Export to PDF", plus the outward-ring row only if the inset ring measures under 3:1. The spacer comment in `PreviewChromeBand.css:61-64` and the card say "Back leads, chip trails". Done when `npm run design -- --check` is green; a person tabs through the card and sets its reviewed date before the card change is committed.
- **Failed-banner return button (RU5, RU2-2).** `PreviewBanner` gains an optional second action. The tab store's `lastMove` – `{ action, from, to }`, set on commit and never cleared by the coordinator; WI-20 decides when, through `setLastMove(panelId, null)` – names the move. When a move caused the failed banner, the banner says "pricing.html could not be shown – it may have been moved or deleted." instead of "The preview stopped running." (`HtmlPreviewPanel.tsx:66`), and shows "Back to overview.html" (runs Back; after an open or a Forward) or "Return to pricing.html" (runs Forward; after a Back) **first**, and it takes focus. When no move caused it but the tab has an earlier page, "Back to overview.html" comes after the banner's own action, unfocused. The limit-reached banner gets no return button: without a view no page can load (correction to UX §1.2, §3.9).
- **After the return button (RU2-2).** Its move unmounts the banner, with focus on the pressed button, and mounts the band in the same render. The panel calls `focusBack` (§3.6) once the band has mounted, so focus lands on Back instead of falling to the page body. While an action runs, the banner's button is `aria-disabled` with the busy style, not `disabled` (`PreviewBanner.tsx:79` today), so Chromium keeps focus on it. Tests: `HtmlPreviewPanel.test` (focus on Back after a banner-started move; the move-caused text), `PreviewBanner.test` (busy keeps focus, `aria-disabled`).
- **Announcements (RU7, RU2-1, RU3-1).** The coordinator writes `{ origin: 'chrome' | 'page', closedCount, target, focusMoved }` to the tab's store entry before the commit, `target` being the checked `{ filePath, anchor }` and `focusMoved` true when an answered prompt moved focus to Back (WI-19). The text goes into a polite region on the panel root (`HtmlPreviewPanel`, mounted whatever the view), not into the band's region, which mounts only in the normal view. It is written only on a `pageChanged` for that tab whose `filePath` and `anchor` equal `target` and whose `failed` is false, in UX §6 wording ("Showing pricing.html." for a chrome-started move; "Closed the other tab that showed it." / "Closed 2 other tabs that showed it." when tabs closed; nothing for a page-started move that closed nothing), then cleared. It is cleared without a word on a refused or skipped commit, on `failed: true`, and on a `pageChanged` for any other target – so a refused move followed by a `#section` jump says nothing (`HtmlPreviewPanel.test`, `previewTabMove.test`). When the move also moves focus (a banner-started move, an answered prompt), the text is written one animation frame after the later of the `pageChanged` for its target and `focusBack`, so a focus change cannot cut it off. The failed banner itself is `role="alert"`.
- **As built (WI-20).** `PreviewNavControls` is presentational; `usePreviewNavigation` supplies its state and callbacks, the panel root's keys, the banner's return button and focus to Back, and `usePreviewMoveAnnouncer` owns the panel-root region, which reuses the band's `erf-band__announce` class. The panel's cases are in `HtmlPreviewPanel.navigation.test`, the band's in `PreviewChromeBand.nav.test` – `PreviewChromeBand.test` (599 lines before this change) is not edited.
- **Widths, as measured.** The row never wraps: it scrolls sideways at every width, with no visible scrollbar, and degrades in two tiers – compact below 385 px (tighter padding and gaps; the chip drops its "· 34 allowed" tail, keeping the start of its name) and minimal below 293 px (Find and Export to PDF leave the row, matched by accessible name, while their shortcuts keep working; Open in default browser stays). The band stays 41 px high.
- **A move caused the banner** only when the last `pageChanged` reported the page on screen as `failed` **and** `lastMove.to` is that page: `lastMove` alone would blame a move for a crash an hour later, and a failed report alone also comes with a first load. WI-20 clears `lastMove` on every `pageChanged` that did not fail.
- **Test ids:** `preview-band-back` (with `data-preview-nav="back"`), `preview-band-link-mode` (`aria-pressed`) and `preview-move-announcement` (the panel root, `role="status"`); the banner's buttons have none – e2e finds them by role and name.
- **The card, as built.** `design/claims.json` gained two contrast claims; the two pairs on the pressed fill cannot be claimed – the fill is translucent – and were measured by hand: the focus ring about 5.8:1, the icon about 7.9:1. The toggle's glyph (`mouse-pointer-click`) is a placeholder, the final one the ui-designer's call. The card grew from 759 to 1 049 lines (recorded as debt); its `reviewed` date stays 2026-09-01 until the walk-through (parent §5.5).

## 3.11 Risks specific to part 3

| Risk | Likelihood | Impact | Mitigation |

| Code assumes a tab id names its file | medium | high | lookup by `params.filePath` only; every listed consumer changed; `getFilenameFromPanelId` already reads params first |
