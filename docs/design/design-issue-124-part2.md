# Design – issue #124, part 2: frames show pages from the same project

Parent: [design-issue-124.md](design-issue-124.md). Covers P2-AC1 to P2-AC5 and user answers 5 (the request-type bug) and 9 (`srcdoc` frames past the caps). Work items WI-7 (types), WI-12 to WI-16, WI-29 and WI-24. Spike facts are from `temp/124-spikes.md` (S1–S13 and S15–S17, Electron 39.8.10, macOS).

## 2.1 Content-security policy

- **Drop `frame-ancestors` from every response** (S2: an opaque, `sandbox allow-scripts` parent can frame a child only when the child carries no `frame-ancestors`; `'none'`, a scheme source and an own-token source all fail). Who can still frame a preview page: only a document inside a preview partition, because the scheme is handled per partition (`session.protocol.handle`), never globally – and Erfana writes that document's `frame-src`. Recorded as a lasting contract and as a security note.
- **`frame-src erfana-preview://<own-token>`** – S2 and S10: another token is refused in the browser (-30) before any main event. Never scheme-wide, never a remote host (even an approved one), never `data:` or `blob:`. `srcdoc` frames inherit the parent's sandbox and CSP (S3) and need no `frame-src` entry.
- Everything else in the policy is unchanged. Every response keeps `sandbox allow-scripts`, so every framed document has its own opaque origin and parent and frame cannot read each other (S2, S3); the e2e pins it.
- **Builder.** `buildPreviewCsp(hosts, { ownToken }, onReject?)`. A token that is not 32 lowercase hex degrades to `frame-src 'none'` and is reported – the builder still never throws (NEW-4). `onReject` receives a `PreviewCspRejection`: `{ kind: 'host', host }` for a skipped host, `{ kind: 'own-token' }` for an unusable token – never the token's value, which the caller already has and which may carry a line break (WI-13). `PreviewRootRegistry.issue()` mints the token before building the policy; `rebuildCsp(token, hosts)` passes the same token. `buildResponseHeaders` keeps its two tripwires.
- **Tripwires (RX3, WI-13).** `previewCsp.test` pins that `frame-src` is exactly `erfana-preview://<32 lowercase hex>` – never the bare scheme, never a host – and that a malformed token gives `frame-src 'none'` plus a report and never throws. A new `previewSchemeScope.test` scans `src/main` and fails if the preview scheme is handled anywhere but on a preview session object, so dropping `frame-ancestors` stays safe: exactly one `session.protocol.handle` site, on `attach()`'s own `Session` parameter, reached only from `PreviewSessionFactory.ts`, and no `defaultSession` in the handler or the factory. An item that changes that `attach()` shape (WI-12, WI-14) updates the test in the same change.

## 2.2 Request kind ledger – fixes answer 5 and classifies frames

S1: `protocol.handle` sees no request type (`sec-fetch-dest` null, `request.destination` empty, 11 of 11 cases), so `readDestination()` (at `PreviewProtocolHandler.ts:154` before WI-12; the function is gone, and the handler now reads `requestKind(ctx.ledger.take(request.url))` at `:277`) returned `''` in the real app. The "entry page missing" and "unsupported asset type" badges therefore most likely never fire; unit tests pass only because they fake the header. `webRequest` does see `resourceType`.

- `PreviewRequestKindLedger` (new, one per session, built in every `PreviewSessionFactory.create` together with the filter context, §2.4, and handed to both the filter and the handler). The filter's `onBeforeRequest` calls `note(url, resourceType)` for every `erfana-preview:` URL; the handler calls `take(request.url)`. A FIFO queue per URL (the same URL can be both an image and a frame), `REQUEST_KIND_LEDGER_MAX` 256 entries, `REQUEST_KIND_LEDGER_TTL_MS` 10 s. Unknown → `''`: no badge, bytes still served (fail-safe for a diagnostic). As built (WI-12): the filter notes only the `erfana-preview:` requests it lets through, so a refused one leaves no note; the key drops the fragment, and a URL past `REQUEST_KIND_KEY_MAX_CHARS` (2048) keeps its first 2048 characters plus its length – two such URLs with the same head and length share a key, at worst mislabelling one badge – so the ledger's memory is bounded whatever the page requests.
- `readDestination()` is replaced by `requestKind()`: `mainFrame` → `document`, `subFrame` → `iframe`, `script` → `script`, `stylesheet` → `style`. The `sec-fetch-dest` read is removed – one source of truth – and the handler tests that fake it change on purpose. `requestKind()` is exported from `PreviewRequestKindLedger.ts`, for WI-14.
- Handler outcomes: a refused **main frame** records its reason – through `ctx.pageScopes().forMainDocument()`, so while main loads a page it lands in that page's pending scope (§2.3), which survives the commit because the refused page still commits, with its 404 (S15) – the badge intended since #74, which now also covers a same-tab move onto a page deleted after the check; a refused **subframe** records `frame-escape` (from `path-escape`), `frame-excluded` (from `excluded-path`), `missing-local-file` or `asset-too-large`; an unknown MIME for `script` or `style` records `unsupported-asset-type`. As built (WI-12), all three handler failures about a main-frame document – the refusal, the 503 of a shed read and the 500 of a missing CSP – go through `forMainDocument()` (`recordDocumentFailure` in the handler's context), and a refused subframe document is listed by its `url.pathname`, never with the token. Everything else goes to the committed scope.
- **Test first (red).** `PreviewProtocolHandler.test.ts`: a request with no `sec-fetch-dest` and no `destination` (what Electron really sends) plus a ledger note must badge – today it records nothing. WI-12 also runs the `error/` corpus e2e: if its `unsupported-asset-type` assertion already passes on current code, WI-12 reports that S1 does not hold in the real app, and the ledger is still used, because frames need it. With the fix in, that e2e's comment (`e2e/html-preview-corpus.e2e.ts:150-156`, "does NOT fire here") is wrong; WI-24 tightens the test.

## 2.3 The page scope – one owner for per-page state (RA2, RA2-1, WI-29)

Before WI-29 per-page state was spread out: the service held the blocked-host ledger, the live view held the failure log and the CSP bridge, and `applyApprovedHosts` reset part of it by hand. Two past bugs came from that (#74): a log cleared without its dedupe bridge, and a ledger that survived a reload.

- `previewPageScope.ts`: `createPreviewPageScope(deps)` builds one object per page holding the failure log, the blocked-host ledger and its sink (`reportBlocked`), the CSP-violation bridge (`handleCspViolation`, spending this page's dedupe and budgets) and the frame refusal set (`frameRefusals`, below), and – from WI-14 – the frame counters, the committed-frame set and the over-limit timer. A scope is silent until its holder makes it live, so a pending scope emits nothing before its commit. `dispose()` clears its timers; a disposed scope ignores late writes and emits nothing.
- **One holder per view, two slots (RA2-4, RA3-1, RA3-3).** `PreviewViewService.open()` creates the holder before the session – `createPageScopeHolder(() => createPreviewPageScope(…))` – on its existing `createFailureLog` dep, no new dep. It holds the **committed** scope – the page on screen – and at most one **pending** scope – a page main has started loading. The session factory gets a getter, `ctx.pageScopes()` (`PreviewSessionPageScopes`: `committed()`, `forMainDocument()`), which replaced `recordFailure`; the service's `onBlocked` writes `committed().reportBlocked`. The live view gets the holder itself: `PreviewLiveViewParams.pageScopes` (in `previewLiveTypes.ts`) replaced `failureLog`, and `onBlockedHost` is gone, because the CSP bridge now lives in each scope. `previewLivePage.ts` only fills and empties the pending slot (`beginPending()`, `commit()`, `dropPending()`); it never creates the holder. `dispose()` ends the view: both scopes and their timers go, and nothing is emitted. The live view's teardown runs it as a step (`pageScopes.dispose`), and `open()` calls it on its three early exits. No writer keeps a scope: `onBlocked`, `recordFailure`, the preload's CSP reports and every frame writer look up `committed()` or `forMainDocument()` each time they write.
- **Who writes where (RX2-1).** Only the handler's refusal of a **main-frame document** writes into the pending scope (`forMainDocument()`: the pending scope, or the committed one when nothing is pending). Every other writer – the frame guard, the request filter, the failed-load writer, the console bridge, subresource refusals – writes into the committed scope. An event from page A while B loads therefore stays in A's scope and goes away with it: A cannot put text in B's badge.
- **Start.** `previewLivePage.startPageLoad(target, kind, load)`, with `kind` one of `initial`, `reload`, `open`, `back` and `forward`, puts a fresh pending scope in place, then runs the load (`loadURL`, `reload`, or a native history step). Every main-frame, cross-document load main starts goes through it, the pipeline's reload and the approval reload included; a page cannot start one, because `will-navigate` cancels every page-started top navigation (`previewViewLifecycle.test.ts:240-258` pins that). The approval path therefore resets nothing by hand. A view's first load (`initial`: open, resume) creates no pending scope: its committed scope is new and empty, and nothing is on screen, so the refusal lands there through `forMainDocument()` (RA3-3); it still gets the navigator's intent, which ends by the rules below. A `reload` always gets one. An `open`, `back` or `forward` onto the document on screen – a same-file anchor step, Back or Forward between `#section` entries of one document – never creates a pending scope, so the badge, the watchers and the frame state survive it (RS2-1). The returned promise never rejects: a load's outcome arrives through the navigation feed. A `load` that throws synchronously never started, so its pending load ends at once and the error reaches the caller.
- **Same document (RS3-2).** Targets and event URLs are compared with `samePreviewDocument(a, b)` in `previewUrl.ts`: `new URL` on both sides, equal scheme, `host` and `pathname`; the fragment and the query (which the builder never writes) are ignored. S15: encoded paths round-trip unchanged, but a raw fragment comes back re-encoded (`#sec 1` → `#sec%201`, `#zażółć` → `#za%C5%BC%C3%B3%C5%82%C4%87`), so an exact string match would never see such a commit and the tab would stay pending.
- **The pending-load lifecycle (LC).** `previewLivePage` attaches its own `did-navigate`, `did-navigate-in-page` and `did-stop-loading` listeners to the view's contents; `previewViewLifecycle.ts` reports neither navigation event and stays untouched. A pending load – the pending scope and, for open, back and forward, the navigator's intent (part 3 §3.5) – ends at the first of four events:
  1. **A main-frame cross-document `did-navigate`.** Same document as the target → **commit**: the pending scope becomes the committed one, the old one is disposed, and main emits the new scope's failure snapshot – an empty list included – so the renderer's badge simply mirrors main (RS2-3). The commit is `failed` when `httpResponseCode >= 400`: a refused page commits (S15); WI-29 computes it and only logs it, WI-17b acts on it. From WI-17b, a commit onto another page also retargets the entry watcher, the watch set and the link context and invalidates the still frame (part 3 §3.4). Any other document → **drop**, logged; that commit is then a commit with no intent – logged, pushes nothing. That is safer than taking it as the move: a page that reloaded itself would otherwise make the tab claim B while it shows A.
  2. **A main-frame `did-navigate-in-page` to the target** (the step was same-document) → drop the scope; the navigator sets the history index. Never for a `reload`, which is always cross-document: an in-page step the old page takes meanwhile, such as a scroll spy's `replaceState`, names the same document and must not end it.
  3. **Another `startPageLoad`** → the earlier pending load is dropped and its intent ended; history unchanged; logged "superseded" (RS3-3). S15: a superseded load fires no event of its own, and its `loadURL` rejection names the successor's URL; `startPageLoad`'s promise swallows it.
  4. **`did-stop-loading` while the load is still pending** → drop it and end its intent; history unchanged; logged "stopped without a commit" (RX3-2). The event covers the whole WebContents – the page as a whole stopped loading. S16 measured it over 12 cases in three runs: between a main-frame navigation's start and a commit that followed, it never fired – not while A's subframe, image or fetch finished inside the window, not for a superseded or a bodyless 404 load, not when A called `window.stop()` during an app-started `loadURL`. It fired early only when the page cancelled a link move with `window.stop()`, and that move never committed – the case this rule exists for.
- **A drop** disposes the pending scope; the committed scope, A's watchers and A's badge stay (RS2-2, RX2-3), and the paused pipeline resumes on A. **Nothing else ends a pending load**, and S15 and S16 show why: no main-frame fail event fires for a refused or a superseded load (S15), while a stale main-frame `did-fail-load` -3 naming the **old** URL arrives 3–4 ms **after** a commit (S16, an app-started move while A still loads); `did-finish-load` fires for the **old** page while the new one is pending, so it is neither a commit nor an end (S16); `did-start-navigation` fires for page-started navigations that `will-navigate` then cancels (S15); `did-start-loading` fires for the new page only when the tree was idle (S16); and the load call's promise is no commit signal – it resolved on A's `did-finish-load` about 370 ms before B committed, or rejected -3 naming A after B committed (S16). The handler's `request.signal.aborted` stayed false for a cancelled or superseded load (S16), so the handler cannot tell either. Subframe fail events (§2.6, S10) keep their writers unchanged. Not measured: `beforeunload`, redirects, back/forward moves, a subframe failing inside the window, a visible window.
- **Why a pending slot (RA2-1).** Round 1 swapped the scope when main started the load. That wiped A's badge and pointed A's watchers at B before B existed, left them so when the load never committed (`window.stop()`, a provisional failure), and let A's frames write into B's fresh scope. A swap at commit would lose the main-document refusal, which the handler records before the commit. `did-start-navigation` also fires for page-started navigations that `will-navigate` then cancels (S11). With a pending slot the one early write has a place to go, and everything else stays with the page on screen until that page is replaced. Round 2 ended a pending load on a main-frame fail event for its URL; S15 showed that neither a refused nor a superseded load fires one, so that rule would have left the tab pending for good – hence the four events above.
- If a page reloads itself and Chromium does not route that through `will-navigate`, no pending scope exists; the commit is a reload of the committed document and the committed scope is kept. Entries are deduplicated, so the badge does not double. Script-started navigation is out of scope.
- **Refusal set (RX2-2).** `previewFrameRefusals.ts` keeps one entry per address. It cuts each address to 2048 characters and removes line breaks – CR, LF, U+2028 and U+2029 – **before** the address becomes the dedupe key (the failure schema allows 2048 characters and no line breaks, `preview-schema.ts:298-301`), and holds at most `PREVIEW.MAX_FAILURES` (100) entries per page; further refusals are counted, not recorded, and the count is logged once, when the page ends. Each entry's error code follows its type. Tests: a 100 kB address; 1 000 distinct refused frames.

## 2.4 Second guard – request level

In `PreviewRequestFilter`'s `onBeforeRequest`, before `decideRequest`:

- `resourceType === 'subFrame'` with a URL that is not `erfana-preview:` or `about:` → cancel and record `frame-remote`, **whatever the allowlist says**. Approved hosts still load as subresources, never as frames.
- `subFrame` on `erfana-preview:` whose host is not this view's token → cancel and record `frame-escape`.
- Everything else is unchanged; `decideRequest` stays pure.

`PreviewFilterContext` (`PreviewRequestFilter.ts:81`) gains `ownToken`, `ledger` and `recordFrameRefusal(type, url)`, which looks up the committed scope's refusal set at each write (§2.3) – `ctx.pageScopes().committed().frameRefusals`, for which the `PreviewSessionPageScopes` slice widens. The context is **rebuilt in every `PreviewSessionFactory.create`** with that session's token – assembled in `previewSessionFilterContext.ts`, the fallback split WI-12 made because the factory was at 489 lines after WI-29 (480 after the split) – and the listener is registered again, because partition names are recycled (`src/main/services/CLAUDE.md`): a stale token must fail closed (RX9). Test: a recycled partition with a stale or foreign token cancels the subframe and records `frame-escape`. In S10 the browser's own-token `frame-src` refused remote and foreign frames before `webRequest`, so this guard is the second line; §2.6 is what lists those frames. Frame refusals go to the failure log, never to the permission band.

**As built (WI-12).** `buildPreviewSessionContexts` in `previewSessionFilterContext.ts` builds both contexts over one ledger – the handler's gains `recordDocumentFailure`, `recordFrameRefusal` and `ledger` – each routing its writes to the page scopes at the moment it writes, and the file now holds `PreviewSessionPageScopes` (the factory re-exports it; the WI-29 follow-up added `recordViewFailure`). The guard fails closed on an empty own token, a URL that does not parse, and a token in another case; it lists the full URL, or only the scheme for `data:` and `blob:`. Its tests are `PreviewRequestFilter.frames.test.ts` and `previewSessionFilterContext.test.ts`, over a shared `__test-helpers__/previewRequestFilterMocks.ts`, plus additions to the factory's `partitionRecycling` suite.

## 2.5 Frame guard – navigation level (WI-14)

Pure decision in `previewFrameGuard.ts`; event wiring in `previewFrameEvents.ts`, attached in `previewLiveWiring.ts` to the lifecycle hooks built there. On `will-frame-navigate` for a subframe (S4: fires for each `src` frame's **first** load, where `details.frame` is the new child with an empty URL, and for link clicks inside frames; `preventDefault` cancels both silently). It does **not** fire for frames the browser's CSP refuses (S10) or for `srcdoc` frames (S11); §2.6 and §2.7 cover those.

| Check | Rule | Failure type |
|---|---|---|
| depth | parent walk to the main frame, at most `MAX_FRAME_DEPTH + 1` steps; a child of the page is depth 1; `srcdoc` levels count; depth > `MAX_FRAME_DEPTH` (3) is refused | `frame-too-deep` |
| count | `mainFrame.framesInSubtree.length - 1 > MAX_FRAMES_PER_PAGE` (50) is refused. S12: inside the event the navigating frame is already in the list (length = k + 1 for the k-th frame), so frames 1–50 load and the 51st is refused; refused frames stay in the tree, so every later frame is refused too | `frame-over-limit` (aggregated) |
| scheme | `about:blank` → always allowed (not a document the page wrote); `about:srcdoc` → allowed; `erfana-preview:` with this token → allowed (the handler confines each request); another token → refused; any other scheme → refused (a cheap second line behind the CSP) | `frame-escape`; `frame-remote` on a first load, `frame-link-blocked` when an existing frame navigates |

- The guard writes each refusal itself, because a cancelled first load is silent (S4). All three writers – guard, filter, failed-load writer – go through the committed scope's refusal set (`pageScopes.committed().frameRefusals.record(type, address)`, looked up at each write), so one URL gives one entry.
- **Over the cap:** one entry per page load, written when the main frame stops loading or `FRAME_OVER_LIMIT_QUIET_MS` (500) after the last refusal. The timer lives in the committed page scope (`createPreviewPageScope`, cleared by its `dispose()`), so when a same-tab move commits within 500 ms it is disposed with A's scope and never writes into B's badge (RS14); `previewFrameEvents.test` pins that.
- **`_top` and `_blank` inside a frame do nothing (S13).** The sandbox has neither `allow-top-navigation` nor `allow-popups`; a real click, a script click and `top.location` all fail inside the frame, and nothing fires in main – no `will-navigate`, no `will-frame-navigate`, no window-open handler. No guard is written for them, and they cannot be listed in the badge (documented in the HTML preview docs). The earlier `initiator` check is dropped.
- Cost per navigation: a walk of at most 4 steps plus one `framesInSubtree` read; past the count cap no further reads (§2.7).

**As built (WI-14).**

- **Order.** The scheme first (no reads); then, on the own token, a first load on a page already past the cap (no reads), the depth and the count. The count cap applies to a frame's first load only – a link inside a frame that already showed a document adds no frame – and once a page is past it every new frame is refused and counted with no further reads, so the guard fails closed. S17: S12's count rule holds for `srcdoc` frames too (2 to 61 for 60 siblings).
- **Entry addresses**, as the other writers list them, so one frame gives one entry: an own-token frame too deep – its path, never the token; a foreign-token or remote frame – the full URL; `data:` and `blob:` – the scheme; `frame-link-blocked` – scheme and host; a URL that does not parse – as it came (the refusal set cuts it), and as a link only its scheme.
- **Bookkeeping in the page scope.** The committed-frame set remembers at most 1 024 frames per page (`MAX_REMEMBERED_FRAMES`, local to `previewPageScope.ts`); past it, a frame not remembered counts as one that never showed a document – the stricter reading. The over-limit entry is written once per kind (`src`, `srcdoc`) per page.
- **Fails closed.** A frame the guard cannot judge – gone, or a read that throws – is cancelled, with a warning that names the panel and the reason, never a URL. A `srcdoc` check that throws only logs: the frame shows either way (answer 9).

## 2.6 Frames the browser refuses first – the failed-load writer (RS1, WI-14)

S10: with an own-token `frame-src`, a remote frame or a frame on another token never reaches `will-frame-navigate`, `webRequest` or the handler. The only main-side signals are a console error in the parent ("Framing '…' violates the following Content Security Policy directive …") and `did-fail-provisional-load` with code -30 (`ERR_BLOCKED_BY_CSP`), `isMainFrame` false, the full URL in `validatedURL`, and the subframe's process and routing ids (S10 maps them to the frame).

`previewFrameEvents.ts` listens to `did-fail-provisional-load` on the view's `webContents`:

| Condition | Records |
|---|---|
| not the main frame, code -30 or -27, URL on `erfana-preview:` with another token | `frame-escape` – entry: the frame's address |
| same codes, any other scheme, the frame never committed a document | `frame-remote` – entry: the address; for `data:` and `blob:` only the scheme, so a large inline URL never enters the log |
| same codes, the frame committed a document before (the page scope's committed-frame set, fed by `did-frame-navigate`, keyed by `frameTreeNodeId`) | `frame-link-blocked` – entry: scheme and host only |
| the main frame, or any other code | nothing here – the handler and the load-state path own those |

- -20 (`ERR_BLOCKED_BY_CLIENT`) is the filter's own cancel and is already recorded at its source.
- The frame must still resolve from its process and routing ids; a frame already gone is skipped.
- An inert `about:blank` commit – the empty document a script-made `<iframe>` with no `src` commits first – is no shown document: the committed-frame set skips it, so a later refused `src` is listed as a refused frame (`frame-remote`), not a refused link (`frame-link-blocked`). An `about:srcdoc` commit still counts.
- As built (WI-14): the frame resolves through `webFrameMain.fromId`; a -30 or -27 on this view's own, valid token is not listed here – the handler owns such a frame; an own token that is not 32 lowercase hex makes every preview frame `frame-escape` (the CSP then says `frame-src 'none'`, WI-13).
- Every entry goes into the committed scope (§2.3), so a refusal from A's frames while B loads disappears with A.
- **A frame's `did-fail-load` no longer settles the page's load (RX2-3).** Today every `did-fail-load` – frames included – reaches the load-settled path (`previewViewLifecycle.ts:156`), which reads the page colour in the isolated world and steps the backdrop; a page with many refused frames would drive both. WI-14 passes the event on only when `isMainFrame` is not `false`. Test in `previewViewLifecycle.test`; `PreviewViewService.test.ts:778`, which emits the event with no arguments, stays unchanged.
- WI-24 asserts an entry for the remote, foreign-token, `data:` and script-made `blob:` frames and records which layer wrote each (RX10).

## 2.7 `srcdoc` frames and the caps (RS9, S11) – decided, answer 9

S11: `will-frame-navigate` never fires for `srcdoc` frames (0 events over a four-level chain and 60 siblings), so they cannot be cancelled before they load. `did-start-navigation` (`about:srcdoc`, not the main frame) does fire for each, `frame-created` gives the correct parent chain, and `framesInSubtree` counts them correctly (61 for 60 frames, S11 and S12). `WebFrameMain` has no stop or navigate method in Electron 39, so emptying a frame after the fact would need main-run script in the page's frames – best effort, not deterministic.

**The rule (user answer 9, option 1):**

- `src` frames: the caps apply exactly as P2-AC4 says – a `src` frame at depth 4 (under `src` or `srcdoc` parents) and every `src` frame past 50 stay empty and are listed.
- `srcdoc` frames: detected from `did-start-navigation`. One that is too deep, or past the count cap, **is shown anyway** and is listed once per page load under the existing labels (§2.12), with an entry that says so: "srcdoc frame – shown anyway; the depth limit covers src frames only", and "10 srcdoc frames over the limit of 50 are shown anyway" (RU2-5). Once the count entry is written, later `srcdoc` frames only bump a counter, so main does no per-frame reads past the cap.
- Main runs no script in a page's frames. Option 2 – main telling an over-cap frame to blank itself – was offered and not chosen, so no blanking spike was run and there is no blanking code.
- Why acceptable: the cap is a robustness limit, not a security boundary. `srcdoc` content is written by the page itself, inherits the sandbox and the CSP (S3), and can load nothing the page could not load directly. Recorded in `docs/technical-debt.md`, `docs/security.md` and the HTML preview docs (Phase 10).

`srcdoc-chain.html` makes a `srcdoc` frame the 4th level and also holds a `src` frame at depth 4 under `srcdoc` parents; `many-srcdoc.html` holds 60 `srcdoc` frames. WI-24 asserts the `srcdoc` 4th level shown and listed, all 60 `srcdoc` frames shown with one count entry, and the `src` 4th level empty and listed.

## 2.8 Blocked hosts inside frames reach the permission band (S9)

- **No preload in frames.** `nodeIntegrationInSubFrames` stays `false` (`previewSessionPolicy.ts:43`), so frames get no IPC and the link channel stays main-frame only. `previewSessionPolicy.test.ts:108` stays as it is.
- **Main-side detection.** S9: a CSP violation inside a frame reaches main as `console-message` with `details.frame` set to the real subframe (flag off). `previewFrameCspConsole.ts`: only `level === 'error'`, only a frame that is not `wc.mainFrame` and whose parent walk reaches `wc.mainFrame` within 4 steps (frames of this view only).
- **Arrival cap (RX2).** Before truncating or matching, each view admits at most `FRAME_CONSOLE_MAX_PER_SECOND` (100) such messages per second; the rest are dropped and counted, and the count is logged at most once per window. As built (WI-14), `Framing` lines and main-frame lines are dropped before the cap, so a flood of refused frames spends none of it; the depth walk comes after it. Then the message is truncated to `FRAME_CSP_CONSOLE_MAX_CHARS` (4096) and matched by anchored, backtracking-free patterns – the quoted URL at most 2048 characters, the directive `[a-z-]{1,64}`:
  - Electron 39 format, captured in `temp/spike-124/logs/s9.log`: `Loading the <kind> '<url>' violates the following Content Security Policy directive: "<directive> …`
  - the older `Refused to load the <kind> '<url>' because it violates the following Content Security Policy directive: "<directive> …`
  - S17 (WI-14): `Loading media from  '<url>' violates …` (with the two spaces Chromium prints; audio and video) and `Connecting to '<url>' violates …` (fetch and XHR); the directive-less `Fetch API cannot load …` line that follows is ignored.
  - `Framing '<url>' violates …` lines (S10) are **ignored**: a refused frame is a badge entry (§2.6), never a band row.
  - The captured lines are the parser's fixtures; an unrecognised format is ignored (no row). A flood fixture pins the arrival cap.
- The match becomes `{ blockedURI, effectiveDirective }` and goes into the **same** CSP-violation bridge as the preload's reports – the committed page scope's, through `pageScopes.committed().handleCspViolation(…)` (WI-29: each scope has its own bridge, so its budgets and caps are per page): same per-second budgets, origin and per-host caps, dedupe and origin canonicalisation, then the same `reportBlocked` sink into that scope's ledger, so the band row with Allow appears exactly as for the page itself.
- **Framing violations never reach the band (RS2, RX2-7).** The preload forwards every trusted `securitypolicyviolation` (`previewPage.ts:186-189`), and `kindFromDirective` maps `frame-src` / `child-src` to `frame` (`previewBlockedKind.ts:83-84`), so today a remote `<iframe>` in the top page produces a band row whose Allow cannot work – approved hosts never load as frames, and the row returns after the reload. `previewCspViolationBridge` now drops `frame-src` and `child-src` violations **right after the zod parse** – before the per-view origin cap, the per-host cap and the report budget are charged (`previewCspViolationBridge.ts:276-310`); only the parse budget (500 a second), which bounds parsing itself, is spent. That holds for the preload path and the console path alike, so a flood of remote frames cannot fill the list and hide a real host. Test: 60 remote-frame violations, then a real script host still gets its row. The failed-load writer (§2.6) is the single badge source for those frames, so there is no second writer to deduplicate. WI-24 asserts `refused.html` leaves the band empty.
- Main-frame console messages are ignored on this path; the preload already reports them with `isTrusted`, so nothing is counted twice. S9 caveat: a subframe's own `console.log` is attributed to the main frame, so page-printed look-alikes land on the ignored path. If one got through, it could add a row the user may approve – no more than a real `new Image().src` to that host already gives.
- **Approval.** `rebuildCsp` → reload through `startPageLoad` → frames are requested again under the same token and receive the rebuilt policy → the host loads inside the frame (P2-AC2). An approval that lands during a pending same-tab move replaces that move's load (§2.3, event 3; technical debt, part 3 §3.6).

## 2.9 Live reload for frame sources

- `linkExtract.ts`: `<iframe src>` becomes a watch candidate and a frame source; `<iframe srcdoc>` is parsed with the same extractor, its links resolving against the parent document's folder. New export `extractFrameSources(html) → { src: string[], srcdocHtml: string[] }`. A backslash in a frame `src` becomes `/` before resolving (Chromium treats `\` as `/` in standard URLs); other link kinds are unchanged. As built (WI-15): an element with both counts as its `srcdoc`, as the browser shows it, and an empty `srcdoc` is skipped.
- `previewFrameSources.ts`: breadth-first from the entry. The entry's own links come first, then frame documents by depth (1 to 3) – `src` frames before `srcdoc` frames within a level – each read with the existing bounded reader (`PREVIEW.MAX_ENTRY_HTML_BYTES`, 4 MiB), stopping at `MAX_WATCHED_FILES` (16 per view; 64 global unchanged). Returns `{ candidates, frameAssets }`, where `frameAssets` is every path referenced from a frame document plus the frame documents themselves. An unreadable frame document is skipped; real refusals are reported by the guard and the handler. The watch coordinator's confinement and real-path dedupe are unchanged (Windows). As built: only `.html` / `.htm` frame documents are read and parsed; at most `MAX_FRAMES_PER_PAGE` (50) frame documents are scanned, which bounds a page of link-less `srcdoc` frames that never reaches the budget; a quick `<iframe` text check spares a document with no frame the second parse; a `src` frame one level past the depth cap is watched – it is a link of its parent – but not read.
- **Only inside the project (WI-15 follow-up).** A frame document is read only when `confinePath` – the gate the protocol handler and the watch coordinator use – passes on the path as written and again after `realpath`, and it is read at the real path that passed. With no project root no frame file is read; nothing is logged. A refused frame's path stays in the candidate list, where the watcher's own gate drops it (counted as not watched); folders the handler never serves (`node_modules`, dot-folders) are skipped too. The wiring hands the session's `realRoot` to the pipeline – WI-15's one edit of `previewLiveWiring.ts`.
- **Frame assets in the watcher's spelling.** `watchedFrameAssets(frameAssets, watchSet)` turns each frame asset into the spelling the watch coordinator reports its changes in – the real path, through symlinks, `/var` → `/private/var` on macOS and Windows short names – so `classifyReload` compares like with like; it calls `realpath` only for an asset the coordinator neither watched nor dropped.
- **Shared stylesheet.** `classifyReload(paths, frameAssets)` (`PreviewReloadPolicy.ts:62`): a single `.css` change swaps in place only when no frame uses it; otherwise a full reload, so the frame is never left stale. The in-place swap stays a top-page promise only (settled assumption).
- The call site lives in `previewLivePipeline.ts`, which asks for the page on screen once per run and re-runs `classifyReload([path], frameAssets)` on a swap decision, so the reload policy built in the wiring is unchanged. The pipeline's frame tests are in `previewFrameSources.pipeline.test.ts`, split from `previewFrameSources.test.ts`.
- Frame assets share the 16-file budget, so a framed page with more than 16 files shows a non-zero "not watched" count – expected, not a fault.

## 2.10 Gitignore and confinement – a lasting contract

Confinement on every served request (real path, symlinks, always-excluded folders, dot-paths – `previewPathResolve.ts`) applies to frames unchanged. The gitignore check (`PreviewEligibilityService.ts:104`) only decides how a tree click or a link opens a file; it never blocks a served request. So a gitignored `.html` in the project may run inside a frame, while a link to it still opens as source. Written into the HTML preview docs and the security doc's accepted risks.

**A leaf symlink is a missing file, not an escape.** A frame whose `src` ends in a symlink – pointing inside the project or out of it – is listed under Missing local file (404), not Frame escaped the project: the #74 resolver (`previewPathResolve.ts`) opens with `O_NOFOLLOW` at step 8e, which refuses every leaf symlink before the escape check at step 8h. Confinement is unchanged – the target is never read – and the resolver stays as it is, because "escaped" would be wrong for a symlink inside the project. A symlinked folder that leads out is still an escape (step 8c). On Windows there is no `O_NOFOLLOW`; from the code, the dev/ino compare (step 8g) refuses the same symlink with 403, listed as an escape – not yet run there.
