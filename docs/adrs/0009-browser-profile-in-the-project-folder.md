# ADR 0009: The browser's trust decisions live in the project folder, its Chromium profile under Erfana's user data

- **Status**: accepted (owner decision, 2026-11-03) – revised 2026-11-02 after the expert panel (the location itself is an owner decision of 2026-11-01); decision 6 corrected 2026-11-05 (`notices.json` is unsigned); **amended 2026-11-03** (owner, option E): the Chromium profile moves to `<sessionData>/browser-profiles/<name>/` – see [Amendment 2026-11-03](#amendment-2026-11-03-the-chromium-profile-moves-under-user-data)

## Context

Each project keeps its browser profile in `<project>/.erfana/browser/` (owner, 2026-11-01). The accepted risks: the agent, scripts, sync, archives and build contexts can read or change it; `git clean -fdx` deletes it. Open points: how the folder is created and guarded, where Erfana's own trust decisions live, how a **cloned** profile is treated, how deletes stay inside the project, how Linux without a keyring behaves, and how Erfana's separate window processes share a session.

Facts: `session.fromPath` gives a persistent session per absolute path ([Electron session](https://www.electronjs.org/docs/latest/api/session)); a session cannot be destroyed while the app runs; there is no per-session cache-size setter, and `--disk-cache-size` sets the maximum of each disk cache (per session, inferred). Erfana opens each window as its own process and locks a project to one of them (`ProjectLockService`). `lockHmac.ts` keeps a `safeStorage`-encrypted secret and **turns signing off** on Linux `basic_text`.

## Decision

1. **Layout** (amended 2026-11-03). In the project: `.erfana/browser/.gitignore` (exactly `*`, spec change S-20); `profile/Erfana/` (Erfana: `marker.json`, `trust.json`, `credentials.json`, `permissions.json`, `popups.json`, `zoom.json`, `history.json`, `notices.json`, `keyring-canary.bin`); `captures/`. Under Erfana's own data folder (`app.getPath('sessionData')`, which is `userData` – Erfana does not move it): `browser-profiles/<name>/project.json` (the canonical project path the folder belongs to) and `browser-profiles/<name>/chromium/` (the Chromium profile: cookies, storage, cache, network state). `<name>` follows Claude Code's `~/.claude/projects/` rule: every UTF-16 code unit of the canonical path that is not an ASCII letter or digit becomes `-` (`/Users/x/.claude` → `-Users-x--claude`, `C:\Users\x\proj` → `C--Users-x-proj`); past 128 characters (40 on Windows, for `MAX_PATH`) it is cut there and `-<first 8 hex of the path's SHA-256>` is appended. The rule is lossy, so a folder is used only when its `project.json` names this exact path; otherwise `<name>-2`, `<name>-3`, … up to `-100` is tried, and every candidate is checked before a new one is claimed (`browserProfileFolders.ts`). A profile left in `<project>/.erfana/browser/profile/` by an earlier build is never read by Chromium again; Forget deletes it with the folder.
2. **Guards before the session exists** (`browserProfileGuards.ts`): canonical project path (`realpathSync.native`); per level (`.erfana`, `browser`, `.gitignore`, `profile`, `profile/Erfana`, `captures`) `lstat` without following links, refuse symlinks and junctions, require the real path inside the project; create one level at a time; files with exclusive no-follow flags (Windows: `wx`, then `fstat` and a real-path re-check). Re-run before each capture write. Failure refuses the tab with a toast. `erfanaDirGate.ts`'s first step is reused. The same guards run, rooted at the canonical `sessionData` folder, on `browser-profiles`, `<name>`, `project.json` and `chromium` (amended 2026-11-03): a link at `browser-profiles` or `chromium` refuses the tab; a candidate `<name>` that is a link, a file or has no readable `project.json` is skipped, never used.
3. **A cloned or copied profile is set aside** (spec change S-12). `marker.json` holds the canonical project path and creation time, HMAC-signed; a copy of the signed marker is kept in `~/.erfana/browser-profiles/<hash of canonical path>.json`. At session creation the profile is trusted only if both copies verify and match. It is also untrusted if `git ls-files .erfana/browser` lists anything (the folder was committed). An untrusted profile is renamed to `.erfana/browser/profile.untrusted-<UTC time>` (guarded like a delete) and a fresh one is created – a cloned repository's service worker, cache or local storage never runs. Since the 2026-11-03 amendment a repository can no longer ship Chromium data at all, but the user-data `chromium/` is set aside with it, as `chromium.untrusted-<the same UTC time>`: distrust of the project half means the whole profile starts fresh.
4. **One session per project, one process per project** (spec change S-24). `session.fromPath(<sessionData>/browser-profiles/<name>/chromium)` (amended 2026-11-03; was `<canonical>/.erfana/browser/profile`) in the process that holds the project lock. The lock also makes a project's folder claim race-free: only two *different* projects can race for one name, and the loser moves on to the next. Since every window is its own process, "share one session across windows" means across windows of that process; a second process that opens the project's browser while the lock is held elsewhere is refused with a toast naming the holder, and a stale lock is taken over through `ProjectLockService`'s existing rules. Popups are the only windows that share a tab's session across windows.
5. **Registered ids, not session lookups, decide exemptions.** `browserSessionRegistry.ts` records each browser session; `BrowserTabService` and `BrowserPopupWindow` register each view's `webContents` id **synchronously** when they create it. In `web-contents-created`, a `webContents` whose session is a browser session but whose id is not registered is destroyed at once and logged (fail closed); only registered ids skip the `webContentsBaseline`.
6. **Signed trust files.** `trust.json`, `credentials.json`, `zoom.json` and `history.json` carry HMAC-SHA-256 over `{ kind, generation, canonical project path, content }`; the generation counter lives in `~/.erfana/browser-profiles/<hash>.json`, so an older signed file replayed into the folder is refused. A failing file is ignored, replaced on the next write, and logged (event and path only). (Amended 2026-11-05, owner decision: `notices.json` is not in this list. The code keeps it unsigned on every backend, read without following a link and replaced by a rename – `browserKeyringState.ts`. It holds the weak-protection dismissal and the recorded backend name.)
7. **Linux `basic_text` (no keyring).** There is no OS-protected key, and `lockHmac` signs nothing there. Behaviour: trust decisions, saved sign-ins and zoom are kept **in memory for the session only** (spec change S-26, extending 025-FR-022's rule); history and notices are kept unsigned; (ADR 0012's loopback server needs no per-folder key – its address token is random per run); no keyring canary is written; a switch from a keyring backend to `basic_text` is detected from the backend name recorded in `notices.json` and shows "Logins were reset because the keyring changed". Unit tests run every rule per backend (`keychain`, `dpapi`, `gnome_libsecret`, `kwallet*`, `basic_text`).
8. **Keyring canary** (other backends): at session creation decrypt `keyring-canary.bin`; on failure show the reset notice once and rewrite it.
9. **Cache cap**: `--disk-cache-size=536870912` before `app.whenReady()` (spec change S-5).
10. **Kept out of Erfana's views**: `.erfana/browser` always excluded from the project tree, watcher and git polling. Best effort against cloud sync: set `com.dropbox.ignored` and the macOS File Provider ignore attribute on `.erfana/browser` where the platform supports it; failures are logged, never fatal. (Amended 2026-11-03: the Chromium profile is no longer in the project, so project sync, archives and build contexts no longer carry cookies, storage or cache.)
11. **Deletes stay inside.** Before **every** delete (Clear's capture step, Forget, expiry, setting a profile aside) the per-level link check of decision 2 runs again, and the target's real path must equal `<canonical>/.erfana/browser` or a path under it. Windows pending deletes are stored in `~/.erfana/browser-pending-deletes.json` as project canonical path plus relative path, HMAC-signed, and re-guarded before they run at the next start. In the user-data folder (amended 2026-11-03) a delete never leaves `<sessionData>/browser-profiles/<name>/` (each entry is removed with `rm`, which removes a link itself, never its target); a Windows delete the running session blocks leaves a `forget-pending` file there, and the next start – or, failing that, the project's next open, before its session exists – finishes it; the tab is refused while it cannot.
12. **Clear and Forget**: Clear uses `clearStorageData`, `clearCache`, `clearAuthCache`, `closeAllConnections` and the matching keys of Erfana's files, each under a 10 s `withTimeout`; the session APIs act on the Chromium profile wherever it lives, so Clear reaches the user-data folder with no path of its own. Forget closes the project's browser tabs, clears every storage, then deletes `.erfana/browser/` and every entry of `<sessionData>/browser-profiles/<name>/` except `project.json` (amended 2026-11-03), which keeps the name this project's so the still-running session's folder cannot be claimed by another project. Both halves are tried even when one fails; the first error is reported.
13. **No tabs restored**: no tab list is stored anywhere (025-FR-006).
14. **Project switch in a window** (`ProjectService` session change): end pick mode, abort a capture write and delete its partial files, then close the old project's browser views – in that order – before the new project opens.

Implementation note (decision 6): the generation counters sit in their own file next to the marker's home copy, `~/.erfana/browser-profiles/<hash>.generations.json` (`profileGenerations.ts`), and `permissions.json` is signed the same way as `trust.json` and `credentials.json`.

## Amendment 2026-11-03: the Chromium profile moves under user data

**Found.** On macOS Chromium always runs the network service in its sandbox (`IsNetworkSandboxEnabled()` is true on Mac), and Electron 44.9.3 gives that sandbox write access only below `app.getPath('sessionData')` (`GetNetworkContextsParentDirectory()` returns `DIR_SESSION_DATA`; Chromium `sandbox_parameters_mac.mm`). A `session.fromPath()` profile in `<project>/.erfana/browser/profile` therefore never wrote its `Cookies` database, HTTP cache, Shared Dictionary, Trust Tokens or network state: every sign-in was lost at quit, in packaged, dev and e2e builds alike. Electron has no setting to grant another folder (see [technical debt](../technical-debt.md) entry 69, which holds the upstream issue text).

**Decided (owner, option E).** Keep the Chromium profile under Erfana's own data folder, one folder per project (decisions 1, 2, 4, 11 and 12 as amended above); keep Erfana's signed files, the marker and captures in the project, where nothing breaks. The out-of-project trust anchors stay where they were, `~/.erfana/browser-profiles/<sha-256>.json` and `.generations.json`: they are keyed collision-free by the exact path, must outlive Forget (a replayed signed file stays refused after it), and every signed-file store reads them without the folder-name lookup – one naming scheme for them would need that lookup in every store for no gain in safety.

**Effects.** Sign-ins persist across restarts (025-AC-015, e2e with the sandbox on); `git clean -fdx` no longer signs the user out (it deletes Erfana's files and captures; the marker is rewritten and the Chromium data kept); moving or renaming a project folder starts its browser profile fresh, as before; a deleted-and-recloned project at the same path finds its old Chromium data unless the clone carries a committed `.erfana/browser` (then both halves are set aside); the user's data folder grows by each project's profile until Forget (the disk-cache cap, decision 9, still bounds the cache).

## Consequences

- Planted or replayed trust files grant nothing; a cloned profile never runs; reading cookies, storage and cache stays possible for same-user processes, as accepted – but no longer through the project folder (amended 2026-11-03).
- Linux without a keyring forgets permissions, certificate exceptions and zoom at quit.
- On Windows the project folder cannot be moved or deleted while Erfana has a browser tab open in it: Erfana's own files there stay open (user guide).
- The HMAC is a guard, not a secret store: on Windows and Linux any same-user program can decrypt the `safeStorage` secret.

## Alternatives considered

- **Profile under the app's user-data folder** – out of the agent's reach, but the owner chose the project folder. Rejected by the owner on 2026-11-01; **adopted for the Chromium half on 2026-11-03** (amendment above), because the macOS network sandbox cannot write a profile anywhere else.
- **Everything, Erfana's files included, under user data** (2026-11-03) – one location, but it moves every signed-file store and its tests for no fix: nothing breaks with those files in the project. Not chosen.
- **Turn the network sandbox off** (`--no-sandbox` or a feature switch) – weakens every page's isolation for a storage path. Rejected.
- **A symlink from the project to user data** (or the reverse) – the guards refuse links by design (decision 2), and a link does not change what the sandbox allows. Rejected.
- **Trust decisions in Chromium's stores** – Electron persists none of them. Rejected.
- **Unsigned trust files** – any project script could grant the camera or trust a forged certificate. Rejected (owner question Q3 confirms).
- **Trust a cloned profile** – a repository could ship a service worker that runs on the user's first visit. Rejected.
