# ADR 0007: Pick overlay drawn by the engine through the DevTools protocol

- **Status**: accepted (owner decision, 2026-11-03) – revised 2026-11-02 after the expert panel (`.local/panel/design-025-adr/`); amended 2026-11-03 for the engine-probe results of commit 8 (decisions 2, 4, 6, 7 and 11) and the owner's answers to Q1, Q2 and Q5; **amended 2026-11-05** (owner, queue item 24): the read-only "covered by" check of 025-FR-035 may hit-test the element drawn on top – see [Amendment 2026-11-05](#amendment-2026-11-05-owner-decision-the-covered-element-check); **amended 2026-11-05** (owner): the live outline is drawn by Erfana, in ink and paper, on a native surface over the page – see [Amendment 2026-11-05](#amendment-2026-11-05-owner-decision-the-live-outline-is-drawn-by-erfana)
- **Date**: 2026-11-03 (amended 2026-11-05)
- **Deciders**: Marcin Obel (owner), Claude Code
- **Related**: [spec 025](../../specs/spec-t4-025-built-in-browser/requirements/02-requirements.md) 025-FR-025 to 025-FR-029, 025-FR-033, 025-FR-035, 025-FR-038, 025-NFR-001, 025-NFR-004 · [solution design](../../specs/spec-t4-025-built-in-browser/architecture/001-solution-design.md) § 4, § 5, § 11 Q1–Q2 · [ADR 0005](./0005-sub-frame-preload-one-receive-channel.md) · [ADR 0008](./0008-freeze-with-debugger-pause-after-capture.md) · [design note](../designs/browser/README.md) § Pick overlay and label

## Context

Pick mode must outline the element under the mouse, label it, refine to parent and child, and read its facts – in the top page and in every frame, including cross-site frames in another process, nested, `srcdoc`, `about:blank`-written and sandboxed frames (025-FR-029). 025-NFR-001 asks for no Erfana code inside the page. Hover must keep reaching the page in pick mode (025-FR-025, 025-FR-028), and the highlight must follow the mouse within 50 ms at p95 (025-NFR-004).

Electron 44 gives main three tools:

- `webContents.debugger` – a CDP client; `sendCommand(method, params, sessionId)` reaches flattened child sessions ([Electron debugger](https://www.electronjs.org/docs/latest/api/debugger)). Its `detach` event fires "when DevTools is invoked for the attached webContents".
- `before-mouse-event` – emitted before the page receives a mouse event; `preventDefault` keeps the event from the page. Its `MouseInputEvent` carries view `x`/`y` and screen `globalX`/`globalY` ([webContents](https://www.electronjs.org/docs/latest/api/web-contents)).
- The CDP `Overlay` domain, **experimental** ([Overlay.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Overlay.pdl)): `highlightNode` with `showInfo`, and `highlightQuad` / `highlightRect` with a fill and an outline colour.

## Decision

**Engine-drawn, main-driven picking with no preload**, one CDP session per view.

1. **Session.** `BrowserCdpSession` attaches when the view is built and sends `Target.setAutoAttach({ autoAttach: true, waitForDebuggerOnStart: true, flatten: true })` (fixed parameters). Each child target gets its always-on domains sent **without awaiting each reply**, then `Runtime.runIfWaitingForDebugger`, and its own `setAutoAttach` for nested frames. Popups get a session of the **popup kind**, which has no pick, overlay or freeze methods (§ 5 of the solution design).
2. **Domains only when needed.** Always on, every target: `Runtime` (console, exceptions, hang probe) and `Log`; `Network`, because the commit-8 probe showed `Log.entryAdded` (source `network`) cannot carry 025-FR-038's failed requests from a dedicated worker (see Probe results), with a bounded request-id map and zero body buffers (`NETWORK_ENABLE_PARAMS`, `src/main/services/browser/cdp/cdpPinned.ts`). `DOM`, `CSS` and `Overlay` are enabled when pick mode starts and disabled when it ends; `Page` only where dialogs need it (ADR 0011). Console objects are released (`Runtime.releaseObjectGroup`, `Runtime.discardConsoleEntries`) after each entry is copied into the log buffer.
3. **Flood budget.** Per target, at most 200 events and 1 MB of event payload per second; over budget, `Runtime` and `Log` are disabled for that target until the next navigation and the capture notes "logs truncated" (spec change S-14). `DOM.getDocument` is never called with `depth: -1`. Outer HTML is read by `Runtime.callFunctionOn` in an **isolated world** (`Page.createIsolatedWorld`) with a fixed function that cuts the string in the page to 20,001 UTF-16 units before it crosses the protocol (spec change S-14).
4. **Hit test in main** (amended 2026-11-05 – the covered-element check, below). `before-mouse-event` fires per frame widget, so an out-of-process frame's events carry **frame-local** `x`/`y` (confirmed by the commit-8 probe). For a point in the top document, main uses `globalX`/`globalY` minus the view's screen origin (or `x`/`y` when the globals are 0, as with main-side `sendInputEvent`). For a point in an out-of-process frame, `globalX`/`globalY` are the frame's bounding-box origin plus the *untransformed* local point, which is wrong for a transformed frame (the probe: about 18 px off for a rotated, scaled frame). Main therefore treats the globals only as the place where the frame's box starts, finds the frame target whose box in the view starts there (tolerance `FRAME_ORIGIN_TOLERANCE_PX`, 2 CSS px), and starts the hit test **in that frame at the exact local point**; the point is mapped to the view through the frame's quad. With no matching frame it falls back to the globals. The test is `DOM.getNodeForLocation({ x, y, ignorePointerEventsNone: false })` – the element the user's click would hit – and, when it lands on the owner of an out-of-process frame, goes on in that frame after mapping the point through the owner's content quad (`DOM.getContentQuads`, so transformed and nested cross-site iframes work). One hit test in flight; the latest position wins. Outside pick mode the mouse router returns at once except for the click guard and the activation tracker. Code: `src/main/services/browser/pick/pickHitTest.ts`, `pickGeometry.ts` (`pointerCandidates`).
5. **Not `Overlay.setInspectMode`** – it swallows mouse moves (hover menus would not open) and confirms on its own click. Commit 8 keeps a probe that shows this.
6. **The live highlight – outline only (owner decision Q2, 2026-11-03; amended 2026-11-05 – [drawn by Erfana](#amendment-2026-11-05-owner-decision-the-live-outline-is-drawn-by-erfana)).** The live highlight is an outline, drawn by the engine through `Overlay.highlightQuad` / `Overlay.highlightRect` on the owning session (the quad of the element's border box, mapped into the owning frame), with no fill. The decided Focus card is **not** amended: the live outline follows the Element picker card's rule as closely as the engine allows. In forced-colours mode (`nativeTheme.inForcedColorsMode`) the colour comes from the system highlight colour. The engine cannot draw the card's two-tone outline exactly; the two-tone outline is drawn on the still image. `Overlay.highlightNode` with its fill, band and engine label is not used for the live highlight.
7. **The label (owner decision Q1, 2026-11-03).** The exact 025-FR-026 text from `src/shared/browser/elementLabel.ts` is echoed in the pick row's status slot, replacing the banner's later clauses while hovering. It is the stable, exact form and is what tests assert (a hook returns the requested node and box; one `capturePage` pixel check proves the live paint). Because Q2 chose an outline-only highlight, the engine's own label next to the element (a feature of `highlightNode`'s `showInfo`) is not drawn; the status slot is the one home of the label. *Inferred consequence, to be confirmed by the owner: 025-FR-026 no longer promises a label next to the element.*
8. **Crosshair (spec change S-11, accepted).** The commit-8 probe showed `webContents.insertCSS('* { cursor: crosshair !important }', { cssOrigin: 'user' })` reaches the top document only; same-origin and cross-site frames keep `auto`. The crosshair therefore shows over the top document, and over frames only where the engine draws it; the still image carries the crosshair of 025-FR-034.
9. **Focus emulation** (`Emulation.setFocusEmulationEnabled`) on every frame target while pick mode is on, turned off at **every** pick end.
10. **Reads.** Refinement and the 025-FR-033 facts use `DOM` and `CSS` on the owning session; the two React reads – the lookup and, for React 19, the `_debugStack` read (`REACT_DEBUG_STACK`, owner decision 2026-11-05) – are the only main-world calls (`Runtime.callFunctionOn`, fixed function identity, `userGesture: false`, `awaitPromise: false`, `throwOnSideEffect: true`).
11. **DevTools coexistence (owner decision Q5, 2026-11-03).** The commit-8 probe (Electron 44.9.3, macOS) showed DevTools does **not** detach Erfana's session: commands answer while DevTools is open and after it closes. Pick therefore stays available with DevTools open, and spec change S-9 (pick unavailable with "Close DevTools to pick", "DevTools took over – nothing was sent") is **not** adopted. The probe stays as a regression test and runs on Electron update pull requests; Linux and Windows are not yet probed.

### Frame kinds

| Frame kind | Supported |
|---|---|
| Top document, same-process frames, `srcdoc`, script-written `about:blank`, `<frame>` | Yes |
| Cross-site frame in another process, nested, transformed | Yes (auto-attach; owner quad) |
| Sandboxed without `allow-scripts` / `allow-same-origin` | Yes; origin `null`; React lookup reports "source not found" |
| Open or closed shadow root | Yes; closed-root rule of 025-FR-033 |
| Plugin or PDF content in `<embed>` / `<object>`; `<fencedframe>` content | No – the host element is picked (spec change S-2) |
| `<canvas>`, WebGL, video | The element; crosshair in the screenshot |

## Amendment 2026-11-05 (owner decision): the covered-element check

**Found.** 025-FR-035 sends an element covered by another one as picked, with the note "covered by" and the covering element's tag in the untrusted block. The check ran the pick hit test of decision 4 at the centre of the picked element's box, and that test is pinned to `ignorePointerEventsNone: false` – the element a click would hit. An overlay with `pointer-events: none` lets the click through, so it was never found as covering, though it is drawn on top of the element (025-AC-035's fixture overlay; `e2e/browser-pick-frames.e2e.ts` held the case as an expected failure, owner queue item 24).

**Decided (owner, 2026-11-05).** The hit test has two rules. The **click** rule, `ignorePointerEventsNone: false`, stays the only rule that chooses what is hovered, outlined and picked – decision 4 is unchanged for picking. The **topmost** rule, `ignorePointerEventsNone: true`, finds the element drawn on top at a point and is used **only** by the covered-element check: one `DOM.getNodeForLocation` per session at the centre of the picked element's box, through the same frame descent and embed-host rule as the pick, after the user has picked. It reads which element is on top and nothing else: no page script runs, nothing is injected into any world, the page's state is not touched, and the element sent is the one the user picked whatever the check finds. The CDP allow list now takes `ignorePointerEventsNone` as a required boolean, so each caller still names its rule. Code: `PickHitTest`'s `HitRule` (`src/main/services/browser/pick/pickHitTest.ts`), `coveringTag` (`src/main/services/browser/capture/captureFacts.ts`), `DOM.getNodeForLocation` in `src/main/services/browser/cdp/cdpAllowList.ts`.

**Why.** The note exists to tell the agent that what the user saw over the element is not the element; a click-through overlay (a dimming scrim, a watermark, a tooltip layer) is exactly that case. The check is a DOM-domain read on a session Erfana already holds, so it adds no surface beyond decision 2's domains and needs no exception to 025-NFR-001. A picked element that itself has `pointer-events: none` is now found as itself, so it is no longer reported as covered by the element under it.

**Residual risk.** The allow list no longer refuses `ignorePointerEventsNone: true`, so a coding mistake could put the topmost rule on the pick path; then a click-through overlay, not the element under it, would be outlined and picked. Unit tests pin each caller's rule (`pickHitTest.test.ts`, `captureFacts.test.ts`). An element that is fully transparent or invisible but still painted on top (`opacity: 0`, an empty positioned box) is reported as covering, as the engine's hit test sees it; the note is information for the agent and never changes what is sent. As before, only the centre of the box is tested, so an element covered elsewhere is not reported.

## Amendment 2026-11-05 (owner decision): the live outline is drawn by Erfana

**Found.** Decision 6 left the live outline to the engine: one `Overlay.highlightQuad`, which Chromium strokes as one line in one colour (a second quad replaces the first, and a fill is ruled out by Q2). One colour cannot hold 3:1 against every page – the accent falls to about 2.1:1 on a white page – so the live outline and the still image's two-tone outline looked different, and the live one could vanish (design note, Differences in the build).

**Decided (owner, 2026-11-05).** Erfana draws the live outline itself, outside the page, as the still image draws it: a 1px ink line just outside the element's border box, a 2px paper line inside its edge and a 1px ink line inside that – `--color-brand-black` and `--color-white`. The still image (`.erf-brw-still__outline` in `PickRow.css`) changes from accent to paper in the same arrangement, so both look identical.

- **Surface.** A borderless, transparent **child window** of the browser window, covering the visible page area, holding eight plain `View`s – four ink strips 4px thick, then four paper strips 2px thick over them. It has no `webContents`: no renderer process, no page, no script. Code: `src/main/services/browser/pick/pickBand.ts` (geometry, placement), `pickBandWindow.ts` (the window), `pickOutlineColours.ts` (the two tokens, resolved from `design-tokens.css` at build time and inlined as `__ERFANA_OUTLINE_INK__` / `__ERFANA_OUTLINE_PAPER__` – main has no hex of its own).
- **Input passes through.** `setIgnoreMouseEvents(true)` is set before the window is first shown; Electron documents that every mouse event in such a window "will be passed to the window below this window" (macOS, Windows, X11 and Wayland). The window is `focusable: false` and only ever shown with `showInactive()`, so it never takes keyboard focus either. Hover over the element's edge, clicks and the wheel reach the page.
- **Not in the capture.** `capturePage` of the page view copies what the page's process drew; another window is never part of it. The capture path still hides the band first, as the still image replaces it.
- **Placement.** The element's top-level box (`boxInView`, CSS px) times the page zoom, offset by the page view in the window and the window on the screen. The band is drawn again whenever the page view is placed again (tab switch, panel resize, width preset – `TabViewFrame.watchPlacement`) and when the window moves or comes back; it is hidden while the window is minimised or hidden and while the page is out of the window. A wheel event hides it; once the wheel has been still for 150 ms (`SCROLL_SETTLE_MS`) the box is read again and the band follows it.
- **Hidden** on every path the engine outline was: before a capture, at pick end and after the send flash, on navigation, when the element's frame goes, and with the tab (closed for good). A window blur does not hide it: the child window stays stacked with its parent, as the engine's outline stayed in the page.
- **`Overlay.highlightQuad` stays as a fallback only**, with its allow-list entries: where a child window cannot be placed – a Wayland compositor places top-level windows itself (`canPlaceBandWindow`: `--ozone-platform`, else `XDG_SESSION_TYPE` / `WAYLAND_DISPLAY`) – and when the band fails to open or draw. There the outline is the engine's one-colour accent, as before.

**Why.** An outline shows on any page only if one of its colours stands out by 3:1 from every page colour; two tones at least 9:1 apart always leave one of them 3:1 or more from any background, and ink on paper is 18.5:1. The engine strokes one colour; only Erfana can draw two. A surface outside the page keeps 025-NFR-001 – nothing of Erfana's enters the page.

**Not chosen.** Views inside the browser window (a `WebContentsView` strip, or a plain `View`): Electron 44 has no way to let a view pass the mouse through ([electron/electron#53841](https://github.com/electron/electron/pull/53841) is still open), so a strip over the page would take the mouse at its pixels; and a plain view's background is drawn beneath a page's native surface ([electron/electron#34329](https://github.com/electron/electron/issues/34329), inferred to hold for `WebContentsView`). This supersedes, for the live outline, the "transparent native view above the page" alternative below: the click-through window is chosen, and Wayland – the reason it was rejected – keeps the engine's outline.

**Residual risks.**

- *Pass-through is verified by Electron's documented contract and the unit tests that pin the window's options and the call order, not by real OS pointer input:* e2e input goes through `sendInputEvent` and CDP, which bypass the window system. A manual check on macOS, Windows and Linux X11 (hover the outline's edge, see the page's own hover react) is the remaining proof.
- *Hover latency (025-NFR-004, 50 ms at p95).* The band is drawn after one more read than the engine quad was (`boxInView` before drawing, where the quad went out first), and native view moves are cheap; the window itself moves only when the page area moves. Measured 2026-11-05 with the reworked `e2e/browser-pick-highlight.bench.ts` (pointer move to the band window's first presented frame): Linux in Docker under xvfb, 3 runs of 200 moves, p95 25.2–25.6 ms; the macOS run is in `docs/performance/browser-025-highlight.md`.
- *Placement lag.* A page that scrolls without a wheel event (keys, script, smooth-scroll after the settle) or changes zoom without a placement change leaves the band where the element was until the next mouse move. On Windows and Linux the window is moved after the parent's `move` event, so a window drag can show the band trailing for a frame.
- *Wayland detection is inferred* from the switch and the session variables; a wrong guess either keeps the engine's outline or places the band where the compositor puts it.
- *Forced colours.* The band draws its tokens, not the system colours; decision 6's forced-colours rule applies to the engine fallback only.
- *Design system.* The decided Focus card's Exceptions row for the element picker still names "a 2px accent ring with a 1px ink line on both sides" and "one colour" on the live page; updating it is the owner's call.

## Consequences

- No Erfana code in the page except fixed read functions run by CDP in an isolated world or, for React, in the main world – both main-driven (S-14 records it in the spec).
- The live highlight is an outline with no fill and no engine label (Q2); since the 2026-11-05 amendment Erfana draws it in ink and paper on a click-through child window, the same outline as the still image; the engine's one-colour outline is the Wayland fallback.
- `Overlay`, `DOM.getFrameOwner`, `DOM.getContentQuads` and `Emulation.setFocusEmulationEnabled` are experimental (`DOM.getNodeForLocation` is not); the probes of commit 8 stay as regression tests and run on every Electron update pull request.
- `Runtime.enable` is detectable by pages (a known automation tell), which can lower the odds of 025-FR-024's best-effort Google sign-in; accepted, since 025-FR-038 needs console events.
- Chromium's hung-renderer signal is suppressed while a debugger is attached (inferred); 025-FR-056 uses Erfana's probe.

## Alternatives considered

- **Isolated preload in every frame (ADR 0005 pattern)** – full control of the look, but Erfana code in every frame of every site, no preload in `about:blank` frames, and a page can fight or erase it. Rejected.
- **`Overlay.setInspectMode`** – swallows hover and confirms by itself. Rejected.
- **`Overlay.highlightNode` with fill, band and engine label** – gives a label next to the element but a fill the decided Focus card does not allow. Rejected by the owner (Q2, 2026-11-03) in favour of the outline-only highlight of decision 6.
- **A transparent native view above the page** – takes the mouse from the page; a click-through window cannot be positioned on Wayland. Rejected for the whole overlay; for the live outline alone a click-through child window is chosen by the [2026-11-05 amendment](#amendment-2026-11-05-owner-decision-the-live-outline-is-drawn-by-erfana), with the engine's outline kept on Wayland.

## Probe results (commit 8, 2026-11-03)

Electron 44.9.3, macOS 27.2 (Darwin 27.2.0, arm64), `e2e/browser-engine-probes.e2e.ts`, 5 runs each, all consistent. Playwright is attached as a second CDP client to every page in these runs. Recorded for the owner's acceptance decision. On 2026-11-03 the owner accepted this ADR and the decisions above were amended to match (decisions 2, 4 and 11 from these results; 6 and 7 from Q1 and Q2).

| Probe | Result | Bears on |
|---|---|---|
| Mouse coordinates, cross-site frame at an offset (CDP-routed input) | `before-mouse-event` fires on the **top** `webContents` with **frame-local** `x`/`y`; `globalX`/`globalY` minus the view's screen origin is the view point (within 1 px) | Decision 4 holds for offset frames; the "frame-local x/y" inference is confirmed |
| Mouse coordinates, transformed cross-site frame (rotate 12°, scale 0.8) | `x`/`y` frame-local; `globalX`/`globalY` are the frame's bounding-box origin plus the **untransformed** local point – 17.8 px from the pointer | Decision 4 does **not** hold for transformed frames: `globalX`/`globalY` cannot be used as-is there |
| `sendInputEvent` mouse events (the T2 harness) | `globalX`/`globalY` are 0, and they never reach a cross-site frame | Real-OS coordinates cannot be produced in e2e; OOPIF input tests need CDP `Input.dispatchMouseEvent` |
| `Overlay.setInspectMode` | The page gets no `mouseover`/`mousemove`/`mousedown`/`click`; the click becomes `Overlay.inspectNodeRequested` | Decision 5 confirmed |
| DevTools opened and closed with Erfana's session attached | **No detach**; commands answer while DevTools is open and after it closes | Decision 11: coexistence works; the Q5 fallback is not forced by detach |
| View closed with the session attached | `detach` reason `target closed`; at the event `isDestroyed()` is still `false` | Fixed after the probe: `target closed` while DevTools is closed now maps to cause `viewClosed` |
| Outer-HTML cut with `throwOnSideEffect: true` | Passes in the main world and the isolated world, full value, no exception | Decision 3 / 10 confirmed |
| `Overlay.highlightNode` in `capturePage` | Present (87 % of pixels in the box changed); gone after `hideHighlight` | § 6.1: hide the highlight before the capture |
| Failed requests, `Log` vs `Network` | Both: 500, 404, unresolvable host, CORS block; both skip a cancelled request. **Only `Network` reports a dedicated worker's failed request** | Decision 2: `Network` is needed for 025-FR-038's worker requests |
| `insertCSS('* { cursor: crosshair !important }', { cssOrigin: 'user' })` | Top document only; same-origin and cross-site frames keep `auto` | Decision 8: crosshair over frames needs S-11 |
| Cross-site frames with the tab-kind session attached | At first **never committed** (the tab loaded for ever). Cause: the child's `Runtime.runIfWaitingForDebugger` was sent inside Electron's synchronous `attachedToTarget` event, before Chromium began holding the navigation | Fixed in `cdp/`: the resume goes out on a later task (`RESUME_DELAY_MS = 0` on the injected clock); the probe now passes |
