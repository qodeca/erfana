# ADR 0013: One freshness capability follows every open file

- **Status**: accepted (owner decisions on scope, 2026-11; recorded 2026-11-18)
- **Date**: 2026-11-18
- **Deciders**: Marcin Obel (owner), Claude Code
- **Related**: [#478](https://github.com/qodeca/erfana/issues/478) · #70, #252, #450, #464 (the earlier fixes this replaces the shape of) · [File watching](../file-watching/README.md) · [Technical debt #72](../technical-debt.md#72-known-limits-and-accepted-trade-offs-from-478-2026-11)

## Context

An open tab sometimes never showed a change made to its file by an agent, git or another editor, and in most cases it said nothing. The tabs that show file content – the Markdown editor, the image viewer, the HTML preview, Markdown preview images and the comments drawer – each owned their own way to start a watch, catch up with the disk and react to a change. The v0.24.1 fixes for #70, #252, #450 and #464 patched single paths; the problem stayed because it had three shared causes:

1. **Starting a watch and catching up with the disk were separate steps**, owned by each tab type. A write in between was lost (open while an agent writes, Reload, a deleted file coming back).
2. **The watch layer could stop, pause or lose a tab's watch without telling the tab** – a failed project switch, a window reload during a save, a deleted-and-recreated folder, a wake from sleep, a full watch cap.
3. **Nothing compared a tab with the disk again** after a missed event, so every other cause stayed visible until the tab was closed.

On top of that came path spellings the lexical entry check refused (case, 8.3 names, junctions, symlinks), network and WSL volumes whose change events are unreliable, a 300 ms write-finish wait plus a 300 ms debounce that made an editor tab update about 0.7 s after the last write, and a guide that described Dismiss, the re-arm and the delay wrongly.

## Decision

**One shared capability, built once; each tab type plugs in with one adapter.** The issue's acceptance criteria are the contract; these are the choices that shape the code.

1. **The core is plain TypeScript in `src/shared/freshness/`** with no Electron, Node, DOM or React import (`freshnessPurity.test.ts` enforces it). It runs in the renderer (editor, image, Markdown images) and in main (HTML preview, comments), and against a fake disk and a fake clock in tests.
2. **One tracker per tab, one state object.** `FreshnessTracker` holds `{ watch, content }` – `watch` is `active` (full or limited), `queued` or `stopped(reason)`; `content` is `fresh`, `changed` (held or deferred), `deleted` or `unavailable(reason)`. Every notice and every Reload reads that object only. An adapter supplies an update rule (`read`, `readNow`, `apply`, `onState`) and the core never asks which tab type it serves.
3. **Starting to follow always ends with a catch-up.** A subscribe answers after the native watcher is ready, with a stamp read after that. Open, Reload, file-back, restart and a slot freeing all compare that stamp with the tab's and read when they differ. A change that arrives before `started` is buffered and folded into the catch-up.
4. **A safety net compares the tab with the disk** on tab shown, window focus, power resume, after a save and, for a limited volume, every 2 s while the tab is visible. A check probes against the last stamp and does nothing when the content is the same, so a focus change never reloads, re-renders or moves the cursor.
5. **A stamp is `size`, `mtimeMs`, `ctimeMs`, `ino` and a SHA-256** (files over 16 MiB are compared by stat only). "Same content" is equal size and hash, so a copy that keeps the modified time is caught and a touch-only write is silent. The hash goes through one cache (256 entries, one hash in flight per path).
6. **`FileWatcherService` is the only watch layer, for every consumer.** Subscriptions are keyed by owner and a fresh `watchId` per subscribe, so a reload, a file-back and a restart cannot be confused with an old watch. An owner is a window (with a page generation) or an in-process owner (the HTML preview, the comment service). Caps are buckets in profile data – `tabs` 100, `preview` 16 per owner and 64 in all, `comments` 64, `dependent` 8 per owner group and 32 in all – counted from the profile main resolves, never from a number the renderer sends. A subscribe past a cap waits in a first-in, first-out line (200 per bucket) and gets `started` when a slot frees.
7. **`armWatch` is the one place a native watcher is created or re-created** – subscribe, the atomic-save re-arm, the error re-arm, the health round, waitlist promotion, resume after a project-switch suspend and the wake re-arm. It first re-runs `realpath` and the inside-the-project check, then requires a regular file. Watches are keyed by the real path (case-folded on Windows and macOS, NFC on macOS), which fixes 8.3 names, junctions, drive-letter case and Unicode form.
8. **Every end is told to the tab.** The project switch suspends watchers just before the commit and ends every old subscription after it (a failed open resumes them); a window reload drops that window's subscriptions on navigation; a power resume re-arms every watch, runs a health round and asks every tracker to check. The health round (every 2 s, one `lstat` at a time) compares each watch's `(dev, ino, birthtime)` with the one it was armed on, because a deleted-and-recreated folder can reach the project watcher as one `change`.
9. **The port is split.** `FreshnessSource` (subscribe, unsubscribe, probe, read, events) serves every tracker; `PausableSource` (pause, resume, write) is reached only through the editor's save add-on. An import test keeps the read-only adapters away from it.
10. **Own-save identity is decided in main, from the stamp.** `file-watch:writeText` writes through `atomicWriteText`; an autosave sends the tab's last stamp as `expectedStamp`, and main checks it stat-first (an exact stat match is "unchanged" with no hash; only a mismatch hashes) right before the rename, again before each rename retry and before an in-place write. If the file changed, nothing is written and the tab shows the "Not saved" conflict. An explicit Cmd/Ctrl+S, **Restore file** and a save in the conflict state send no stamp and write unconditionally, as before. The save pauses only its own subscription, so another tab or window on the same file hears the save as an outside change.
11. **One timing source.** `src/shared/freshness/timingProfiles.ts` holds the profiles (editor and image settle 75 ms, poll 25 ms, throttle 250 ms; preview settle 50 ms with its 30 ms coalesce; read retries after 100, 300 and 900 ms; delete confirmed after 500 ms; deleted-file probe 0.5 s backing off to 2 s) and the limits. The IPC profile enum is built from its keys. The 300 ms main-side debounce is gone; the throttle is leading plus trailing, so the first change shows at once and a burst updates every 250 ms.
12. **A change is read only after it settles.** An event read, made right after the write gate, reads at once and settles only if that read finds the file moving; every other read waits for two matching probes – one settle apart, the same size and modified time – then reads with a before-and-after check on the same descriptor. A change the write gate emits at its 5 s cap is marked forced and still waits to settle before it reads. A file that does not hold still within the 5 s cap is not read: the tab shows 'cannot be read right now' until it does.
13. **HTML preview sub-files stay on the coordinator's pool**, routed through the shared layer; its 30 ms coalesce is their burst control. Each sub-file has its own tracker on the pool's shared owner. The preview keeps its faster profile.
14. **Content that cannot be shown makes the editor read-only.** Too large (over 10 MiB, on open and on refresh), binary, UTF-16 or UTF-32, or unreadable: the tab keeps what it showed, says so, and `shouldAutosave` returns false, as for a conflict or a deleted file. Reload tries again for too-large and unreadable.
15. **One notice per panel**, by priority deleted, conflict, content unavailable, watch stopped, watch queued, limited, with one always-mounted `role="status"` region that announces only in the active tab.
16. **Dismiss on the conflict bar stays Keep My Version** (owner decision): autosave writes the local text over the outside change about 2 s later. The guide now says so.

## Consequences

- One place decides what a tab shows, how long it waits and when it re-checks; adding a tab type is one adapter plus the shared contract suite (`src/shared/freshness/__test__/freshnessContract.ts`, run by five adapter test files).
- An editor or image tab is expected to update about 130–200 ms after a write (gate 75–100 ms, read and render the rest). `e2e/file-freshness-latency.timing.e2e.ts` asserts p50 at most 250 ms and p95 at most 400 ms (Windows, run locally).
- **Known limit – the save write gap.** There is no file lock, so an outside write that lands between the last check and the commit – one `stat` plus one `rename` – is overwritten by the autosave. The check is re-run before every rename retry and every in-place write, which keeps the gap to two system calls. A lock was rejected as not portable.
- **Known limit – the stat after the rename.** `written` carries a `stat` of the final path taken after the commit, plus the SHA-256 of the bytes written. A write that lands between the rename and that `stat` is therefore not adopted as ours: `probeFile` always hashes the real file and `textWrite` does not seed the hash cache, so the check that runs after every save (`check('save')`, which the tracker re-runs if another check was in flight) finds a hash that differs from the one we wrote and shows the write. Editor files are at most 10 MiB, under the 16 MiB hashing cap, so they are always hashed.
- **Known limit – the atomic-save re-arm reads without the settle wait.** After a temp-file-and-rename save, the re-arm reads the new file at once; it is not marked forced. A writer that deletes the file and then streams the new one slowly can briefly show a partial version; its next change, held by the write gate, corrects it. Settling here would add about 75 ms to every atomic save – the main agent write path – on a latency margin of about 20 ms. A follow-up idea: settle only when a second stat about 25 ms later shows the size moved.
- **Known limit – a long pause mid-write.** The settle wait is 75 ms. A writer that pauses longer than that in the middle of a file can still show a partial version for a moment; the before-and-after check on the read and the 5 s gate cap narrow it, and the burst gate (`e2e/file-freshness-burst.timing.e2e.ts`) names the longest writer pause when it fails.
- **Known limit – 8.3 expansion before the full check.** A drive-letter path that spells the project folder with 8.3 short names is expanded with one `realpath` before the inside-the-project check (`lexicalPrecheck.ts`). It runs only for a path the renderer sent with a drive letter, on the drive of the project's real root, and never when that real root is a share. Two cases stay open: a project on a mapped drive whose real root keeps its drive letter lets a short-name path outside the project be resolved on that same share (a timing-only existence probe, no new host), and a folder symlink on that drive that points at a UNC path would be followed (planting one needs admin rights or Developer Mode).
- **Known limit – no focus return (F36).** When a notice closes, focus is not returned to the editor or image viewer. The old notices behaved the same and no criterion requires it; keyboard users click back into the content.
- **Accepted cost – HTML preview speed.** The settle wait makes the HTML preview about 14 ms slower than before (median p50 about 152 ms over 20 Windows runs, against 138 ms at S0). The issue asked it to keep its speed; the owner accepted the cost on 2026-11-19, and the timing gate holds the preview to the measured level so any further slowdown still fails.
- **Known limit – volumes.** macOS reports every volume as local (`volumeKind.ts`), so a network share there gets no limited notice. On Windows a mapped drive letter is caught only when `realpath` resolves it to its UNC form. Network drives and `\\wsl$` are checked by hand, not by an automated test.
- The remaining accepted trade-offs and their rows are in [Technical debt #72](../technical-debt.md#72-known-limits-and-accepted-trade-offs-from-478-2026-11).

## Alternatives considered

- **Patch each tab type** – the approach of #70, #252, #450 and #464; it left the three shared causes in place. Rejected.
- **Freshness in main only** – the editor's "edited or not" and its cursor live in the renderer, and the renderer-side tracker is what a notice reads. Main keeps the disk helpers, the watch layer and the in-process owners; the core runs on both sides. Rejected as the single home.
- **Counting subscriptions per path** (the old `SubscriberCounter`) – a pause or release by one tab touched another and a reload leaked slots. Per-subscription ids replaced it.
- **A pure debounce instead of settle-before-read** – a writer that pauses mid-file shows a partial file after any fixed delay. Rejected for the settle check plus read verification.
- **Hashing in the renderer** – the renderer hashes text, main hashes bytes, so BOM and line endings give different hashes and an own save looks foreign. Rejected; the stamp is main's.
- **A file lock for own saves** – not portable across Windows, macOS and Linux and visible to the agent writing the file. Rejected; the write gap above is accepted instead.
