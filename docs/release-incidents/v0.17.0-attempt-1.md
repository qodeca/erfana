## Root cause: tag-push race against `checks.yml` completion time

`checks.yml` triggers on `on: push` with no ref filter — it fires independently for every push to every branch **and every tag**. The tagged commit `ba6e455a0299de32bb951efb89b9690df84952ca` (`chore(release): bump version to 0.17.0`) was pushed through develop → main → tag in rapid succession, producing three separate `checks.yml` runs against the same `head_sha`:

| Run | Ref | Started | Duration | Status at 15:38:03Z (query time) |
|---|---|---|---|---|
| 31264834993 | `develop` | 15:35:22Z | 3m22s (→ ~15:38:44Z) | still `in_progress` |
| 31264930955 | `main` | 15:37:40Z | ~1m50s+ | still `in_progress` |
| 31264941009 | `v0.17.0` (tag) | 15:37:56Z | ~1m34s+ | still `in_progress` |

`release.yml`'s `prepare` job checked out the tag and ran its "Assert checks.yml has a green run" gate at **15:38:03Z** — 7 seconds after the tag-triggered `checks.yml` run even started, and ~41 seconds before the earliest (develop) run reached `completed`/`success`. The gate's query (`?head_sha=...&status=success`) correctly found nothing, because at that instant nothing matching had finished yet. All three runs went on to pass (confirmed after the fact via `gh run list`), so this is **not** a real CI regression — it's a timing race baked into the release flow: nothing in `release.yml` or the operator's tag-push sequence waits for `checks.yml` to actually finish on the tag ref (or any ref at that SHA) before `release.yml`'s own gate evaluates.

The `main` branch protection model (direct push, no PR gate) makes this race easy to hit: `develop → main → tag` can happen within the ~2–3 minutes it takes `checks.yml` to run, so the tag push (which fires `release.yml` immediately) routinely lands before any `checks.yml` run for that SHA has completed.

## Cleanup-job failure: by design, not a second bug

The `Cleanup on failure` job (job id `93121478087`) also shows `conclusion: failure`, and initial triage flagged it as a possibly-independent bug. It is not. Reading `.github/workflows/release.yml`:

```yaml
  cleanup:
    name: Cleanup on failure
    # Fires on any failure/cancellation of prepare or any build leg. Runs
    # even if the whole thing was cancelled (always()) so leaked drafts
    # don't survive. Final `exit 1` turns the workflow red so operators
    # aren't fooled by a green cleanup.
    ...
      - name: Delete draft release (if any)
        run: |
          if gh release view "$TAG" >/dev/null 2>&1; then
            gh release delete "$TAG" --yes --cleanup-tag=false
          fi
      - name: Fail the workflow
        run: exit 1
```

The `Delete draft release (if any)` step completed cleanly (no draft existed — `prepare` failed before the "Create draft release" step ran, so there was nothing to delete). The job's **second** step, literally named "Fail the workflow", unconditionally runs `exit 1` — that's the entire step. Its only purpose is to force the `cleanup` job itself to report red, per the comment: "Final `exit 1` turns the workflow red so operators aren't fooled by a green cleanup." So `Cleanup on failure` = `failure` here is expected, correct behavior, not a defect. No new cookbook row or code fix is needed for this half of the incident.

## Is the tag burned?

**No.** `prepare` failed before any artifact existed, so nothing was burned: `prepare` failed at the `green_run` gate, before "Create draft release" ran — no draft was ever created (confirmed: `Delete draft release (if any)` in `cleanup` found nothing to delete), and no signing/notarization touched any artifact. This is categorically different from the v0.16.2 case (§ Fix applied) where a matrix leg failed *after* a draft/signed bytes existed and the version was burned.
