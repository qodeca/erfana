Erfana design system / Foundations / Colours

Colours

proposed reviewed 2026-08-31

Erfana is dark mode only, and that is now true rather than aspirational: the renderer contains 0 prefers-color-scheme blocks. Every colour on screen is a token from design-tokens.css, and a pairing is judged by its contrast on the surface it sits on, never on its own.

It shipped one until recently – thirty lines restyling the Mermaid toolbar for a light OS. Not dead code: color-scheme: dark does not change what that query reports, because the query follows the operating system. It was a second, unmaintained theme that real users saw in exactly one component. It was deleted rather than documented, because a card reading "dark only, except there" writes a bug down as a rule.

The rules

  1. Text clears 4.5:1 on the surface it sits on – WCAG 2.2 SC 1.4.3 Contrast (Minimum), level AA. Read the pair off the text matrix, never the colour off a swatch.
  2. Large text may drop to 3:1, as SC 1.4.3 allows: 24px and up at regular weight, or about 18.66px and up when bold. In Erfana only --text-2xl at 20px qualifies, and only when it is bold. Everything smaller – which is nearly all UI text – stays at 4.5:1. The text matrix below judges every pair at 4.5:1; a bold --text-2xl pair that reads "fail" there passes if it clears 3:1.
  3. Non-text parts clear 3:1 against what is next to them – SC 1.4.11 Non-text Contrast, level AA: an icon that carries meaning, a control's boundary, a focus ring, a selected-state edge, a meter's fill, a status dot. A fill that only decorates is not held to it.
  4. --color-text-muted is decoration and disabled only. A disabled control is exempt from both criteria; a divider glyph or a background ornament carries no information. Anything a person has to read or recognise – a label, a hint, an icon that means something – takes --color-text-tertiary or brighter.
  5. State that carries information is never a fill alone. Hover and pressed may be a wash. Selected and drop-target carry an edge that clears 3:1, because a wash measures under 1.5:1 and a forced-colours theme removes it entirely (Forced colours).
  6. On a violet fill, the foreground is dark. --color-text-on-accent, never white, on every violet state (below).
  7. A data colour is never the only signal. Git status carries a letter, the context meter carries its percentage, and an error carries its words.
Nothing on this page is typed by hand. Every swatch is painted with var(--token) from the synced copy of the app's design-tokens.css. Every resolved value and every contrast ratio is baked into this page by npm run design from the shipping token file, across all 110 colour tokens the app declares – the page itself runs no JavaScript.

What that guarantees is narrow and worth stating exactly: npm run design -- --check fails in CI when the token copy, a resolved value or a ratio here disagrees with the app, and the ownership guard fails when a colour token is added to the app and not to this page.

Text

Two criteria, two bars – and they are not interchangeable. SC 1.4.3 Contrast (Minimum) asks 4.5:1 of text, or 3:1 of large text. SC 1.4.11 Non-text Contrast asks 3:1 of a control's visual boundary, its states and meaningful graphics; it says nothing about text.

--color-text-secondary reaches only 3.72:1 on a panel and 4.15:1 on the sidebar and tree. The same token on the app background clears 4.5:1, which is why this card judges a pair, never a colour on its own: secondary is a text colour for the app background only. On a panel or the sidebar, a label takes --color-text-tertiary.

--color-text-muted is not a text colour at all. It measures 2.69:1 on a panel, 3.00:1 on the sidebar, 2.72:1 on a hovered row and 2.02:1 on a selected one – under 4.5:1 everywhere, and under 3:1 on three of the four, so it fails a meaningful icon too. That is why it is decoration and disabled only (rule 4).

Reading the failures:

  • --color-text-secondary passes on the app background and the preview surface only.
  • --color-link-visited fails on panels and on every row state – which is why the documentation keeps visited links in the link colour, and why the app should too.
  • The selected row is the hardest surface. Placeholder, error and warning text all fail there. A status shown inside a selected row is carried by its icon and words, or by --color-error-text-hint, which passes.
  • Placeholder text also fails in a warning box and on the danger hover: a field does not sit there.

Text on a violet fill

The brand violet is a light tint, so anything drawn on it – a primary button's label, an active toggle's icon, a badge count – is dark, not white. --color-text-on-accent (brand black) measures 8.40:1 on the resting fill; --color-white measures only 2.20:1, under both the 4.5:1 text bar and the 3:1 icon bar. --color-btn-primary-text is the button alias of it. accentFill.contrast.test.ts holds every violet fill in the renderer to 4.5:1.

The colour half of a state. The opacity steps themselves are decided on the Surfaces card; this card decides which colour token each state paints, and what it must clear. Each frame is a sidebar row (--color-bg-tertiary).

Data colours

Git status

The tree draws a status three ways: a small dot on a folder, a coloured file name, and a letter badge. The dot takes the base token, the name and the badge the -light variant. The letter is what makes the state readable without colour (#95 is the folder case, where only the dot exists).

--color-git-renamed (brand indigo) is never a foreground. It is a dark blue on a dark surface and fails the 3:1 a meaningful dot needs. Anything renamed that has to be seen – a name, a count, a dot – takes --color-git-renamed-light. The folder dot still paints the base token today, so a renamed folder's dot is the one row above that fails; see open defects.

Context meter

The terminal's Claude Code context meter is a traffic light, and its percentage text repeats the band so colour is never alone. The safe band is a true green, --color-context-safe, because Qodeca lime reads as yellow beside the amber band – the same collision named under open defects.

What ships differs: ClaudeStatusBar.css paints amber and red with the retired --color-warning-bright (text 6.39:1 · pass) and --color-error-bright (text 4.95:1 · pass). Both pass; the change is consolidation, not repair. It is one of the retired-token sites in the README defects.

Open defects in the palette

Named here so a design does not lean on them. Each is also a row in the README's defects list.

Success and warning collide

success
warning

--color-success is Qodeca lime and --color-warning an amber-yellow: two yellows, 1.74:1 apart. Side by side a person with full colour vision can tell them apart; in a toast seen alone, or with a red–green deficiency, they read as the same message. Until the palette is changed, a success and a warning must differ by icon and words, never by colour.

There is no info tone

info
accent
link

--color-info is the brand violet: 1.00:1 from the accent, the link and the focus ring. There is no --color-info-bg or --color-info-border, so an info banner borrows the accent and looks like a selected or focused thing. Until an info tone exists, an info message is drawn neutral (panel fill, default border, an info icon) rather than violet.

The renamed folder dot

The folder dot paints --color-git-renamed (1.92:1 · fail on the sidebar). It should take --color-git-renamed-light, which the file name already uses.

Every colour token

Grouped as design-tokens.css groups them. Text-like tokens are judged against 4.5:1, everything else against the 3:1 non-text bar. Fills and washes – backgrounds, -muted tints, drag highlights – carry no verdict: they are surfaces, so the figure is their step from the panel and from the app background, which is what tells you whether two surfaces read as different.

Exceptions

Where the shipping component departs from this card, with the reason. An undocumented deviation is a bug; a documented one is a decision. Each row has a deviates: marker at the site. For the screenshot overlay the bypass is colour, type size and offsets – no tokens reach the window; corners are still 0.

WhereThe cardThe component, and why
Screenshot overlay hint (.screenshot-overlay-hint) Every colour is a token. Literal white text on a 65% black scrim. The area-select overlay is its own transparent window and does not load design-tokens.css (#164); it paints over arbitrary desktop content, not an app surface, so the scrim is what guarantees the contrast. Screenshot overlay size readout (.screenshot-overlay-size) Every colour is a token. Same treatment as the hint, at a smaller size. The bypass covers colour, type size and offsets – no tokens reach the window; corners are still 0, like the rest of the app.
HTML-preview comment overlay (overlayStyles.ts, in the previewed page) Every colour is a token. Literal values, resolved from the tokens by main and sent in commentState.theme (commentOverlayTheme.ts, pinned to design-tokens.css by a test). The overlay is drawn inside the page, where a var() would read the page's own properties. The mapping is drawn in the proposed Comment overlay card.
