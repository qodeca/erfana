Theme

proposed not yet reviewed

Erfana is dark only. There is one theme, it is declared once (color-scheme: dark on :root), and nothing queries the system's light or dark preference. Selection is a per-surface decision: data a reader would copy is selectable, chrome they click or drag is not, and components that own their selection are left alone.

Dark only

No prefers-color-scheme query, ever. A query is a promise of a second theme, and a second theme is a second design system to keep in step: every contrast ratio on every card would need a light twin. The renderer ships 0 prefers-color-scheme blocks today; keep it there.

color-scheme: dark is what makes native parts dark. It is set once, on :root in design-tokens.css. Without it Chromium paints a checkbox as a white square and every scrollbar light – the token file's comment records the white checkbox that prompted it. Do not set it again per component, and never set it to light.

The light surfaces that are not a theme

Three places show light pixels on purpose. None is a light mode; each is content, not chrome.

The screenshot overlay is the third exception: it paints over arbitrary desktop content, so its colours are fixed rather than themed – recorded on the Colours card.

Text selection

dockview-core sets user-select: none on panel chrome, and it inherits into everything inside a panel. So without a deliberate override, text in a panel is silently not selectable – which once broke the Markdown preview's prompt menu (Explain, Modify, Ask, Visualize), because it reads the selection and did nothing when it was empty.

Try it

Decision rule. Would a reader reasonably want to copy this text? Yes – make it selectable. A clickable or draggable label acting as chrome – leave it none. A component that owns its selection – do not interfere.

Scope rule. Opt in on the element that holds the data, not on a clickable or draggable ancestor: a row with both cursor: pointer and user-select: text makes drag-to-select fight click-to-pick. The file picker is the worked example – the override is on .file-picker-filename and .file-picker-path, not on .file-picker-item. Use container scope (.dialog-body, .markdown-preview-content) only when nothing inside it is interactive; when a container mixes data and buttons (the welcome screen's recent-project rows), list the data selectors one by one.

Where it lives. One grouped rule in src/renderer/src/styles/utilities.css, with a row for each selector in userSelect.audit.test.ts. The only exceptions are the CSS-module surfaces in ImageViewerPanel.module.css, whose hashed class names a global selector cannot match. The unprefixed property is enough – the app runs on Chromium.

Cascade assumption. The overrides win because app stylesheets load after dockview-core/dist/styles/dockview.css. Do not change the CSS import order without re-running the audit test.

Proposed: one selection colour

The app sets no ::selection rule, so selected text takes the operating system's accent – blue on one Mac, pink on another, something else on Windows – and the terminal draws its own. Proposed: a single rule in utilities.css, ::selection { background: var(--color-bg-selected); color: var(--color-text-emphasis); }, the same violet wash that marks a selected row. The selectable samples above use it.

Exceptions

None recorded. A shipping component that departs from this card carries a deviates: marker at the site and gets a row here, naming the file.

Defects this card names

  • No app-wide selection colour. No renderer stylesheet declares ::selection; selection follows the OS accent, and the terminal uses its own hex (already in the README's terminal-palette row).
  • The selection-policy count disagrees with itself. utilities.css says two CSS-module surfaces declare the rule in place; docs/ui-style-guide.md says four. The card names the file, not a count.
