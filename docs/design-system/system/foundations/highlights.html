Text highlights

proposed not yet reviewed

A highlight paints a range of text without changing it. Erfana has five, plus the reader's own selection. Each has its own shape, not only its own colour: Find is a lime fill with no bar, a comment mark is a violet fill with a solid bar under it, the open thread's mark doubles that bar, and changed words get a dashed bar with no fill. Find paints last of Erfana's highlights, so a hit is never hidden under a mark. A comment mark never uses --color-bg-selected, so it never reads as a selection, and it always has a fill, so it never reads as a link. In forced colours, marks and hits use Mark; Highlight is kept for the selection.

Paint order

Bottom to top. Where two ranges overlap, the higher one's fill covers the lower one's. Shipping code sets this with the priority of each Highlight object; Find sets none today, so its current hit sits above its results only because it is registered second.

The selection is not in Erfana's ladder: the browser paints it above every custom highlight (CSS Pseudo-Elements level 4, highlight overlays). This is from the specification and has not been checked against Erfana's Chromium. That is why its look must differ from all five rather than sit above or below them by choice. Find in the HTML preview is Chromium's native findInPage, which paints its own colours; Erfana styles Find only in the Markdown preview.

Tokens

Proposed – not in the app yet

The comment screens already read them, with the card's 35% color-mix as the fallback until they ship: docs/designs/comments/selection-comments/selection.css, docs/designs/comments/markdown-comments/markdown-comments.css and docs/designs/comments/comments-v2/comments-v2.css. Every highlight, on every ground

Static frames. Spans stand in for ::highlight() ranges, using only the properties that pseudo-element allows. The white and grey grounds are HTML pages; the dark ground is the Markdown preview. The link on the light grounds is drawn in the bar's own hue on purpose – the worst case. Find on the light grounds is drawn in lime only to set the marks against it: an HTML page gets Chromium's own find colours, and the lime-muted fill would all but vanish on white (see the contrast table).

Where two meet

Contrast

Text on a fill needs 4.5:1; a bar that carries a mark on its own needs 3:1 against the ground (WCAG 1.4.11). Translucent fills are measured over the ground they sit on.

The floor row is a bound, not the value: on a light ground a 35% fill is lighter than the full violet, so dark text on the real mark is at least that ratio. On the dark ground no such bound exists, which is why that row waits for the token. The violet bar fails on white, which is why light grounds take the deep violet.

Forced colours

A Windows contrast theme drops every colour above. Each highlight keeps a shape and takes a system colour by meaning: Mark and MarkText for search hits and comment marks, Highlight and HighlightText for the selection only. The bars stay, repainted in CanvasText. The current hit swaps Mark and MarkText, so it differs from the other hits by more than a fill. See Forced colours.

@media (forced-colors: active) {
  ::highlight(search-results)       { background-color: Mark; color: MarkText; }
  ::highlight(search-current)       { background-color: MarkText; color: Mark; }
  ::highlight(erf-comment),
  ::highlight(erf-comment-active)   { background-color: Mark; color: MarkText; text-decoration-color: CanvasText; }
  ::highlight(erf-comment-changed)  { text-decoration-color: CanvasText; }
  ::selection                       { background-color: Highlight; color: HighlightText; }
}

Rules for a new highlight

  • Build it from background-color, color and text-decoration only – the properties ::highlight() allows – so the same look works in the overlay and in the Custom Highlight API.
  • Give it a shape that differs from every highlight above: fill or none, bar or none, bar style.
  • Set its priority below Find.
  • A highlight is paint only; a screen reader hears nothing. What it marks must also be reachable by a control with a name (for comments, the thread's own button).

Open defects

  1. Text on the 35% mark over the dark preview is not baked. The contrast bake reads tokens only; it needs either --color-comment-mark in design-tokens.css or a mix form in the contrast spec.
  2. The proposed ::selection colour for the preview is not set in MarkdownPreview.css, so the preview still paints the browser's default selection.
  3. Find sets no priority; once comment marks ship, Find must set one above them.
  4. How Chromium layers a lower highlight's bar under a higher one's fill is drawn, not checked.
