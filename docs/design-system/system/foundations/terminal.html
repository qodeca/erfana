Terminal and code colours

proposed not yet reviewed

The terminal is the one surface whose colours do not come from design-tokens.css: xterm.js takes a JavaScript theme object, and today that object is literal hex. The direction: every colour the terminal paints becomes a --color-terminal-* token, read into the xterm theme from the computed style, and there is one theme object, not two. Until then this card draws what ships – its colours and its size are generated from XTERM_OPTIONS by npm run design – and labels every value that is not a token.

The rules

  1. A colour the terminal paints is a token or a named defect. Today the theme object is the source: xterm's WebGL renderer paints from it and never reads CSS. TerminalPanel.css names tokens for the background, the cursor and the scrollbar, but those reach the screen only in xterm's DOM fallback, used when WebGL is unavailable. Until the theme reads the tokens, each such value must equal its token.
  2. The focused cursor is a block in the cursor colour with its character in black. Unfocused, xterm draws the cursor as an outline (its default inactive style), in the same colour. It is the only thing in the terminal that says where typing goes, so it is held to 3:1 against the background, and the character under the block to 4.5:1 against the cursor.
  3. The terminal scrollbar is the app scrollbar. It takes --scrollbar-thumb and --scrollbar-thumb-hover, not a separate grey ramp.
  4. Program output keeps its own colours, and the palette clears a bar. The ANSI palette is the program's choice of meaning; Erfana picks the 16 values, not which one a program uses. So the palette is judged as a set: every ANSI colour except black clears 4.5:1 on the terminal background, and each bright colour is brighter than its normal twin. Today red, blue and bright black fail the bar – see the palette.
  5. Code in the preview takes the --color-syntax-* tokens, and every one clears 4.5:1 on each surface code sits on. That is true today for inline code and front matter in the preview. The direction for the editor is the same three tokens; today it uses only --color-syntax-string, for inline code, and Monaco's own theme colours everything else.

Named defects

  • Two theme objects. TERMINAL_THEME in terminalPanel.logic.ts and XTERM_OPTIONS.theme in useXtermSession.ts carry the same palette twice. Only the second ships; the first also carries scrollbar colours that are never applied. Until one is deleted, npm run design -- --check fails when the two disagree.
  • Literal palette. The default text, the selection and the 16 ANSI colours are hex, so no token change reaches them; their ratios are measured from the literals above.
  • Tokens that do not reach the screen. The WebGL renderer paints the background and the cursor from the theme object, so the --color-black and --color-cursor overrides in TerminalPanel.css act only in the DOM fallback. They agree with the literals today by coincidence of value, not by construction.
  • Palette under the bar. red, blue and bright black fall under 4.5:1 on the terminal background (rule 4).
  • Scrollbar hover. --color-gray-600 in the terminal against --scrollbar-thumb-hover everywhere else.
  • Header border. TerminalPanel.css draws the header's bottom border with a literal translucent white instead of --color-border-default.

Exceptions

None recorded. A shipping component that departs from this card carries a deviates: marker at the site and gets a row here, naming the file.
