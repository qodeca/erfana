Focus and keyboard

decided reviewed 2026-10-28

One ring: a 2px solid outline in --color-border-focus, offset 2px outward, shown on :focus-visible. It goes inset only inside a scroller, never on a violet, lime or danger fill, and nothing on screen may cover it. Tab through this page – the live rings below are the real one; the frames further down draw the states you cannot tab to.

Why one ring. The app used to ship three focus rings: a 1px outline on tabs and the activity bar, a 2px outline in dialogs and toasts, and a 3px soft glow on inputs. That was not a style choice, it was drift.

The two numbers come from two different criteria. SC 1.4.11 Non-text Contrast (AA) asks a focus indicator for 3:1 against what is next to it. SC 2.4.13 Focus Appearance (AAA) asks for an indicator at least as large as a 2px perimeter, changing contrast by at least 3:1. The 1px ring fails the area half of 2.4.13; the 2px ring meets both, so 2px is the floor here. SC 2.4.11 Focus Not Obscured is a third, separate rule – about the ring being hidden, not about its size – and has its own section.

Every renderer stylesheet is held to this by focusRing.audit.test.ts (width and offset of every drawn ring) and by npm run lint:css (--shadow-focus is banned in src/ as well as here).

The ring

default outline: 2px solid var(--color-border-focus), offset 2px – 6.23:1 against a panel, clear of the 3:1 that SC 1.4.11 requires of a focus indicator.
inside a list
Same ring, offset inward. An outward ring gets sliced off by the scroll container. This is the only permitted variation.

The ring on every kind of control

Static frames: the ring drawn as it looks on focus, so each case can be checked without a keyboard. The ratio under each frame is the ring against what it actually touches.

Rings on a filled control

Never draw an inset ring on a violet, lime or danger fill. The ring is the brand violet. On a violet fill an inset ring measures 1.00:1 · fail – it is not there. On lime it measures 1.66:1 · fail, and on the danger red 2.49:1 · fail.

The alternative is always one of two: the ring goes outward, across a 2px gap of the surface colour, or – where outward would be clipped – the control keeps a transparent border and the ring is drawn inward into that border (the inner gap), so it still lands outside the fill. Both keep the ring on the surface, where it measures what the frames above show.

Focus not obscured

SC 2.4.11 Focus Not Obscured (Minimum), level AA: when something takes focus, it may not be entirely hidden by content the author put on top – a sticky header, a docked toolbar, a toast. (SC 2.4.12, AAA, asks that no part is hidden.) Erfana holds itself to the AAA form: no part of the focused element may be hidden. This is binding (owner decision, 2026-10-28).

The rule: a scroll container with a sticky header sets scroll-padding-top to the header's height (var(--header-height)), and one with a sticky footer sets scroll-padding-bottom, so a row scrolled into view by the keyboard stops below the header instead of under it. A toast or floating panel never opens over the element that has focus; if it must cover that area, it moves.

The same rule, for things that open from a trigger. A tooltip, toggletip, popover or menu never covers the focused element. It closes when focus leaves its trigger, and a hover tooltip hides when keyboard focus moves to an element underneath it. This extends the binding rule above to these surfaces; it does not reopen it. The surfaces themselves are on the Tooltip and Menu cards. 
.erf-scroller { overflow-y: auto; scroll-padding-top: var(--header-height); }

Two rules that are not negotiable

1 · Use :focus-visible, never bare :focus. Bare :focus paints the ring after a mouse click too, which looks broken, which is what makes people delete it. :focus-visible shows it to keyboard users only, so nobody wants it gone.
2 · outline: none is only allowed with a replacement on the very next line. Some panels in Erfana can be reached with Tab and show nothing at all, because someone wrote outline: none; /* Remove focus outline */ and stopped there. A keyboard user lands in the editor and has no idea. If an element takes focus, something must change on screen.

4 stylesheets remove an outline without declaring a :focus-visible rule anywhere in the same file. That is a signal, not a verdict – a few of them replace the ring with a box-shadow or sit on an element nothing can focus. It is the list worth reading, not the list of confirmed defects. A box-shadow replacement is itself suspect: a forced-colours theme removes box-shadow (Forced colours).

Retired

--shadow-focus – the 3px soft glow used on inputs – is retired as a focus indicator. It reads as a glow rather than an edge, it is a fourth idiom, and some dialogs hand-rolled its exact geometry with a different colour instead of using the token. Inputs take the same outline as everything else – and since #230 they do: the search bar, the settings controls and every dialog input and select draw this ring, and the glow has no remaining use in src/.

What a card must promise about the keyboard

QuestionThe answer a component owes you
Can I reach it?Native element first: <button>, <a href>, <input>, <select>, <details> bring focus, a role, a name slot and their keys for free. A custom control owes all four by hand: a role, an accessible name, tabindex="0" (or a roving -1/0 inside a composite), and the keys its role promises – Enter and Space for a button, the arrows for a list, tree or menu. A <div onClick> has none of the four.
Can I tell where I am?The ring above. Always, and never covered.
Can I move inside it?Lists, trees and menus take arrow keys, and hold one Tab stop between them – not one per row.
Can I get out?Escape closes and returns focus to whatever opened it.
Do I know what it is?A visible label tied by for/id, or an aria-label – never both competing.
The file tree passes row three with a roving tabindex. The whole tree is one Tab stop: the focused row has tabIndex="0", every other row has -1, and the arrow keys move focus between rows. Before #87 it failed in the more hostile direction. ProjectTreeNode.tsx spread dnd-kit's drag attributes, whose tabIndex: 0 and button role made every row a Tab stop that answered no key: 400 files, 400 dead stops. The fix was not additive. Those attributes had to be dropped first, or the two mechanisms would have fought over the same attribute. The tree's rows sit in a scroll container, so they draw the inset ring shown above. The context menu, and the file, screen and window pickers, take arrow keys too (Menus).

Exceptions

Where the shipping component departs from this card, with the reason. An undocumented deviation is a bug; a documented one is a decision.

WhereThe cardThe component, and why
HTML-preview placeholder ring Offset 2px outward, or inset inside a scroller – the only permitted variation. Outward at offset 0, and only the top edge shows: the page's native view paints over the placeholder box, and the panel clips the other three sides. A visible 2px edge still meets SC 2.4.7. Accepted at #124 QG-8 U2; see HtmlPreviewPanel.css.
Escape from a previewed page Escape returns focus to whatever opened it. Returns to the permission band's chip, not to the placeholder that entered the page. The chip's accessible name states that exit ("Press Escape in the previewed page to return here", decided band card), and a page can also be entered with the mouse, where there is no opener.
Screenshot area-select overlay A solid violet ring from the tokens. A 2px dashed white ring (Highlight in forced-colours mode), literal values. The overlay is a separate transparent window that cannot load design-tokens.css, and it is drawn over whatever is on the desktop. Same bypass as the Colours card's exception; see ScreenshotOverlay.css.
Settings checkboxes Offset 2px outward, inset inside a scroller, or the inner-gap form – decided on this card since 2026-10-28. Inset by 2px. The element is a 24 × 24 target around the Form card's 16px box, with a transparent 4px border between the two, so the inward ring lands 2px outside the visible box – where the card draws it. Outward, it would float 6px off. See SettingsOverlay.css (#96). The card now decides this form (Rings on a filled control), so the site's deviates: marker can go.
HTML-preview toolbar tools Offset 2px outward, or inset inside a scroller. Inset – the permitted case, recorded. The bar scrolls sideways when a narrow pane cannot fit it (overflow-x: auto, PreviewNavControls.css), so an outward ring is clipped at the scroll edge, and across the tools' 2px gap it would land on the neighbouring tool. Recorded because this card words its inset case for lists. The band's chip keeps the outward ring: it fits inside the bar's padding. See PreviewChromeBand.css.
HTML-preview comment overlay (outline and pin ring, inside the page) The ring is var(--color-border-focus) at --border-width-thick. Literal colours passed in by main as commentState.theme – the accent ring with an ink line or halo beside it – because the overlay is drawn in the previewed page, where a var() would read the page's own properties. See overlayStyles.ts and the proposed Comment overlay card.
Comment pins Every control is reachable with Tab. Focusable (role="button") but tabindex="-1". A page can carry hundreds, and every thread is reachable from the comments drawer, which is the guaranteed keyboard route (plan §10.8).
Closing the comment window or menu opened from the page Escape returns focus to whatever opened it. The opener is page content, so focus returns natively to the page view, with the picker on the same element – Erfana cannot focus a node inside the native view. Planned for P6; see the proposed Comment window card.
