Form controls

decided reviewed 2026-10-28

One text field, one multi-line field, one select and one checkbox, all drawn by form.css. The boundary is --color-border-input, hover brightens it, focus draws the one ring, and a field has exactly one name. An error is three things at once – aria-invalid, a red edge with an icon, and a message the field names with aria-describedby – and on submit, focus goes to the first field that failed. A read-only field looks like a resting one, still takes focus and still lets its text be selected.

These controls were invisible, and it was a token defect, not a card defect. --color-bg-input and --color-bg-secondary resolve to the same colour, so a field's interior is pixel-identical to the panel behind it. The only thing marking the control is its border – and that border was --color-border-default at 1.24:1, against the 3:1 that WCAG 2.2 SC 1.4.11 requires.

1.4.11 is met if either the fill or the boundary reaches 3:1. Neither did, on any of the three surfaces an input actually sits on. The fix is a new --color-border-input, now 3.10:1 here – not a brighter fill, which would have to clear 3:1 against all three surfaces and would end up reading as a button. --color-border-default and --color-border-subtle are unchanged; 1.4.11 does not govern decorative dividers. An unchecked checkbox is identified by its edge alone too, so it takes --color-border-input for the same reason (#96).

Separately, and under a different rule: the placeholder was --color-gray-600, 2.69:1. Placeholders are text, so the bar is 1.4.3's 4.5:1, not 3:1 – it is now 4.52:1.
What this card replaces. Five copies of the same dropdown, three text inputs of three different heights, and two entirely different checkboxes shipping in the same window. Two of the five dropdowns have no disabled style, so they still light up on hover when they cannot be used.

The classes. form.css is proposed component CSS, not yet in src/. It offers .erf-field with __label, __error, __hint, __foot and __counter (--near, --over); the controls .erf-input, .erf-textarea (--reply), .erf-select inside .erf-select-wrap, and .erf-checkbox; and the checkbox row .erf-check with __body, __label and __desc. The comment window already ships the same rules under erf-comment-* names – see Exceptions.

The error contract

The contract exists in one place and is missing in the rest. aria-invalid appears in 2 places in the renderer – the comment form fields in CommentParts.tsx, which also name their message with aria-describedby. That is the contract below, and it is the model to copy. The rename and new-file field in FileSystemDialog.tsx does none of it: its <label> is linked to nothing, it never sets aria-invalid, and its message is a sibling <div> the field does not point at (#94).
RuleWhy
The field carries aria-invalid="true"It is how a screen reader knows this field is the problem.
The field points at the message with aria-describedbyOtherwise the message is read out of order, or not at all. A hint and an error both go in the list: aria-describedby="name-err name-hint", error first.
The border changes, and there is an iconColour alone is invisible to some readers. Two signals, always.
The message says what to do“Invalid name” is a verdict. “Cannot contain a space – try my-notes” is help.
The message sits directly under the fieldNot at the top of the form. Not in a toast.
Validate on submit and on blur – never on every keystrokeAn error that appears while the first character is typed is noise, and it re-announces on every key.
On submit, focus moves to the first invalid fieldThe reader lands on the problem, and the field's aria-describedby reads the message out. No separate announcement is needed for one field.
The submit button stays enabledA disabled submit gives no reason. Let it be pressed, then move focus to what failed.

Messages that are not about one field

MessageWhere it is announced
A field error, on submitNowhere extra – focus moves to the field and its description is read. The message is not a live region, or it is read twice.
A field error, on blurNowhere extra – the field is already named; the reader hears it on returning. Do not steal focus on blur.
Several fields fail at onceFocus still goes to the first. A count above the form (“2 fields need attention”) is optional and, if drawn, sits in a role="status" region.
Saved, or could not saveOne polite role="status" region per surface, present in the DOM before the text is put in – a region inserted together with its text is not announced. A failure that blocks work uses role="alert" (see Feedback).

Naming a field

Every control has exactly one name, from exactly one source. Either a visible <label for> tied to the control's id, or an aria-label when there is genuinely no visible text. Never both – they compete, and the reader hears the wrong one. A title is never the name (see Tooltip).

The name is short. A sentence that explains the control is a description: its own element, linked with aria-describedby – never inside the <label>, where it becomes part of the name. The checkboxes above are built that way.

Some fields in Erfana have neither name source – the rename field, on the path for every rename, new file and new folder, is one (#94). And a <label> with no control is not a label – it is a heading. Use a <span>.

The multi-line field

Used where the text is prose – a comment, a reply, an edit. It keeps this card's border, ring and error contract unchanged and adds four things. The shipping copy is CommentField in CommentParts.tsx.

RuleWhy
Four lines to start: rows="4" and the matching min-block-sizeEnough to show a paragraph is welcome; one line says “keep it short”.
It grows by dragging, vertically only: resize: verticalA sideways drag breaks the panel's layout; a taller field breaks nothing.
The reply variant, .erf-textarea--reply, starts at two linesIt sits inside a thread, under messages that matter more than the empty box.
A counter beside the hint, always shown: “count / 4000”The limit is visible before it is reached, not announced after.
From 3600 characters the counter takes a warning glyph and --color-warningWarns while there is still room to cut. The field is not invalid and can be saved.
Past 4000 the counter takes an error glyph and --color-error, and the field takes aria-invalid, a red edge and a message that names the limit and the countOver the limit is an error like any other, so it gets the whole error contract above.
Never colour alone: each counter state changes the glyph as well as the colourSC 1.4.1. A reader who cannot tell amber from grey still sees the triangle.
The counter is in the field's aria-describedby, after the error and the hint – and is not a live regionIt is read when the field is focused; announcing every keystroke's count would drown the typing.
⌘Enter / Ctrl+Enter saves the focused field; a plain Enter is a new lineEnter belongs to the text in a multi-line field. Either modifier works on every platform; the label names the platform's own, written as the Writing card says.
One press is one save: a held key's auto-repeat, or Enter that confirms an IME composition, does not save againA double save writes the comment twice.
The save button carries aria-keyshortcuts (Meta+Enter / Control+Enter)The shortcut is discoverable from the button, not only from a tooltip.

Read-only

A field whose text must not change right now but must stay readable – the reply box while its reply is being written to the file (CommentThread.tsx:162, NewCommentView.tsx:280). It is not disabled: a disabled field leaves the Tab order and dims, and its text can no longer be copied.

RuleWhy
The native readonly attribute, not disabled and not aria-readonly beside itThe attribute is what a screen reader announces as “read only”; a second ARIA copy adds nothing and can disagree.
Keeps the --color-border-input edge and the resting text colour; no opacityIts text is content to read, not a control that is off.
Text stays selectable (user-select: text) with a text cursorCopying out of a field that cannot be edited is the reason it is read-only and not disabled.
Takes focus and draws the ringA keyboard reader has to reach the text to select it.
No hover brightenA brightening edge says “you can edit this”.
The reason is said nearby, in words – for the reply box, the Reply button reads “Saving…”Without it, typing that does nothing looks like a broken field.

Sizes
