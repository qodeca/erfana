Menu

decided reviewed 2026-10-28

A menu that declares role="menu" keeps the whole keyboard contract – arrows, Home, End, Enter, Esc and a letter to jump – and a destructive item looks the same under the pointer and under the keyboard. Shown as a table, a frame-by-frame pass, and every visual state.

The decision: a role is a promise. Before #90, Erfana's context menu declared role="menu" and role="menuitem" and implemented none of the keyboard behaviour those roles commit to – no tabIndex, no arrow keys, no focus moved on open, no focus returned on close. Only Esc was bound.

That was worse than declaring nothing. A screen reader switches to application mode on a menu and hands the arrow keys straight to the widget, so the user lost their normal browse-mode keys and got nothing in exchange – in a component with 12 dependants.

After #90, ContextMenu.tsx keeps the whole contract below: a roving tabindex, arrows, Home, End, typeahead, focus moved in on open and handed back on close. The rule stands for the next menu anyone builds: implement the contract or drop the roles. Both are honest; a role with nothing behind it is not.

Roving tabindex: exactly one item is 0. The visible shortcut glyph and the icon are aria-hidden; the item names its keys with aria-keyshortcuts, written in the ARIA key syntax – DOM KeyboardEvent.key names joined with +, modifiers first – never as the glyph. Roving tabindex, not aria-activedescendant. Exactly one item carries tabindex="0" and really holds focus; the rest are -1. Both patterns are valid, and this one is chosen because real DOM focus is what makes :focus-visible, scroll-into-view and the browser's own find behave normally. With aria-activedescendant the focus ring is something you have to draw yourself, and a design system that has just spent a card unifying focus rings should not immediately need a second way to paint one.
Focus must come back. Closing a menu without restoring focus drops the user at the top of the document – the same rule the Permission band card applies when its confirm step closes, returning focus to the chip. The trigger is remembered when the menu opens, not looked up when it closes.
Typeahead is not a nicety. It is the only way a long menu is usable without counting arrow presses, and it is what people expect from every native menu on every platform.

Every state

Each frame is one item in one state, under a neighbour at rest. .is-focus stands in for :focus-visible; the app never ships it.

Hover, keyboard focus and the active item look the same – for a destructive item too. A menu has one active item whichever device you use. The danger fill used to sit on the hover rule alone, so the keyboard landed on Delete with the neutral grey fill a pointer never showed. One fill per meaning, on every route to it.
Disabled beats danger. A greyed-out Delete must not still be red. The colour is a promise about what activating the item will do, and a disabled item will not do anything – a red item you cannot click reads as an error, not as "not available right now". So the disabled rule wins the cascade, and the frames above render that case rather than describing it.

Disabled text is deliberately dim: WCAG 1.4.3 exempts inactive controls. It is the one place on this card where low contrast is correct, which is worth saying out loud so nobody "fixes" it.

The shortcut hint, measured

The hint is aria-hidden and repeated by aria-keyshortcuts, so assistive tech never depends on it – a sighted reader does, and reads it at --text-sm, so it needs 4.5:1 on every surface it sits on. --color-text-secondary, which ContextMenu.css still ships, does not; the card moves it to --color-text-tertiary.

The trigger has to say something too. Whatever opens a menu carries aria-haspopup="menu" and aria-expanded. Without them a screen-reader user has no way to know the control does anything before pressing it. Where ARIA forbids one of the two – a tree row, a text field, a widget a library owns – the opener is listed under Exceptions with the reason.

Exceptions

Where the shipping openers depart from "the trigger carries aria-haspopup="menu" and aria-expanded", with the reason. Every opener here still opens its menu with Shift+F10 and the Menu key, and the menu itself keeps the whole keyboard contract above (#90). An undocumented deviation is a bug; a documented one is a decision.

WhereThe cardThe component, and why
Project-tree rows The opener carries aria-haspopup and aria-expanded. Neither. On a treeitem, aria-expanded already means "this folder is open", so it cannot also report the row menu. The menu announces itself as a menu when it takes focus. See ProjectTreeNode.tsx.
Dock tabs (editor, image, HTML preview) The opener carries aria-haspopup and aria-expanded. Neither. The focusable element is dockview's .dv-tab, which has no role, and both attributes are invalid on a role-less element. Giving it role="tab" needs a tablist around it, which is dockview's markup, not Erfana's. See Tabs/useTabMenuKey.ts.
Markdown editor The opener carries aria-haspopup and aria-expanded. Neither. The focused element is Monaco's own input textarea, whose ARIA Monaco manages. See MonacoMarkdownEditor.tsx.
Terminal The opener carries aria-haspopup and aria-expanded. Neither. The focused element is xterm's helper textarea, whose ARIA xterm manages. The marker sits where the terminal opens its menu, in useXtermSession.ts.
Text fields (new file, rename, prompt, diagram chat) The opener carries aria-haspopup and aria-expanded. aria-haspopup="menu" only. ARIA does not allow aria-expanded on a textbox. See PromptDialog.tsx, FileSystemDialog.tsx and ChatBubble.tsx.
HTML-preview comment menu (“Add comment”) The opener carries aria-haspopup and aria-expanded. Neither. The opener is an element of the previewed page, inside a native view Erfana does not own, and the in-page picker announces the element instead. The menu itself keeps this card's whole contract, opens with Shift+F10 and the Menu key, and on close returns focus natively to the page. Planned for P6; see the proposed Commenting on a page card.
Menu minimum width (menu.css, and ContextMenu.css, which ships the same value) Tokens only (docs/design-system/README.md). A literal min-width: 180px. No width token exists for floating surfaces. Proposed: --menu-min-width, read by the context menu and by any future dropdown, so two menus side by side cannot drift to two widths. The card file carries a deviates: note until the token lands in design-tokens.css.
