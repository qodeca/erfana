Icons

proposed reviewed 2026-08-31

Every icon comes from the shared registry (utils/iconRegistry.tsx), takes a size name from the token scale and is drawn at one stroke weight. Bypassing the registry is the problem: today 50 files import lucide-react directly, so each picks its own size and stroke at the call site, and nothing can change them in one place.

The problem, counted. 162 icons are sized with a number typed at the call site – size={14}, size={18} – across 8 different values. 3 of those exist nowhere in the token scale (14, 18, 48). The registry itself sizes by number too, and its default size is off the scale. 12 files already import from the registry, which is the shape of the fix: once the registry takes a size name, routing the bypassing files through it fixes sizes and strokes together.

The five sizes

TokenValueSampleUse
--icon-size-xs12pxInline with --text-sm – an error message, a badge
--icon-size-sm16pxThe default. Tree rows, toolbars, menus, and every 24px icon button
--icon-size-md20pxBeside --text-md and larger – a 40px button, a banner
--icon-size-lg24pxA panel header, a standalone status glyph
--icon-size-xl32pxDialog headers, empty states
The decision. Icons take a size name, never a number. The three off-scale values map to the nearest token: 14 → sm (16), 18 → md (20), 48 → a new --icon-size-2xl (drawn below at --space-24 until the token exists). Nothing else is added – eight sizes for one small app is too many. A tree row or a toolbar is sm, not lg: a 24px glyph fills a 24px button edge to edge and leaves no room for its hover fill.

One stroke weight

Lucide draws a 2-unit stroke on a 24-unit grid, so the stroke scales with the icon: thin and grey at 12px, heavy at 32px. The rule: 1.5px on screen at every size – in the app, strokeWidth={1.5} with absoluteStrokeWidth, set once in the registry; on this card, vector-effect: non-scaling-stroke.

Lucide default – 2 units, scales xs sm md lg xl 2xl
Decided – 1.5px, non-scaling xs sm md lg xl 2xl

Why 1.5: at the default sm it is a whole number of device pixels on a 2× display (3), and it keeps a 12px glyph from going hairline-grey or a 32px one from reading bold.

Colour states

An icon is a graphical object: where it carries meaning it needs 3:1 against its surface (WCAG 1.4.11). It takes currentColor and never sets its own fill – the button or row around it decides the colour.

Does this icon have a name?

This is the only accessibility question an icon raises, and it has exactly two answers. A title – on the SVG or on the button – is never the answer: it is not announced reliably and never appears on keyboard focus (see Tooltip).

New file

No – it sits next to words. The icon repeats what the label already says, so a screen reader announcing it twice is noise. Mark it aria-hidden="true". This is the common case.

No – but its button does. The icon stays hidden; the button carries aria-label="Close preview". Never put the label on the glyph inside a button – that is one name too deep.

Yes – the icon is the information. A git status dot with no text beside it. Give it role="img" and an aria-label. Erfana already does this correctly on file badges.

The third case is the one that gets missed. A colour or a shape carrying meaning on its own needs a name, or the meaning is invisible to anyone not seeing colour. Erfana's sidebar footer currently fails this: it shows M3 U2 D1 where only the colour separates modified from deleted, with no label at all.

Minimum target

An icon that can be clicked lives in a target of at least 24 × 24 – WCAG 2.2 SC 2.5.8. The glyph itself is usually smaller: a 16px icon centred in a 24px button is the standard pairing, and it is what the button above does. Never shrink the target to fit the glyph. See Buttons – icon-only.

Exceptions

None recorded. A shipping component that departs from this card carries a deviates: marker at the site and gets a row here, naming the file.
