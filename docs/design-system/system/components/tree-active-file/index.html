Active file in the tree

proposed reviewed 2026-11-03 · for #453 · design note project-tree

When a file or preview tab becomes active, the project tree marks that file's row with the active tab's own mark – a 2px lime line – drawn under the file name. The tab and the row then say the same thing in the same shape: "this is the file you are looking at". The mark is not selection, not focus and not hover, and it never moves keyboard focus.

This card adds one state to Rows and lists (decided) and changes nothing in it. The row, its height, its indent, the selected state (fill plus lime left edge), the inset focus ring, hover, cut and the git badges are all that card's; the frames below link its row.css rather than copy it. A row is in this state when it carries aria-current="true", so what is drawn is exactly what a screen reader announces – the same rule ProjectTreeNode.tsx follows for aria-selected.
Why four marks have to stay apart. In the tree today, selected means "the folder paste and New file act on" – only a folder click or Enter on a folder sets it; opening a file never does (ProjectTreeNode.tsx, isSelected). Focus means "where the keys go". Hover means "where the pointer is". Active file means "what the editor shows". All four can sit on screen at once, on different rows, while the editor holds focus – so each needs its own shape, not just its own colour.

Why A. The person just clicked a tab that wears a lime line. Finding the same lime line in the tree needs no learning – it is the same mark, in the same colour role (--color-accent-secondary) and the same thickness (--border-width-thick) as the selected tab's underline on the Tabs card. It sits right under the name the eye reads, so it is found at once after the scroll. It adds no fill, so it can never be mistaken for hover or selection; it is a line, not a ring, so it can never be mistaken for focus.
Why B was rejected. An edge on the side facing the editor is a neat spatial idea and has no clash with cut. But it puts a second lime edge on the same row type: a newcomer has to learn that left means "paste target" and right means "open file". In a wide sidebar it also sits far from a short name, so it is slower to find – and finding the file is the whole point of #453.
Cut + active file is the one combination A has to resolve. The Rows card draws cut as a dashed underline on a dimmed name. With both, the name stays dimmed and the line stays dashed – the shape still says cut – and the line turns lime. That one combination tells "also the open file" by colour, which is acceptable only because the active tab says the same thing in words. The app today draws cut differently (a full-width dashed line under the row and an opacity fade, ProjectTree.css), and there the two lines simply stack.
"Active file + selected" cannot happen today – only folders are selected, and only files are revealed. It is drawn so the layering is settled if selection ever reaches files: the fill and left edge are selection's, the underline is the reveal's, and they do not touch.

Considered and rejected

TreatmentWhy not
A fill of its own (a lime or grey tint)Fill-only, so it is told from hover and selection by hue alone, and a contrast theme removes it (Forced colours card, rule 1). A lime tint also reads olive on the sidebar – the colour #432 is moving success away from.
Bold nameFolders and Markdown files already ship in --font-medium; weight cannot mean a third thing.
An outline around the rowThat is the focus ring's shape (Focus and keyboard).
A marker iconThe app's row has no free slot – the icon slot holds the file icon – so a marker would push every name out of line.
A flash or pulse when it landsThe reveal is a state, not an event. Motion in the side panel pulls the eye off the editor the person is reading.

In the tree, one tab switch at a time

The editor holds focus throughout frames 1–3 and 5–6, so no row shows a ring. The strip above each tree stands in for the tab bar. docs was opened by the person; every other open folder was opened by the reveal.

The reveal never takes focus. The app is held to this contract by ProjectTree.reveal.test.tsx and revealActiveFile.test.ts (unit) and e2e/tree-follow-active-tab.e2e.ts (the real app).

Contrast

WCAG 1.4.11 asks 3:1 of a state indicator against what it sits on. Measured on every surface the row can have under the line.

The line onRatio
The tree (--color-bg-tertiary)11.55:1 · pass
A hovered row (--color-bg-hover-solid)10.46:1 · pass
A selected row (--color-bg-selected over the tree)7.77:1 · pass
Against the focus ring it may sit inside (--color-border-focus)1.66:1

The last row has no minimum: the line and the ring never touch – the ring is inset at the row's edge, the line sits under the name – and they differ in shape. It is shown so nobody has to wonder.

In a contrast theme

Simulated with system colours, as on the Forced colours card. The browser repaints a text decoration in the text colour, so the line survives as a shape.

Measurements

PropertyValueWhy
Hookaria-current="true" on the treeitemOne attribute is both the announcement and the style hook.
Where the line goesThe name onlyNever the file icon, the sensitive-file warning or the git badge.
Colour--color-accent-secondaryThe selected tab's underline role (Tabs card).
Thickness2pxThe tab underline's thickness.
Offset below the text4pxClears descenders, stays inside the 28px row.
Name box padding4px top and bottomThe name clips its overflow so it can elide its tail (.file-name in the app, .erf-row__name here), and that clip also cuts a line drawn below the text. The first render of this card lost the line on every row without a fill – found by looking, not by reading.
Skip inknoneOne unbroken line, like the tab's; a broken line reads as dashed, which is cut.
How many rowsAt most oneThe active tab of the focused editor group. A split view does not mark two.
Hidden files. ProjectTree.css dims a hidden file's name with opacity, which would fade the line with it. The active file's row therefore shows a hidden file's name at full strength – what a hovered hidden file already does – so the line is always measured at the values above.
