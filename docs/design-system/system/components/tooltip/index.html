Tooltip

proposed not yet reviewed

A tooltip is .erf-tooltip in tooltip.css: a short description that appears on hover and on keyboard focus, can be hovered itself, stays until the pointer or focus leaves or Esc is pressed, and is linked with aria-describedby. It is never the control's name, never a title attribute, never interactive, and never the only place information lives.

Why a card now. Erfana ships two tooltips that disagree – .dialog-tooltip in Dialog.css and .chat-tooltip in ChatBubble.css, with different fills, edges and shortcut keys – and both are built so WCAG 2.2 SC 1.4.13 fails: pointer-events: none means the pointer cannot move onto them, and Esc closes the whole dialog instead of the tooltip. Neither is linked to its button, so its text never reaches a screen reader. Everywhere else the renderer reaches for title, which is no tooltip at all.

The shortcuts are real and written in the macOS glyph form: Project ⌘B (activityBarConfig.ts), Case sensitive ⌥⌘C (SearchBar.tsx) and ⌘Enter to submit (PromptDialog.tsx). On Windows and Linux the same box reads Ctrl+B, Alt+C and Ctrl+Enter – see Writing – Keyboard shortcuts. Each trigger points aria-describedby at the shortcut line only, so the name is not read twice, and declares the keys in aria-keyshortcuts.

The last one is a toggletip: click it or press Enter. Its button exists only to show that text, so it opens on activation and works on touch – the shape the dialog and chat “i” buttons should take.

The rules

RuleWhy
The control has its own name – visible text, or aria-label on an icon buttonThe tooltip is a description. If it is removed, the control must still say what it is.
title is never the accessible name, and never a tooltipBrowsers fall back to title for the name only when nothing else names the control, and screen readers do not treat that fallback alike – so it never stands in for aria-label or visible text. It is not shown on keyboard focus or touch, cannot be hovered and cannot be styled.
The trigger points at it: aria-describedby="<tooltip id>"; the tooltip has role="tooltip" and stays in the DOMA description is read after the name. Removing the node or toggling aria-hidden on it is not needed and only risks losing it.
A tooltip that only repeats the visible name adds nothing – leave it outA text button already says it. Tooltips belong on icon buttons and on controls with a shortcut.
Hoverable (1.4.13)The pointer can move onto the tooltip – no pointer-events: none, and the gap is bridged – so a magnifier user can read it.
Persistent (1.4.13)It stays until hover or focus leaves, or it is dismissed. No timeout.
Dismissible (1.4.13)Esc hides it without moving the pointer or focus – and is consumed, so the dialog behind it stays open. A second Esc reaches the dialog.
Nothing interactive insideFocus never enters a tooltip. A link or button in it makes it a popover; use the toggletip.
Never the only place information livesTouch has no hover. Anything needed to finish the task is on the surface, or behind a toggletip.
Short – one line, two at most, sentence caseIt is read in passing. A paragraph belongs on the surface.
Shown after a short hover delay, at once on focus; no motion under reduced motionA delay stops tooltips flashing as the pointer crosses a toolbar; focus is deliberate, so it gets no delay.

The keyboard contract

KeyResultFocus ends on
Tab to the triggerThe tooltip shows at onceThe trigger
Esc while it showsThe tooltip hides; the event stops there, so a dialog behind it stays openThe trigger – focus does not move
Esc againReaches the surface: the dialog closesThe control that opened the dialog
Tab awayThe tooltip hidesThe next control
Tab while a hover tooltip shows on another controlThe hover tooltip hides, so it never covers the control that now has focus (Focus not obscured)The next control
Enter / Space on a toggletipOpens it; again closes itThe toggletip button
Esc or a click outside a toggletipCloses it (native popover light dismiss)The toggletip button
Tab away from an open toggletipCloses itThe next control

A hover tooltip hides when keyboard focus moves to another control – the pointer may still rest on its trigger, but the tooltip must not sit over the newly focused control. No app test holds a tooltip to this contract yet. The Esc rows, the hover tooltip hiding on a focus move, and the toggletip closing on Tab away need script – a native popover is not dismissed when focus leaves it – which this static page cannot have. They are the part a test must prove.

Exceptions

None recorded. No deviates: marker points at this card yet; a shipping file that departs from it on purpose carries one at the site and gets a row here.
