Buttons

proposed reviewed 2026-08-31

One button component, .erf-button in button.css, in seven variants. Its height is a --btn-height-* token, its focus is the one ring, a hover changes the fill and never moves the button, and every state – disabled and busy included – reads without colour alone. The dialog buttons that ship today are drawn further down as an illustration of what this replaces.

Disabled dims the content, never the button. The label and icon fade and the fill fades with them, but the focus ring keeps full strength – the rule the Permission band and the comment window already ship. A button that cannot run yet because a field is empty is blocked: the same disabled look on aria-disabled, still in the tab order, never a third style.

The primary button's label is near-black, not white. The brand violet is a light tint, so white on it measures 2.20:1 and fails WCAG 1.4.3. --color-btn-primary-text (brand black) on the same violet measures 8.39:1, and 6.84:1 on hover.

This holds for every violet fill, not only dialog buttons. The editor's Save button, the view-mode toggles, the welcome screen's action and the diagram chat buttons all shipped a white label until #231, because only Dialog.css was guarded. Now accentFill.contrast.test.ts scans every renderer stylesheet – if you draw a violet button with a white label in a design, the test will reject the implementation.

Every state

Each cell is a static picture of one state, forced with a .is-hover, .is-active or .is-focus hook that the CSS writes beside the real pseudo-class – :is(:hover, .is-hover) – so the picture and the live button cannot disagree. Disabled uses the real disabled attribute; busy uses aria-busy="true" with aria-disabled="true". Every label sits in its own <span>: the disabled rule dims child elements, and a bare text node is not one.

StateHow it reads without colour
HoverA fill appears or steps; the button never moves, so the pointer target never shifts under the cursor.
Focus-visibleThe one ring: --border-width-thick of --color-border-focus, offset --space-1. Keyboard only – never after a mouse click.
Toggle pressed (on)A fill and a lime bottom edge, and aria-pressed="true" for assistive tech. The label never changes when it is pressed – the state is the attribute, not the words.
Radio checked (one of many)A fill and a brighter glyph, with no lime foot, and aria-checked="true". Exactly one in the group is ever checked, so the reader compares it with its neighbours; the missing foot keeps it from reading as “on” beside a real toggle (Toolbar – View modes beside toggles).
DisabledThe label and icon take --opacity-disabled, the fill and edge are mixed towards transparent by the same amount, the cursor is not-allowed, and hover does nothing. The button itself is never given opacity, so a focus ring on an aria-disabled button keeps full strength. WCAG 1.4.3 exempts the label from contrast; it is still drawn legibly. Prefer explaining why nearby over a silent disabled button.
BlockedThe disabled look on aria-disabled="true" – never disabled, never a third style – because a required field is empty. It stays in the tab order and names what is missing through aria-describedby. Enter and click do nothing.
BusyA spinner plus the -ing form of the button's verb, with an ellipsis: Save becomes “Saving…”, Check becomes “Checking…”, Load more becomes “Loading…”. aria-busy="true" and aria-disabled="true", not disabled, so focus stays on the button instead of falling to <body>. The result is announced by the surface's live region, not by the button. The ::before ring is the only busy spinner: feature CSS never adds a second one – no icon, no pseudo-element, no .erf-progress inside the button.

Focus on a disabled and on a blocked button

A native disabled button never holds focus, so these two are the cases that need the ring: aria-disabled buttons the keyboard can still reach. In both the content is dimmed and the ring is not.

Menu button

A button that opens a Menu: .erf-button--menu on top of a variant, a label, then a chevron-down caret (.erf-button__caret). It carries aria-haspopup="menu" and aria-expanded; while the menu is open the button keeps the hover fill and the caret turns over. Both only repeat aria-expanded. The More button in a toolbar is the icon-only form: no caret, an aria-label.

Heights

The button scale. --btn-height-sm sits exactly on the 24 × 24 target floor (WCAG 2.2 SC 2.5.8), so nothing clickable is smaller. Pick a height by where the button sits, never by how important it is – importance is the variant. A tool in a toolbar takes the toolbar's proposed tool height instead (Toolbar – Tool height).

Beside a field

The button scale (24/32/40) and the field scale (28/36/44) do not pair, so a button beside a field never lines up – the README lists it as a defect. Until the two scales are reconciled, a button that sits on the same row as a field takes the field's height with .erf-button--field-sm|md|lg.

my-notes Wrong: --input-height-md beside --btn-height-md – the bottom edges miss by a --space-2.
my-notes Right: .erf-button--field-md – one height, both edges on one line.
Find Dense chrome: an icon button beside a find field goes square at --input-height-sm.

Order and wording

Destructive action on the right, cancel on its left. The label says what will happen – “Delete file”, not “OK”. A button that cannot be undone never gets keyboard focus by default, so pressing Return twice cannot trigger it.
Proposed: the same rule, inline. The comment window confirms a delete in place, inside the message, rather than in a second dialog – Cancel first and focused, the destructive button on the right, a label that says what goes (“Delete comment”, “Delete thread”, “Delete block”). See the proposed Comment window screen.

Open defects this card names

Departures in the shipping dialog buttons (src/renderer/src/components/Dialog/Dialog.css). None is marked at the site, so none is an exception; each stays here until .erf-button is adopted (the adoption is deferred).

  • A height from padding. The button is about 37px tall: --space-5 padding around a --text-md line, not a --btn-height-* token. It matches neither the button scale nor the field scale.
  • Hover moves the button. Primary and danger hover lift by translateY(-1px) and change the shadow, with no reduced-motion guard.
  • A tracking literal. letter-spacing: 0.2px – the only tracking literal on a control.
  • A hover that changes nothing. Secondary hover sets border-color: var(--color-gray-700), the value --color-border-subtle already resolves to. --dialog-btn-secondary-hover is declared and never read.
  • transition: all – animates every property, including ones that should snap.
  • Disabled dims the whole button. .dialog-btn:disabled and the Markdown toolbar's .toolbar-btn:disabled set opacity on the button. Harmless while they use native disabled (it cannot hold focus); a defect the moment either moves to aria-disabled. The comment window already overrides it for its own buttons (CommentWindow.css).

Tooltip-related – a name or a description that lives only in title, which is not shown on keyboard focus and is not reliably read (the Tooltip card's rule):

  • The comment tools describe themselves in title – components/Comments/CommentToolbarTools.tsx: the mode button, the list button (including the reason it is unavailable) and the pins toggle.
  • The context meter's detail is a title – TerminalPanel/components/ClaudeStatusBar.tsx:118 puts the whole tooltip on the status bar's container.
