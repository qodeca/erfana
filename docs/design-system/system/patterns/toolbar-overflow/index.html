Toolbar overflow

decided reviewed 2026-11-03

No panel toolbar ever cuts a button off. When the panel gets too narrow, buttons move one at a time into a … menu at the end of the row, and the … button never leaves. In the row a button stays icon-only; in the menu it shows its icon and its label. This applies to every panel toolbar, not only the terminal and the project tree.

Why this card exists. #451: dragging the terminal or the project tree narrow clips its header buttons, and the terminal's Maximize button – the one that would give the terminal room – is the first to vanish.

What it does not decide. The icon button and its states are the Buttons card's; the menu's look and keyboard are the Menu card's, reused here unchanged. The one thing this card adds to a menu is the checked item, checkbox or radio (rule 7). The Toolbar card used to sketch overflow by whole groups, with text-only menu items; this card replaces that sketch, and the Toolbar card's overflow section now points here.

The rules

  1. Nothing is clipped. At any width a button is either whole in the row or in the menu, never half-visible and never pushed out of view. The row measures its own width (a panel resizes without the window resizing), not the window's.
  2. The … button. A ghost icon button with the lucide ellipsis glyph, named “More actions” (aria-label, and the same text as its tooltip), with aria-haspopup="menu" and aria-expanded. It appears as soon as one button has moved, sits at the inline end of the row, and is the last thing standing – it never moves, it is never disabled.
  3. What gives way, in order. First the panel title truncates with an ellipsis down to a reserve of a few letters. Then buttons move, one at a time, lowest priority first. Then the title goes, then the panel icon. The … button stays.
  4. Who moves first. Priority is the toolbar order: the rightmost button moves first, so the buttons left in the row stay a run from the left. A toolbar may raise a button so it moves last – the terminal raises Maximize terminal, the project tree raises New file (the order). Nothing is pinned: any button may move, and at the narrowest only … is left.
  5. Never trade one button for …. The menu never holds a single button that would fit in the … button's place, so a toolbar with one button never shows … (the project header's filter toggle is the case).
  6. Icon only in the row, icon and label in the menu. The row's buttons do not change. A menu item shows the button's current icon, its label – the button's tooltip text without the shortcut – and the shortcut in the Menu card's shortcut column. Items keep the toolbar order, not the order they moved in.
  7. State moves with the button. A toggle (aria-pressed) becomes a menuitemcheckbox whose aria-checked matches, drawn with a lime check in its own column at the inline end – the same lime as the toolbar toggle's foot, so “on” reads alike in both places. One choice of a set – a view mode, a diagram direction – becomes a menuitemradio, the current one checked and drawn with the same lime check (its icon slot keeps the button's own icon, rule 6). A disabled button becomes an aria-disabled item that is still reachable. A busy button becomes a disabled item with its busy label (“Importing file…”).
  8. The menu floats. It opens under …, its inline-end edge on …'s. Where that would leave the window – a panel at the window's edge – it flips and opens toward the window's interior. It floats over the neighbouring panel, is never clipped by its own panel, and never truncates a label; a long label widens it.
  9. One copy of each action. A moved button leaves the row's layout and the accessibility tree; it is not hidden with visibility or opacity. A screen reader meets each action once, in the row or in the menu.
  10. No motion. Buttons leave and return instantly; nothing slides while the splitter is being dragged. A button returns only when it fits whole, so the row never flickers at the boundary. The open menu closes if its toolbar resizes.
  11. Focus never falls off the row. If the focused button is about to move, focus moves to …. After a menu item runs, focus goes to … (the item's own button is not in the row), and a dialog that item opened returns focus to … when it closes.

Terminal order (owner, 2026-11-05, #462). Scroll lock, Restart terminal and Scroll to bottom come last in the row, after Maximize terminal, so they are the first to move: at the default terminal width they are in the menu and every other button is in the row. Why raise those two. Maximize terminal is the action a user reaches for because the terminal is narrow – #451's complaint – so it is the last to go. New file is the project tree's everyday action; change and close project are occasional. Every other toolbar takes the plain right-to-left order until someone raises a button on purpose.

Where it applies

Every panel toolbar. Found in src/renderer on this card's date. The shared component is components/ToolbarOverflow/ToolbarOverflow.tsx; the first three rows below ship it (#451):

  • The terminal header – TerminalPanel.tsx. (TerminalToolbar.tsx holds an older copy of the same buttons, without Capture photo and Maximize; it is exported but not rendered – inferred from its imports.)
  • The project header and the project row – ProjectPanel.tsx, ProjectTree.tsx.
  • The Markdown, Mermaid and image viewer toolbars and the HTML preview band's bar – the Toolbar card lists them. The image viewer scrolls instead (#73, a locked requirement); it stays an exception there. The Markdown and Mermaid toolbars – MarkdownToolbar.tsx, MermaidToolbar.tsx – ship it since #461: a separator moves with the button after it, the spacer counts at its minimum width, and the live status region, the modified dot and the comment tools stay in the row (a recorded exception below). Their view modes and diagram directions are radio items in the menu (rule 7). The HTML preview band's bar does not ship it yet.

Found while drawing

  • The filter toggle was not a button. ProjectPanel.tsx drew it as a <span> with a click handler: no role, no tabindex, no aria-pressed, so the keyboard could not reach it. Fixed with #451: it is a button with aria-pressed, named “Filter options”.
  • Two row rhythms. The terminal header spaces its buttons by --space-4, the project row by --space-2. The frames draw each as it ships; this card does not choose between them.
