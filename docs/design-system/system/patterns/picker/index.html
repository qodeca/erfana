Erfana design system / Patterns / Element picker

Element picker

proposed not yet reviewed

Pointing at one element on a page Erfana does not own looks the same wherever it happens: a two-tone outline on the element’s border box (a 2px accent ring with a 1px ink line on both sides), a label on ink naming tag#id.classes then the size, a light fill for the element that was picked, a static flash after a send, and a mode frame that says the keys belong to the picker. The parts are in picker.css; where they go is the component’s job.

Why a pattern card now. These rules live today in one decided feature screen, the HTML preview’s comment overlay, and a Focus card exception. The built-in browser (spec 025) is a second feature that picks elements; without a shared card the two copies drift. This card lifts the overlay’s outline and label with two stated differences – the flash adds the 1px ink line so it survives on white, and the gap before the size is --space-4 (a token) where the overlay uses 1ch – and adds what the browser needs: the selected look on a still image, the flash, and a frame drawn outside the page. Owner decision: the Focus card allows the two-tone ring only for the comment overlay; the owner approved widening it to the browser (browser note, owner decision OD-2, 2026-11-01), and the Focus card's Exceptions now record it.

Picked, sent, and the mode frame

A surface that answers the pick

Proposed with the browser’s prompt-actions screen. A floating Erfana surface over the still image that answers the reviewer’s own pick – the prompt-actions panel, the instruction dialog – carries .erf-picker-owned: a 2px lime top edge, the pick frame’s colour, so the surface reads as part of pick mode and leaves with it. Its edge on the page is still the floating surface’s own border and shadow; lime does not clear 3:1 on a white page (see Contrast), so the lime is identity, never the boundary. It is not a security signal – a page can paint lime; what the reviewer trusts is the place: over the still image, never inside the page.

Two hosts, two frames – recorded, not reconciled. The HTML preview’s comment mode draws a violet frame inside the page edge with a “Comment mode” tab (decided overlay screen). The browser draws the lime frame outside the page, because its violet already means “the page has keyboard focus” and its banner lives in the reserved pick row. Bringing comment mode onto the lime frame is a later decision for the owner; this card does not change the decided screen.

The mode banner and the answering surfaces in narrow room

Proposed with the browser’s picking and prompt-actions screens (review round 1: H-09, M-01, M-03, M-36), so a screen does not decide them.

  • The banner is one line at any text spacing. Every part is nowrap and leaves whole – it never wraps or clamps. The first clause has priority over every optional control beside it: in pick mode the width preset goes icon-only, below the narrow tier it leaves the row, and the target name truncates but keeps at least 8 characters at 380px and wider (browser design rule, README § Tiers, A-30); below 380px it may go down to “…” – the full name stays in the accessible name and the target menu, and the process is never cut. Optional clauses leave in this order: “↑ ↓ parent and child”, the hover echo of the label, the ⌘E clause.
  • One true clause per key-routing state. Pick: “Picking – Esc to stop”. Toolbar focus: “Picking – Esc returns to the page”. Panel open: “Picking – Esc closes the panel”. Dialog open: “Picking – Esc closes the dialog”. Focus elsewhere: “Picking – click the page to continue”, or “Picking – click to return to the dialog” while a dialog waits – no key is named while the keys go to another panel. The Pick element tooltip, while on, reads “Stop picking”.
  • Pick-row tooltips stay inside the pick row’s band, beside the toggle, over the status slot – never over the navigation row or the address bar, never over the focused control – so they show on keyboard focus too.
  • A chrome-side cue while an answering surface is over the still image: the panel or dialog variant of the banner in the status slot with a “Still image” chip (“Page paused” in its place when frozen), or, once pick mode has ended with a dialog still open, “Over a still image of the page – Esc closes the dialog”. A page cannot draw it, so a panel without it is a fake.
  • Behind the panel the rows stay live at full strength – a toolbar click, Ctrl/Cmd+L or F6 closes the panel without sending (025-FR-049). Behind the dialog only, the rows are inert and their buttons’ icons are dimmed; the origin field and focus rings are never dimmed.
  • What lime means here, and only this: pick mode (the frame, solid or dashed, and the pressed toggle’s foot), the selected editor tab’s underline, and the pick-owned edge of a surface that answers the pick. It never means “done” – the send notice’s check is neutral – and no refinement control carries it.
  • Under 400px of room the panel and the dialog are a sheet (Dialog card’s --sheet) inside the page’s rectangle, over the still image, pinned to its foot, with the pick-owned top edge; the frame stays visible round it. While one is open at the narrow tier the target leaves the pick row – the surface shows the target and changes it without losing the pick.

The keyboard contract

The two hosts differ today; the difference is shown, not hidden. Owner decision OD-14: the browser accepts Alt+↑ / Alt+↓ as aliases of ↑ / ↓, so one refinement chord works in both pickers. The comment picker’s banner reads “Comment mode · Esc to leave” on its own in-page tab; the browser’s lives in the reserved pick row. The same owner decision makes it one banner pattern shared by both hosts – one true clause per routing state – with the browser’s lime outer frame kept.

Exceptions

None recorded. The overlay inside a third-party page is drawn from resolved literals, never var(); the comment overlay records that on its own screen, and the browser’s engine overlay will record its own when built (browser note, ADR 0007).
