Empty, loading and error states

proposed not yet reviewed

A region that has nothing to show says what is missing and what to do next, in one title, one hint and at most one action. A region that is waiting shows inline progress in its own place; only a change that would corrupt state if the user kept working blocks the whole window. A region that failed says what stopped, that the rest still works, and how to try again – and never looks like an empty state.

Why a pattern, not a component. The app already ships all three states, many times over, and each copy centres a grey line of text its own way: different paddings, different gaps, different greys – and one of them fails contrast on the surface it sits on. The consolidation set below lists every copy this card would replace. states.css is the proposed shared shape; adopting it is a consolidation, not a ninth variant.

Every state

Each frame is a picture of one state on the surface it really lands on. Nothing in a frame takes focus; the keyboard contract is the table below.

Empty

The copy rule. The title names what is missing, in sentence case, without “Oops”, “Sorry” or an exclamation mark. The hint is one sentence that says what to do or why the region is empty – never a restated title. The action, when there is one, is a verb that changes the state (“New file”, “Show all files”, “Clear search”); an empty state with nothing useful to do has no button. Colour: title in --color-text-primary, hint in --color-text-tertiary, icon in --color-text-tertiary. Not --color-text-secondary: it measures 4.15:1 · fail on the project tree and 3.72:1 · fail on a panel, and both host an empty state.

Loading

Inline progress when…Full block only when…
The wait belongs to one region – a list, a preview, a dialog body.The wait changes something every region reads: the open project, the working folder.
Working elsewhere is safe while it runs.Input during the wait would act on the old state and corrupt the new one.
The user might cancel or navigate away.It cannot be cancelled once begun, and it ends on its own.
Partial content is useful – show it as it arrives.Nothing on screen is valid until it finishes.

If neither column fits – a long job the user should be able to leave running – it is neither state: it is a task with its own progress and a way to cancel, and it does not belong on this card yet. A skeleton screen (grey placeholder rows) is not part of the system: nothing in the app draws one, and this card does not add one.

Error

Open this to see the details pattern work without script

A card cannot run the fallback's toggle, but <details> shows the same contract: a control whose state is exposed (expanded or collapsed), and a region that is absent from the accessibility tree while closed. The app keeps its button + aria-expanded + hidden region, because its label changes between Show and Hide – a summary's text does not.

The markup

<!-- Empty, whole region -->
<div class="erf-state">
  <svg class="erf-state__icon" aria-hidden="true">…</svg>
  <p class="erf-state__title">No file open</p>
  <p class="erf-state__hint">Pick a Markdown file in the project panel, or start a new one.</p>
  <div class="erf-state__actions"><button class="erf-state__action" type="button">New file</button></div>
</div>

<!-- Inline progress: the region is busy, the sentence is the status -->
<div aria-busy="true">
  <span class="erf-progress" role="status"><span class="erf-progress__spinner" aria-hidden="true"></span>Looking for capturable windows…</span>
</div>

<!-- Panel error -->
<div class="erf-state erf-state--error">
  <p class="erf-state__title" id="m1">Project tree unavailable. The rest of Erfana still works.</p>
  <button class="erf-state__action" type="button" aria-label="Reload project tree" aria-describedby="m1">Reload</button>
</div>

Exceptions

None recorded. A shipping component that departs from this card carries a deviates: marker at the site and gets a row here, naming the file.
