Erfana design system / Patterns / Dialog

Dialog

proposed not yet reviewed

Every modal dialog is one shell: a scrim, a titled container, a body that is the only part that scrolls, and a footer of actions that is always on screen. The focus contract is not restated per dialog – BaseDialog keeps it, and its tests hold it.

Why a pattern, not a component. A dialog is assembled from parts other cards own: the buttons are the Buttons card's, the fields the Form controls card's, the stacking order the Layering card's, the entrance the Motion card's. This card decides only how they are put together and how the keyboard moves through them.

The one visual change against the app: today .dialog-container scrolls as a whole (max-height: 85vh; overflow-y: auto), so a long body scrolls the title and the buttons out of view. Here only .erf-dialog__body scrolls.

Every state

Anchored dialog

A dialog about one thing on screen – a comment on an element of the HTML preview – is placed beside that thing, so the reader can see what they are writing about. It is still modal: role="dialog", aria-modal="true", the same focus trap, Esc and focus return. What changes is where it sits and what is behind it.

  • No scrim. The layer under it (.erf-dialog-scrim--clear) still catches a click outside, which closes the dialog, but paints nothing, so the rest of the window stays readable.
  • Placement order: right of the target, then left, then below, then above – the first side with room wins, so it flips at the window's edges. It always stays inside the area, less a --space-4 (8px) margin.
  • The anchored-dialog bounds are --comments-window-width (360px, its usual width) and --comments-window-max-width (480px, its widest). Its height never passes the area less the margin.
  • Header and footer stay fixed; only the body scrolls, as in every dialog.
  • Under 400px of room it becomes a sheet across the foot of the area (.erf-dialog--sheet): full width, top edge only.
  • It floats over content, so it takes the floating surface --color-bg-elevated, an edge and --shadow-dialog (Surfaces).

Inline destructive confirm

A delete inside a dialog asks in place, never with a second dialog on top. The question replaces the item that would go, in an error-tinted box (.erf-dialog-confirm, --color-error-bg with a --color-error-border edge). The question says what goes and whether it can be undone. Cancel comes first and takes focus; the danger button is on the right and its label is a verb (“Delete comment”, not “Yes”). Esc means Cancel and closes the question, not the dialog. The text measures 9.28:1 · pass on the tint.

Wording

  • The title is a question or a task, in sentence case: “Delete 3 files?”, “Rename file”.
  • The action button repeats the verb of the title: “Delete 3 files”, not “OK” or “Yes”.
  • The message says what happens and whether it can be undone. One or two sentences.
  • Cancel is “Cancel”, unless a plainer phrase says what staying means: “Keep working”, “Keep editing”.

Open defects this card names

  • The page behind a dialog is not inert. A screen reader's virtual cursor and a pointer can still reach it; only Tab is trapped, and aria-modal is a hint some screen readers ignore. Fix in BaseDialog.tsx: mark the app root inert while the topmost modal is open.
  • The whole container scrolls. .dialog-container in Dialog.css sets max-height: 85vh with overflow-y: auto, so a long body scrolls the title and the buttons out of view. Fix: make the container a column and give the overflow to the body alone, as .erf-dialog__body does here.
  • No test asserts a name. BaseDialog.test.tsx checks modality and the trap, but nothing fails if a dialog ships without aria-labelledby pointing at its title.
