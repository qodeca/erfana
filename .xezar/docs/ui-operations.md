# Task operation and stage ownership

Select the role workflow and actual available backend/model. Worktree ON for ordinary writing; integration/root-sync modes are separate. Read-only tasks may initialize evidence without dependencies. Bootstrap runs first; then development workflows run preflight → setup → author → readiness → gates → seal → handoff. Every writing workflow — each one that has a `gates` step, `release` with its `changelog` step among them — allows at most two returns to its author step after failed gates. Standalone quality-gates allows two repairs of the same failure. Reassignment retains failure history, not a hidden counter reset.

The terminal agent step must remain last so XEZ:ASK can present options. The question reaches an attached leader as a pushed xezar event, and the leader answers it through the MCP (`execution_control` `answer_question` or `continue`), never through the cockpit; `leader_events` is its fallback when it is not attached. An unresolved required decision in an earlier stage needs a BLOCKED record, and readiness must stop before gates; plain text is insufficient. Because an author step can also end with no work and no BLOCKED record, readiness and both evidence modes refuse a branch with no commits over its base (`branch.has-own-commits`, #312); plain preflight and the read-only roles do not run that check. `design-review` is a read-only role: it posts its verdict with `gh` and neither commits nor needs a `VERIFICATION` record. The one honest exception is a run that only verifies an existing revision (QA of another branch, an acceptance re-run): it writes a `VERIFICATION` record in its evidence directory naming the verified commit (`verified: <sha>`) and where the findings are (`findings: …`), and then passes with no commits and opens no pull request. A malformed record refuses (`scope.verification-record`), and `BLOCKED` still wins. Ask only outside existing authority, never for routine authorized operations. Do not interpret silence as consent.

Complete all source/tests/docs/release metadata and focused commits in development. Handoff verifies unchanged evidence and writes no new content/commit. Missing content returns to the author stage. Publish only within actual assignment authority; draft is not completion. Follow SDLC QA/labels, current CI and actual hosting policy.

Checkpoint: goal/DoD, stable AC and accepted content, plan/tasks/dependencies, decisions/questions, current head/base, evidence/remaining stages, blockers and next action. Handoff: task/phase/outcome, judged/current revision, passed/failed/not-run, PR/CI identity, unmet AC and actionable follow-ups. Decision: accountable delegated authority, question/answer, exact content path/revision/digest or immutable criteria snapshot and conditions. Current checkpoint and late steering must be consumed before resume/final handoff.

## Filing an issue versus triaging one

Two roles touch an issue and they are not interchangeable. `xezar-issue-triage` reads an issue that already exists and returns a verdict — actionable, duplicate, already fixed or unconfirmed — and mutates nothing unless the assignment specifically authorizes it; use it for anything that starts from a `#n`. `xezar-issue-create` creates one new issue in this repository and never edits, comments on, relabels, reopens or closes an existing one; use it when the input is a problem or a proposal with no issue yet. It runs as the `issue-filing` workflow, with a brief that says what to file. That brief is the authority: a brief naming the issue to file approves autonomous creation, and anything weaker — an autonomy flag, silence, a workflow advancing, or merely selecting the skill — stops at a retained draft. An interactive run shows the exact destination, title, body and labels and waits for Create or Revise through `XEZ:ASK` in the terminal step, so a pending approval belongs in `BLOCKED` before the step ends. Finding a duplicate is a triage outcome, not a filing one: report its identifier, link, state and overlap and stop. If both are needed, run them as separate tasks; a filing task is not authority to implement what it files.

## Leader command delivery (MCP)

The project leader works through the Xezar MCP tools only – no cockpit UI, no HTTP API – and is attached so that events are pushed to it as `<channel source="xezar">` messages (a started turn for Codex, OpenCode and pi). `leader_events` pull is the fallback for a leader that is not attached, not the normal path. `gh` stays the way to read GitHub facts (labels, verdicts, merge state) because the MCP does not carry them. Attaching is an MCP action too (#450): the leader calls `leader_events` action `attach` with a new `operationId`, and xezar takes the client from its own session (Claude Code, Codex or pi), so the leader names nothing; `leader_events` action `status` says whether it is attached and can receive pushes. An OpenCode leader is attached by a person in Settings → MCP connection → Attach leader (owner rule, 2026-09-15, #439). A Claude Code leader only receives those pushes when launched with `claude --dangerously-load-development-channels server:xezar`; without that flag, or when Codex is not yet running on the shared local app-server, pi is not yet running xezar's leader extension, or OpenCode has not yet been attached by a person in Settings → MCP connection, read with `leader_events` `read` instead. Per-client leader launch and setup (Claude Code, Codex, pi, OpenCode) is documented once, for the end user, in `docs/guide/13-mcp-leader.md` — do not restate those steps here. A mutating tool call that lost a race (another writer changed the task first) answers `stale_version` instead of applying (for example `execution_control`'s `answer_question`/`continue`/`send_message`): re-read the task with `task_read` for its current `version` and decide again, rather than retrying the same stale write. The task version tracks a persisted, monotonic decision revision: status, archive/pin flags, title/title origin, auto-resume, task brief, queued messages, step identity/status, branch and workflow. Participant input advances it too. Transcript/tool/usage progress alone does not change it. This applies to every execution_control action and every other run-version guard; reversing a decision still invalidates an older token. On stale_version, re-read task_read and make a new decision with a new operationId; never blindly retry currentVersion. After a context compaction the leader recovers by reading, never by waiting (#460 § 4): call `leader_events` with action `read` and no cursor before relying on prior pushes, page with `nextCursor` while `hasMore` is true, deduplicate by `eventId`, reconcile current task state, then acknowledge only the events accounted for — a transport receipt is not an acknowledgement. Delivery is at-least-once within retained durable state, not exactly-once: the journal retains at least the newest 10 000 rows and evicts none younger than 14 days, a page carries at most 100 rows or 40 000 bytes, and anything outside that is an explicit gap whose current state is reconciled before `resumeCursor` is acknowledged. Acknowledgement is cumulative, monotonic and idempotent, only `ack` advances it, and no timer re-pushes a row already delivered. Do not poll while idle. A tool call is not delivery: read back the tool's result (run id, status, effective options) and the pushed event or `task_read` history that shows the task acted on it. The delivery-state table below applies unchanged, with the tool result as the attempt record and the pushed event or history row as the acknowledgement.

## Browser command delivery (a person in the cockpit)

This section is for a person driving the cockpit, and records the retired UI-leader pilot; a project leader does not use it. Reuse one working task tab and close obsolete tabs you created. Before Start or Send, read back project, full task identity, workflow, backend/model, Worktree, autonomy, exact draft and enabled control. A disabled composer is a capability/state question: preserve its draft and restore the supported path before submission. Submit once, then reconcile fresh thread/history; a click or a draft is not delivery.

Use a short command identity in the brief and the existing task checkpoint. It correlates observations; it is not a server idempotency key. Track each state independently:

| State | Evidence required |
|---|---|
| Attempted | Exact command/draft, target, identity and submission time |
| Server persisted or queued | Supported acknowledgement or matching persisted user-message; record which one |
| Runner received | Exposed runner acknowledgement; transcript persistence or queue acknowledgement alone is not runner receipt; otherwise unknown |
| Acted upon | Agent response or artifact explicitly addressing the command |
| Unresolved | Last confirmed state, missing evidence, investigation deadline and next trigger |

A transcript message can be persisted before runner send fails. A startup queue acknowledgement can refer to an in-memory buffer lost on restart. Therefore neither proves runner receipt. For timeouts before/after acceptance, persistence followed by refusal, or deferred acceptance followed by restart, inspect the same command identity and preserve unknowns. Do not blindly retry, launch a replacement owner or equate an accepted message with completed code. Checkpoint unresolved delivery, stop automatic retries, and investigate within a stated finite window; when it expires report the narrow blocker and the supported manual continuation. Never infer absence from one failed or incomplete read.

## Readiness and ownership ledger

Use the existing durable task evidence directory and one coherent checkpoint, not another database. Each row names AC, candidate head/base, implementation artifact, execution status, independent review/QA, current CI, merge commit, primary sync and effective deployment evidence. Unknown, failed, interrupted and not-run remain distinct. A closed issue with unmet AC, a done author with missing review/red CI, or merged code absent from the live artifact remains unready in that dimension. Record archive membership separately from execution; link to archived work that resumes.

A takeover starts with confirmed owner state, checkpoint, branch/worktree and backend session identity. A parked view is not a dead owner. Preserve raw history, correction manifests, consumed workflow returns and same-failure repairs across task IDs/backends. Recover missing history before deciding another repair budget. One primary writer and the actual engine lease remain required where applicable; never manufacture a lease record. Use current authorization when the owner explicitly assigned direct primary-checkout work.
