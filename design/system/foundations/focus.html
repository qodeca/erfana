Focus and keyboard

Where the keyboard is, and how you can tell. Tab through this page — every ring below is the real one.

The decision. The app used to ship three focus rings: a 1px outline on tabs and the activity bar, a 2px outline in dialogs and toasts, and a 3px soft glow on inputs. That was not a style choice, it was drift. One ring wins: a 2px solid outline in --color-border-focus, offset 2px.

The two numbers come from two different criteria, and this card used to cite the wrong one. SC 1.4.11 (AA) asks a focus indicator for 3:1 against what is next to it. SC 2.4.13 Focus Appearance (AAA) asks for an indicator at least as large as a 2px perimeter, changing contrast by at least 3:1. The 1px ring fails the area half of 2.4.13; the 2px ring meets both, so 2px is the floor here. (SC 2.4.11 is Focus Not Obscured — about the ring being hidden behind a sticky header, not about its width.)

Every renderer stylesheet is now held to this by focusRing.audit.test.ts (width and offset of every drawn ring) and by npm run lint:css (--shadow-focus is banned in src/ as well as here).

The ring

default outline: 2px solid var(--color-border-focus), offset 2px — :1 against a panel, clear of the 3:1 that WCAG 2.2 SC 1.4.11 requires of a focus indicator.
inside a list
Same ring, offset inward. An outward ring gets sliced off by the scroll container. This is the only permitted variation.

Two rules that are not negotiable

1 · Use :focus-visible, never bare :focus. Bare :focus paints the ring after a mouse click too, which looks broken, which is what makes people delete it. :focus-visible shows it to keyboard users only, so nobody wants it gone.
2 · outline: none is only allowed with a replacement on the very next line. Two panels in Erfana can be reached with Tab and show nothing at all, because someone wrote outline: none; /* Remove focus outline */ and stopped there. A keyboard user lands in the editor and has no idea. If an element takes focus, something must change on screen.

stylesheets remove an outline without declaring a :focus-visible rule anywhere in the same file. That is a signal, not a verdict — a few of them replace the ring with a box-shadow or sit on an element nothing can focus. It is the list worth reading, not the list of confirmed defects, and it is stated that way rather than inflated into one.
what shipped Tab onto this and nothing happens. This is the live defect, reproduced. WCAG 2.4.7, Level A.

Retired

--shadow-focus — the 3px soft glow used on inputs — is retired as a focus indicator. It reads as a glow rather than an edge, it is a fourth idiom, and two dialogs hand-rolled its exact geometry with a different colour instead of using the token. Inputs take the same outline as everything else — and since #230 they do: the search bar, the settings controls and every dialog input and select draw this ring, and the glow has no remaining use in src/.

What a card must promise about the keyboard

QuestionThe answer a component owes you
Can I reach it?Every control is a real <button> or has a tabIndex. A <div onClick> is not reachable.
Can I tell where I am?The ring above. Always.
Can I move inside it?Lists, trees and menus take arrow keys, and hold one Tab stop between them — not one per row.
Can I get out?Escape closes and returns focus to whatever opened it.
Do I know what it is?A visible label tied by for/id, or an aria-label — never both competing.
Erfana still fails row three in one place: the right-click menu has no arrow keys (#90). The file picker, screen picker and window picker do it correctly, and so does the file tree.

The file tree passes it with a roving tabindex. The whole tree is one Tab stop: the focused row has tabIndex="0", every other row has -1, and the arrow keys move focus between rows. Before #87 it failed in the more hostile direction. ProjectTreeNode.tsx spread dnd-kit's drag attributes, whose tabIndex: 0 and button role made every row a Tab stop that answered no key: 400 files, 400 dead stops. The fix was not additive. Those attributes had to be dropped first, or the two mechanisms would have fought over the same attribute. The tree's rows sit in a scroll container, so they draw the inset ring shown above.

Exceptions

Where the shipping component departs from this card, with the reason. An undocumented deviation is a bug; a documented one is a decision.

WhereThe cardThe component, and why
HTML-preview placeholder ring Offset 2px outward, or inset inside a scroller – the only permitted variation. Outward at offset 0, and only the top edge shows: the page's native view paints over the placeholder box, and the panel clips the other three sides. A visible 2px edge still meets SC 2.4.7. Accepted at #124 QG-8 U2; see HtmlPreviewPanel.css.
Escape from a previewed page Escape returns focus to whatever opened it. Returns to the permission band's chip, not to the placeholder that entered the page. The chip's accessible name states that exit ("Press Escape in the previewed page to return here", decided band card), and a page can also be entered with the mouse, where there is no opener.

The overlay is a separate transparent window that cannot load design-tokens.css, and it is drawn over whatever is on the desktop.
