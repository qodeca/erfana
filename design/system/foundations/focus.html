Focus and keyboard

Where the keyboard is, and how you can tell. Tab through this page — every ring below is the real one.

The decision. The app currently ships three focus rings: a 1px outline on tabs and the activity bar, a 2px outline in dialogs and toasts, and a 3px soft glow on inputs. That is not a style choice, it is drift. One ring wins: a 2px solid outline in --color-border-focus, offset 2px. WCAG 2.4.11 asks for at least 2px, so the 1px version fails outright — that settles it without a taste argument.

The ring

default outline: 2px solid var(--color-border-focus), offset 2px — :1 against a panel, clear of the 3:1 that WCAG 2.2 SC 1.4.11 requires of a focus indicator.
inside a list
Same ring, offset inward. An outward ring gets sliced off by the scroll container. This is the only permitted variation.

Two rules that are not negotiable

1 · Use :focus-visible, never bare :focus. Bare :focus paints the ring after a mouse click too, which looks broken, which is what makes people delete it. :focus-visible shows it to keyboard users only, so nobody wants it gone.
2 · outline: none is only allowed with a replacement on the very next line. Two panels in Erfana can be reached with Tab and show nothing at all, because someone wrote outline: none; /* Remove focus outline */ and stopped there. A keyboard user lands in the editor and has no idea. If an element takes focus, something must change on screen.

stylesheets remove an outline without declaring a :focus-visible rule anywhere in the same file. That is a signal, not a verdict — a few of them replace the ring with a box-shadow or sit on an element nothing can focus. It is the list worth reading, not the list of confirmed defects, and it is stated that way rather than inflated into one.
what shipped Tab onto this and nothing happens. This is the live defect, reproduced. WCAG 2.4.7, Level A.

Retired

--shadow-focus — the 3px soft glow used on inputs — is retired as a focus indicator. It reads as a glow rather than an edge, it is a fourth idiom, and two dialogs hand-rolled its exact geometry with a different colour instead of using the token. Inputs take the same outline as everything else.

What a card must promise about the keyboard

QuestionThe answer a component owes you
Can I reach it?Every control is a real <button> or has a tabIndex. A <div onClick> is not reachable.
Can I tell where I am?The ring above. Always.
Can I move inside it?Lists, trees and menus take arrow keys, and hold one Tab stop between them — not one per row.
Can I get out?Escape closes and returns focus to whatever opened it.
Do I know what it is?A visible label tied by for/id, or an aria-label — never both competing.
Erfana currently fails row three in two places: the file tree and the right-click menu have no arrow keys. The file picker, screen picker and window picker all do it correctly — so the pattern to copy is already in the codebase.

The tree fails it in the more hostile direction. This note used to say "nothing focusable inside them", which is wrong about the tree: ProjectTreeNode.tsx spreads dnd-kit's drag attributes onto every row, and useDraggable defaults to tabIndex: 0 plus a role. So every row is a tab stop, announcing as a button, responding to no key — 400 files, 400 dead stops. A tree nothing can focus is skipped by Tab and quickly understood; a tree where every row stops you and none answers is a wall. It also means the roving fix is not additive: dnd-kit's tabIndex has to be overridden first, or the two mechanisms fight over the same attribute.
