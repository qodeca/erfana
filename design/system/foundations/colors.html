Colours

Erfana is dark mode only, and that is now true rather than aspirational: the renderer contains prefers-color-scheme blocks.

It shipped one until recently — thirty lines restyling the Mermaid toolbar for a light OS. Not dead code: color-scheme: dark does not change what that query reports, because the query follows the operating system. It was a second, unmaintained theme that real users saw in exactly one component. It was deleted rather than documented, because a card reading "dark only, except there" writes a bug down as a rule.

Nothing on this page is typed by hand. Every swatch is painted with var(--token) from the app's own design-tokens.css, then read back with getComputedStyle. Every contrast ratio is computed in this page at load, across the colour tokens the app declares.

This page used to claim the two cannot drift. That was false three ways: tokens.css here is a copy refreshed by a build step, the tables below hand-list a subset of the tokens, and a deleted token falls back to inherited colour — so it renders as a plausible swatch with a plausible ratio rather than failing. What is true is narrower and worth more: npm run design -- --check fails in CI when the copy and the app disagree.

Text

This is the table that decides accessibility arguments. 4.5:1 is the WCAG 2.2 minimum for normal text (SC 1.4.3); 3:1 is the minimum for large text and for non-text parts of a control (SC 1.4.11). --color-text-secondary reaches only :1 on a panel — it is a muted label colour, not a body-text colour. --color-text-tertiary is the lightest muted option that passes.

Read the scope of that carefully: on a panel. The same token on the app background clears 4.5:1 comfortably, which is why this card judges a pair, never a colour on its own.

--color-text-muted is not a text colour at all: it reaches only :1 on a panel and stays under 4.5:1 on every surface. Keep it for icons and large text; a label someone has to read takes --color-text-tertiary.

Text on a violet fill

The brand violet is a light tint, so anything drawn on it — a primary button's label, an active toggle's icon, a badge count — is dark, not white. --color-text-on-accent (brand black) measures :1 on the resting fill; --color-white measures only :1, under both the 4.5:1 text bar and the 3:1 icon bar. --color-btn-primary-text is the button alias of it. accentFill.contrast.test.ts holds every violet fill in the renderer to 4.5:1.

Exceptions

Where the shipping component departs from this card, with the reason. An undocumented deviation is a bug; a documented one is a decision. Each row has a deviates: marker at the site. For the screenshot overlay the bypass is colour, type size and offsets – no tokens reach the window; corners are still 0.

WhereThe cardThe component, and why
Screenshot overlay hint (.screenshot-overlay-hint) Every colour is a token. Literal white text on a 65% black scrim. The area-select overlay is its own transparent window and does not load design-tokens.css (#164); it paints over arbitrary desktop content, not an app surface, so the scrim is what guarantees the contrast. Forced-colours mode swaps both for Canvas / CanvasText. See ScreenshotOverlay.css.
Screenshot overlay selection (.screenshot-overlay-selection) Every colour is a token. Literal white 1px edge and a 25% black scrim outside it, for the same reason: no tokens reach the window, and the edge has to read against the desktop under it.
Screenshot overlay size readout (.screenshot-overlay-size) Every colour is a token. Same treatment as the hint, at a smaller size. The bypass covers colour, type size and offsets – no tokens reach the window; corners are still 0, like the rest of the app.
