Colours

Erfana is dark mode only, and that is now true rather than aspirational: the renderer contains prefers-color-scheme blocks.

It shipped one until recently — thirty lines restyling the Mermaid toolbar for a light OS. Not dead code: color-scheme: dark does not change what that query reports, because the query follows the operating system. It was a second, unmaintained theme that real users saw in exactly one component. It was deleted rather than documented, because a card reading "dark only, except there" writes a bug down as a rule.

Nothing on this page is typed by hand. Every swatch is painted with var(--token) from the app's own design-tokens.css, then read back with getComputedStyle. Every contrast ratio is computed in this page at load, across the colour tokens the app declares.

This page used to claim the two cannot drift. That was false three ways: tokens.css here is a copy refreshed by a build step, the tables below hand-list a subset of the tokens, and a deleted token falls back to inherited colour — so it renders as a plausible swatch with a plausible ratio rather than failing. What is true is narrower and worth more: npm run design -- --check fails in CI when the copy and the app disagree.

Text

This is the table that decides accessibility arguments. 4.5:1 is the WCAG 2.2 minimum for normal text (SC 1.4.3); 3:1 is the minimum for large text and for non-text parts of a control (SC 1.4.11). --color-text-secondary reaches only :1 on a panel — it is a muted label colour, not a body-text colour. --color-text-tertiary is the lightest muted option that passes.

Read the scope of that carefully: on a panel. The same token on the app background clears 4.5:1 comfortably, which is why this card judges a pair, never a colour on its own.
