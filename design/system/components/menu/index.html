Menu

Right-click the panel below — then use only the keyboard. Arrows, Home, End, Enter, Escape, and type a letter to jump.

The decision: a role is a promise. Erfana's context menu declares role="menu" and role="menuitem" today and implements none of the keyboard behaviour those roles commit to — no tabIndex, no arrow keys, no focus moved on open, no focus returned on close. Only Escape is bound.

That is worse than declaring nothing. A screen reader switches to application mode on a menu and hands the arrow keys straight to the widget, so the user loses their normal browse-mode keys and gets nothing in exchange. The menu has dependants, so this is not a corner of the app.

Either implement the contract or drop the roles. Both are honest; only the current state is not. This card implements it.

The keyboard contract

↑ ↓Move between items. Wraps at both ends.
Home EndFirst and last item.
Enter SpaceActivate. A disabled item does nothing.
EscapeClose, and return focus to whatever opened it.
a–zJump to the next item starting with that letter.
TabCloses the menu. A menu is modal to the keyboard while open.
Roving tabindex, not aria-activedescendant. Exactly one item carries tabindex="0" and really holds focus; the rest are -1. Both patterns are valid, and this one is chosen because real DOM focus is what makes :focus-visible, scroll-into-view and the browser's own find behave normally. With aria-activedescendant the focus ring is something you have to draw yourself, and a design system that has just spent a card unifying focus rings should not immediately need a second way to paint one.
Focus must come back. Closing a menu without restoring focus drops the user at the top of the document — the same defect the Permission band card fixes on its Allow button. The trigger is remembered when the menu opens, not looked up when it closes.
Typeahead is not a nicety. It is the only way a long menu is usable without counting arrow presses, and it is what people expect from every native menu on every platform.

Every state

Disabled beats danger. A greyed-out Delete must not still be red. The colour is a promise about what activating the item will do, and a disabled item will not do anything — a red item you cannot click reads as an error, not as "not available right now". So the disabled rule wins the cascade, and the demo above renders that case rather than describing it.

Disabled text is deliberately dim: WCAG 1.4.3 exempts inactive controls. It is the one place on this card where low contrast is correct, which is worth saying out loud so nobody "fixes" it.
The trigger has to say something too. Whatever opens a menu carries aria-haspopup="menu" and aria-expanded. Without them a screen-reader user has no way to know the control does anything before pressing it. Erfana's tree rows do not do this today.
