Every control below is live. Tab through them.

These controls were invisible, and it was a token defect, not a card defect. --color-bg-input and --color-bg-secondary resolve to the same colour, so a field's interior is pixel-identical to the panel behind it. The only thing marking the control is its border — and that border was --color-border-default at 1.24:1, against the 3:1 that WCAG 2.2 SC 1.4.11 requires.

1.4.11 is met if either the fill or the boundary reaches 3:1. Neither did, on any of the three surfaces an input actually sits on. The fix is a new --color-border-input, now :1 here — not a brighter fill, which would have to clear 3:1 against all three surfaces and would end up reading as a button. --color-border-default and --color-border-subtle are unchanged; 1.4.11 does not govern decorative dividers.

Separately, and under a different rule: the placeholder was 2.69:1. Placeholders are text, so the bar is 1.4.3's 4.5:1, not 3:1 — it is now :1.
What this card replaces. Five copies of the same dropdown, three text inputs of three different heights, and two entirely different checkboxes shipping in the same window. Two of the five dropdowns have no disabled style, so they still light up on hover when they cannot be used.

The error contract

Erfana has no error contract today. aria-invalid appears in places in the renderer. No error message is linked to the field it belongs to. The only in-field signal is red text on the value the reader typed — colour alone, which fails WCAG 1.4.1.
RuleWhy
The field carries aria-invalid="true"It is how a screen reader knows this field is the problem.
The field points at the message with aria-describedbyOtherwise the message is read out of order, or not at all.
The border changes, and there is an iconColour alone is invisible to some readers. Two signals, always.
The message says what to do"Invalid name" is a verdict. "Cannot contain a space — try my-notes" is help.
The message sits directly under the fieldNot at the top of the form. Not in a toast.

Naming a field

Every control has exactly one name, from exactly one source. Either a visible <label for> tied to the control's id, or an aria-label when there is genuinely no visible text. Never both — they compete, and the reader hears the wrong one.

Two fields in Erfana have neither: a <label> linked to nothing and a control with no id. The rename field is on the path for every rename, new file and new folder in the app.

And a <label> with no control is not a label — it is a heading. Use a <span>.
