# Known limits

Parts of a design rule that the platform cannot build, with the fallback that ships. Each row is listed in the pull request.

| Item | Limit | Fallback |
|---|---|---|
| C-12 R-20 – a link inside a comment mark | The CSS Custom Highlight API cannot style links inside a highlighted range: `::highlight()` takes no `text-decoration-line` and no descendant selector. The "links keep their colour and gain an underline" rule cannot be built for marks drawn this way (recorded 2026-10-30). | The mark's fill and bar are drawn under the link's own colour and underline as the preview styles it. Link contrast inside a mark is part of the owner's hands-on check on the Text highlights card. |
| 024-NFR-008 – Erfana's own blocks in the Markdown limit scan | The limit scan runs before any parse, so it cannot always tell that a block Erfana wrote is a comment to the parser. It leaves a block's inside out of the raw-HTML count only where crafted text could not make it anything else (`ownBlockInteriors` in `src/shared/markdownComments/markdownLimits.ts`). A block in a paragraph (a list item's text) whose message has a blank line or a line starting with a block marker (`-`, `#`, `>`, a digit, …) is still counted, and so is any block after it in the same paragraph (recorded 2026-10-30). | Such a block adds its `target:` tags (one or two) to the HTML depth, as every block did before. A file is refused as "too large" only if more than 256 of them pile up; it is read-only, never damaged. |
| 024-NFR-001 – Markdown large-file timing | On a 1 MB Markdown file with 200 comments the times are over budget (P50 and P95 pins ≤ 500 ms, save ≤ 1,000 ms). Windows e2e, 20 samples (`e2e/markdown-comments.timing.e2e.ts`): pins after preview-rendered P50 1,134 / P95 1,252 ms; saved comment visible after Save P50 5,421 / P95 5,739 ms (2026-10-30, after the per-thread DOM scans and the preview's second parse were removed; before: pins 4,937 / 14,383 ms, save 36,774 / 43,833 ms). Main-side floor under vitest: list P50 3,273 ms, save P50 3,710 ms (`large-file-timing.md`). Cause: the remark/micromark + GFM parse of the whole file, on every list and save – no change to Erfana's own code reaches 0.5 s. A save costs two parses of the 1 MB text: main's write job (about 2 s) and the preview's render of the reloaded file (about 3 s) – profiled, see `large-file-timing.md`. Owner decision 2026-10-30: measure, record, ship; the owner sets the final budget later. Until then the test's macOS/Linux gate fails (recorded 2026-10-30). | The comment read starts while the preview renders, so pins come sooner than before; "Reading comments…" shows in the drawer meanwhile. Comments stay correct, only slow. HTML meets its budget; its gate F-001 is unchanged. |
| M-08 frames and M-10 overlay setup failure – the HTML menu's reason line | In the HTML Preview a right-click on a frame that cannot be commented (an inline `srcdoc` frame, a frame from another site – M-08) and a right-click after the page overlay failed to set up (M-10) do not take the page→main pick path that names the reason, so the menu cannot say "Comments can't be added inside an inline frame.", "…inside a frame from another site." or "Comments are unavailable for this file: {reason}.". Widening the page→main pick path to these cases was decided against, to leave the right-click gate of security review L-1 (`src/main/services/preview/comments/commentContextGate.ts`) unchanged (recorded 2026-10-30). | The item keeps its action name, disabled with the generic reason line ("This part of the page can't hold a comment."). For M-10 the toolbar's tooltip still gives the full sentence, "Comments are unavailable for this file: {reason}.". |
| 024-NFR-005 – a press on the page in HTML comment mode | In comment mode the page preload stops a primary press from reaching page script (`stopImmediatePropagation` on `pointerdown`/`mousedown`, `input.ts`), but it keeps the browser's default so a drag can still select words (024-FR-004). The default's follow-on events – `focus`/`focusin` on a focusable element, `selectstart`, `selectionchange` – still reach page script, and a press on a form control inside a closed shadow root can focus it. Found by the security audit (L-1) of 2026-10-30. | No comment data or Erfana UI is exposed: the overlay sits in its own closed shadow root and picks go to main only from trusted events. A page that acts on focus may react to a press in comment mode, as it would to a click outside it; leave comment mode (Esc) to use the page normally. |
| Final code review L1 (2026-10-31) – `file-comment:release` under React StrictMode | In development builds only, StrictMode runs each effect's cleanup once right after mount, so a Markdown panel sends `release` once on mount; a list already confining for that panel then answers `not-open`. Production builds do not double-run effects. | The panel lists again on its next refresh; nothing is written or lost. |
| Final code review L2 (2026-10-31) – a keystroke during a Markdown comment save | If the editor is changed after main wrote the comment but before the save answers, `reloadIfUnedited` keeps the edited buffer, and the file watcher's event is what raises the "changed on disk" conflict. On the macOS rename path the event can be missed. Reaching it needs leaving the preview-only view in the middle of a save. | The existing conflict banner when the watcher reports; autosave never fires during the conflict (`useFileWatcher`). |
| Final code review L5 (2026-10-31) – the first free hello after a frame id comes back | `documentHellos` is keyed by frame id; if Chromium reused the id of a dropped child frame, the new record's first hello could fall on the frame budget instead of being free. Chromium frame ids are unique in practice. | The hello is still admitted while the frame's budget has room (5 a second). |
| Final security audit L-2 (2026-10-31) – icon picks at 10 a second | Main now admits 10 element and pin picks a second per view (F-001). A compromised page renderer – a normal page cannot, the preload acts only on trusted clicks – could forge icon picks that mint drafts and push the reader's open draft out of the 64-draft store in about 6.4 s (was 12.8 s). It never writes. | Save answers "key invalid" and the window keeps the typed text in the session drafts. |
| Final code re-review (2026-10-31) – `--!>` hand-typed inside a Markdown block | Main's own byte check (`commentInsertIndent.ts`) counts `--!>` as a comment end, as HTML does; in Markdown it is not one, so a block whose text someone hand-edited to hold `--!>` still reads `ok` but a reply, edit, resolve, rebuild or delete on it is refused (`verify-failed`). Erfana never writes `--!>` itself (the writer escapes `--`). | The window keeps the typed text; the block can be fixed in the editor (Open in source) and the comment then changes normally. |
| Final security re-check L-D (2026-10-31) – where a replaced or removed block sits | Main checks that the bytes replaced or removed are exactly one `erfana:comment` block, not where they sit: text shaped like a block inside a code fence, an attribute value or a script string could be rewritten if the parse worker answered wrong. The worker plans only over blocks its parser found, and the damage is limited to that one span. | The strict write still requires every other byte of the file unchanged on disk. |
