# Large-file timing (024-NFR-001, 024-AC-024)

Generated by `npm run test:timing` (`src/main/services/comments/corpus/largeFileTiming.test.ts`); do not edit by hand.

## Run

- Machine: win32 10.0.26200, Intel(R) Core(TM) i9-9880H CPU @ 2.30GHz × 16
- Runtime: Node v24.21.0 under vitest (the app's Electron is 44.9.3; its bundled Node runs the same code in the parse worker)
- Package conditions: node, development (with `development`, the micromark packages load their debug builds, with assertions; the app's bundle loads the default builds)
- Date: 2026-10-30
- Fixtures: seeded, generated by `largeFixtures.ts` – about 1,048,576 bytes with 200 comments each
- Markdown comments sit on paragraphs and headings, as in the first run, so the runs compare
- Samples: 20 per measure after 2 untimed warm-up runs

## What is timed

The parse work of the comment parse worker, on the calling thread: a cold `list` job (fresh runner, no cached parse), and a save – the `write` job of one add, main's `assembleSplice`, then the `list` of the new file. Before a save the app has listed the file on the same worker – the HTML draft and the Markdown list run first, untimed – so a Markdown save plans on the cached parse; the Markdown save with no list before it is recorded on its own row. IPC, the worker message copy and the preview's drawing are **not** in these numbers, so they are a floor of the budgets, not the 024-AC-024 measurement itself. That one is the e2e timing between the renderer's `performance.mark` points in the built app (`commentTiming.ts`), recorded by `e2e/markdown-comments.timing.e2e.ts` for Markdown and `html-preview-comments.perf.e2e.ts` for HTML.

## Before and after

Kept by hand; a rerun of `npm run test:timing` carries this section over.

### 2026-10-30 – Markdown save plans on the cached parse (Windows, the machine above)

Change: a Markdown (and `.txt`) save plans on the parse the list already left in the worker's cache and parses only once more, to verify (`kindCommentJobs.ts`). Before, it parsed the file twice: once to plan and once to verify. A cache miss no longer hashes the bytes twice either (`commentJobDocs.ts`). Output bytes are unchanged: a save after the list writes exactly what a cold save writes (`markdownCommentJobs.test.ts`).

| Measure (Markdown, 1 MB, 200 comments) | Before P50 / P95 | After P50 / P95 | After ÷ list P50 |
|---|---|---|---|
| list (cold parse) | 2,589 / 2,734 ms | 3,273 / 3,494 ms | 1.00 |
| save after the list (the app's order) | 5,298 / 5,522 ms (planned on a fresh parse) | 3,710 / 3,929 ms | 1.13 |
| save with no list before it (cold) | 5,298 / 5,522 ms | 6,911 / 7,487 ms | 2.11 |

The two runs did not have the machine to themselves alike: the HTML list, whose code did not change, went from 314.8 to 376.2 ms P50 (+19 %) and the Markdown list from 2,589 to 3,273 ms (+26 %). Read the ratios, not the raw differences: a save used to cost about two lists (5,298 ÷ 2,589 = 2.05) and now costs about one (1.13).

What is left is the parse itself. Profiled on the same fixture, under vitest's `development` conditions: micromark with GFM about 2.4 s, mdast to hast with the raw-HTML pass and sanitize about 0.5 s, and everything Erfana does on top (limit scan, index, block classification, list) about 0.25 s. The micromark parse alone, without GFM, takes about 1.9 s with the debug build vitest loads and about 1.2 s with the default build the app ships. So no change to Erfana's own code brings the list to 0.5 s: it would take a faster parse of the same CommonMark/GFM tree.

### 2026-10-30 – Windows e2e after profiling the save (recorded, not gated)

Same test, fixture, machine and build steps as the entry above; 20 samples, `--retries=0`.

Profiled first, with temporary `performance.now()` probes around the save, the list reads, the file watcher's reload, the preview body render and the overlay's icon layout, plus a long-task observer (all removed afterwards). Where the 33 s between main's write and the drawn icon went, one sample before the change:

| Step after Save (Markdown, 1 MB, 200 comments) | Before | Cause |
|---|---|---|
| Main's save (`file-comment:save`, write job + verify) | 2.1 – 3.4 s | the parse; not changed here |
| Overlay icon layout, about 10 draws on the way to the new icon | 2.9 – 3.7 s **each**, about 30 s in all | `markdownAdapter.attach` scanned every line-stamped element of the preview once **per listed thread**: 200 full scans of a 1 MB DOM per draw. Every draw (list answer, watch event, reload, preview commit, the content observer's redraw) paid it on the renderer's main thread, so the file watcher's reload and the preview render queued behind it. |
| Preview body render of the reloaded text | about 3 s, plus a second parse of about 2 – 2.5 s | the deferred (transition) render was interrupted by the next update in the window and React started it again, parsing the 1 MB text twice |
| Lists after the save (`onWritten`, then main's watch event for the same write) | 45 – 440 ms each in main | the parse cache answers; kept |

Changes:

- `markdownAdapter.ts` scans the preview's line stamps once and keeps the index until the content changes (a `MutationObserver` on child lists, text, `data-line-start` and `class`; each read first takes the undelivered records, so a change made earlier in the same task is seen). `attach`, `targetsInOrder` and `hiddenNow` answer from it, exactly as a fresh scan would (`markdownAdapter.test.tsx`).
- `markdownBodyParse.ts`: the preview body keeps its last react-markdown parse in a ref, so a render React throws away and restarts reuses the parse of the same text, plugins and components instead of parsing again. The timing probe's span still covers the parse; the output is the same elements (`markdownBodyParse.test.tsx`).

Profile after the change, one sample: save in main 1.7 – 2 s, list answers 0.6 s, watcher reload 0.3 s, preview parse and render about 2.5 s plus 0.4 – 0.6 s for the restarted render (now without a parse), icon drawn 0.7 s after the preview commit; the overlay's icon layout takes under 100 ms per draw.
